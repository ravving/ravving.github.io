    Running on a Zynthbox

    ravving runs in place of zynthbox-qml, the stock Zynthbox UI: the same startx session, the same display, keys and audio. Only one of the two runs at a time. Everything below is installed by cmake --install and by the AppImage's setup program.

    What is installed where

    PathWhat it is
    /usr/bin/ravvingThe application.
    /usr/share/ravving/Its data (kits.json, presets, demos, the webpage), start.sh, default-app.sh, check-requirements.py, requirements.json and VERSION.
    /etc/systemd/user/ravving.serviceThe user unit that starts ravving.
    /etc/systemd/system/bluetooth.service.d/50-ravving-bluetoothd-path.confStarts bluetoothd from the path Debian ships it at.
    /etc/wireplumber/wireplumber.conf.d/50-ravving-bluetooth.confWirePlumber's Bluetooth settings for ravving.
    /etc/wireplumber/wireplumber.conf.d/50-ravving-hardware.confOne name per sound card on the JACK graph.
    /usr/share/locale/<lang>/LC_MESSAGES/ravving.moThe translations.

    The service and the startup script

    ravving.service (a systemd user unit) runs startx /usr/share/ravving/start.sh with zynthbox-qml's environment (ZYNTHIAN_DIR, ZYNTHIAN_SYS_DIR, HOME=/root…). It conflicts with zynthbox-qml.service and is ordered after it, so starting either stops the other before the new one starts:

    
 systemctl --user start ravving        # switch to ravving
 systemctl --user start zynthbox-qml   # and back

    It requires pipewire.service and wants pipewire-pulse.service (the music player plays through PulseAudio). ExecStop sends SIGTERM to ravving and waits for it to exit before X goes, so the button LEDs are switched off. Restart=always restarts it after any end that was not a requested stop; a crash loop stops after five starts in two minutes.

    start.sh sets up the display and environment the same way zynthbox-qml's start.sh does, starts KWin, then runs /usr/bin/ravving (under gdb, printing a backtrace on a crash, when RAVVING_GDB=1 is set in the user manager's environment). When ravving exits it writes the exit code and time to ~/.local/state/ravving/last-exit, which the next start reads to report how the previous run ended (LastRun).

    default-app.sh: which UI the device runs

    Runs on the device as root. The setup program, tools/device.sh default and ravving's own switch to Zynthbox call it.

    CommandWhat it does
    default-app.sh ravvingravving starts at boot. zynthbox-qml is masked (a /dev/null unit in root's ~/.config/systemd/user), which overrides its global enable and survives the system updater re-enabling it.
    default-app.sh zynthboxBack to stock: zynthbox-qml unmasked and started, ravving stopped and disabled.
    default-app.sh zynthbox --purgeAs zynthbox, and removes ravving's binary, data, unit, translations, settings, session and cache. Saved projects, takes and recordings are kept.
    default-app.sh run APPSwitches to ravving or zynthbox for this session only; the boot choice is unchanged.
    default-app.sh install DIRCopies a bundle (an AppImage's AppDir or a cmake --install staging tree) into the system: the binary, the data (replaced as a whole), the unit, the translations, the WirePlumber files and, where a drop-in starts a bluetoothd that is not there, the bluetoothd path fix. The new binary is checked with ldd before it replaces the old one: one that lacks a library is not installed (exit 2) and the installed ravving stays as it was; deps DIR --install gets the package first.
    default-app.sh statusPrints which UI starts at boot, which one runs, and the installed version.
    default-app.sh deps DIR [--install] [--json]Runs check-requirements.py for the bundle in DIR; --install puts the bundle's files in place and installs the missing packages.

    Stopping a UI kills every process of its service, so a switch requested from inside a UI would kill the script itself. The switching commands therefore re-run themselves in a transient unit (systemd-run) before they touch the services.

    check-requirements.py and requirements.json

    requirements.json lists what the device must have: each entry has an id, a level (startup: ravving cannot start without it; otherwise a feature is lost), the feature it serves, the files, folders or programs that prove it is there, the Debian package that brings it, its effect when missing, how to fix it, and restart when what brings it takes effect only from the next start. A libraries list names the shared libraries the binary links to, each with the Debian package that brings it.

    check-requirements.py [--data DIR] [--binary PATH] [--bundle DIR] [--install] [--json] checks every entry, and with --binary the libraries ldd reports not found. A missing file the bundle carries at the same path is marked inBundle. --install copies those files into place, refreshes the package lists, installs the packages the device's sources have with apt-get (in the system's environment, never asking, waiting at most two minutes for the package manager's lock), then checks again. --json prints the result for the setup program, with an install block saying how the install went (ok, or the reason: offline, locked, unavailable, interrupted, timeout, notroot, failed).

    Exit status: 0 nothing is missing; 1 only features are missing; 2 ravving cannot start.

    The setup program

    The AppImage starts ravving-setup (setup/: main.cpp, Setup.qml, Bundle and Catalog), a full-screen page that installs the bundle and picks the UI. It links Qt only and reads ravving's translations itself, so it starts on any Zynthbox. Bundle runs the bundle's own default-app.sh, in the system's environment, and logs every run to ~/.local/state/ravving-setup/setup.log:

    The system files

    • 50-ravving-bluetoothd-path.conf: the image's own bluetoothd drop-in starts /usr/lib/bluetooth/bluetoothd, which Debian installs in /usr/libexec/bluetooth/; this drop-in starts it from there with the same flags (--compat --experimental --noplugin=sap). Without it the Bluetooth service fails and the adapter stays down.
    • 50-ravving-bluetooth.conf: starts WirePlumber's Bluetooth monitor without a logind seat (the root startx session has no active seat, so otherwise no A2DP endpoint is registered); offers SBC-XQ (bluez5.enable-sbc-xq); and keeps a headset in A2DP when its microphone is opened (bluetooth.autoswitch-to-headset-profile = false).
    • 50-ravving-hardware.conf: disables PipeWire's snd-dummy card, which otherwise shares the HiFiBerry's description and takes its JACK port names on some starts.

    The WirePlumber files are read when WirePlumber starts, so they apply from the device's next start.

    tools/bluetooth-setup.sh

    Prepares Bluetooth on a device without a ravving build, from the laptop (DEVICE=root@host sh tools/bluetooth-setup.sh; --check only checks). It installs bluez-obexd, libspa-0.2-bluetooth and libkf6bluezqt6, puts the bluetoothd and WirePlumber Bluetooth drop-ins in place, restarts bluetooth.service and WirePlumber, and checks that the service is active, the adapter is powered, the adapter lists the Audio Source and Audio Sink UUIDs, and obex.service is enabled. Running it again is safe.
