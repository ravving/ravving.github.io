    Writing code documentation

    The QDoc rules for the C++ sources, the checks that enforce them and how the API reference is built.

    ravving's C++ is documented with QDoc, Qt's own documentation tool: the app in src/, the backend library in src/backend/, and the setup program in setup/. It's published as the API reference beside these pages, in site/api/, generated by tools/build-api-docs.py. The QML in qml/ is not documented there yet: it moves into plugin base types first.

    The rules

    What to write

    1. Document with QDoc. Every public item has a /*! ... */ block:
      • a class, struct or namespace: \class (\struct, \namespace), \inmodule Ravving, its \ingroup and a \brief;
      • a Q_PROPERTY: a \property block;
      • a public method, slot, Q_INVOKABLE or signal: a block;
      • a public enum: an \enum block, with a \value for each value.
    2. Be concise, precise and technical about what the current code does:
      • its inputs and outputs;
      • units: dB or linear gain, milliseconds or seconds, steps or ticks, 0..1;
      • ranges and clamping;
      • the thread it runs on: the GUI thread, the audio thread, a worker;
      • who owns what it hands out, its invariants, and its side effects (what it saves, emits, starts).

    What to leave out

    1. Never write history or AI-style context, in a QDoc block or in any // comment:
      • no used to, was changed, previously, no longer, or now X instead of Y;
      • no dates (found 2026-10-12), no the user asked, no story of a past bug or of why something changed;
      • no bug report numbers, on milo, or measured on / measured with;
      • no paths to docs or notes pages;
      • no lineage (the way zynthbox-qml does, as easyrave's…, ported from), and no wording from the request that created a feature. Keep a zynthbox-qml or libzynthbox reference only as a contract the code depends on.

    Comments, overviews and commits

    1. A // comment is welcome when it explains a non-obvious technical reason that's true of the code as it is: "muted rather than unlinked, so the jacks' sink keeps clocking the graph". A measurement that justifies a constant is a fact, and may stay, stated plainly: "30 %: the lowest still readable in a lit room".
    2. A class overview describes the class, not the screen. No pages, dialogs, rows, toasts, toolbars or "on screen" in a \class block. What QML sees is its context property, and the meaning of its properties and signals.
    3. Every new or changed C++ API comes with its QDoc in the same commit. Run python3 tools/build-api-docs.py so site/api/ follows; it's committed, like site/docs/. ctest checks both (below).

    Where the documentation goes

    The documentation lives in the .cpp files, next to the definitions, as Qt's own sources have it; the headers hold the declarations and short // notes on private members only.

    • A block right before a function's definition documents that function. Parameters are named with \a, every one of them (QDoc warns about a missing one), and a function that returns something says so with "Returns".
    • What has no definition in the .cpp gets a block anywhere in the .cpp, with \fn and the full signature, or \variable. That's a signal, a pure virtual, an inline function in the header, or a static constant. The class's own block, its \property, \enum and \fn blocks go together after the includes.
    • When the definition's parameter names differ from the header's, start the block with the \fn signature as the header has it, so \a names what the reader sees.
    • A header with no .cpp of its own (audioinsert.h, zbcall.h, filesuffixes.h) is documented in doc/src/header-only.qdoc; the header says so in one line.
    • Overrides of Qt's virtuals (rowCount(), data(), paint()) and of ravving's own base classes are \reimp, with a line on what this one adds when it adds something.
    /*!
    \class History
    \inmodule Ravving
    \ingroup ravving-studio

    \brief The project's undo history, published to QML as \c studio.history.

    Participants register once with add() and report each change with record(). ...
*/

/*!
    \property History::undoText
    \brief the name of the step undo() would undo; empty when there is none.
*/

/*!
    \fn void History::undone(const QString &what)

    Emitted after undo() went back over a step; \a what is its name.
*/

/*!
    Registers \a participant. Its state now is where its history starts. The participant
    must outlive the history or be removed with remove() first.
*/
void History::add(HistoryParticipant *participant)

    Briefs and groups

    A property's \brief is a noun phrase that QDoc puts after "This property holds": "the name of...", "whether ...". The groups (\ingroup) are the areas of the reference's landing page: ravving-app, ravving-studio, ravving-machines, ravving-engines, ravving-audio, ravving-system, ravving-setup (defined in doc/src/index.qdoc).

    The checks

    • python3 tools/check-cpp-docs.py (ctest cpp-docs):
    • It finds every public class, struct, namespace, property, method, signal, enum and free function that the headers of src/ and setup/ declare, and fails on any without a QDoc block. A documented property's READ, WRITE and NOTIFY members, destructors and deleted functions are exempt.
    • It also reads every comment of src/**/*.cpp|h and setup/ for history: dates, used to, previously, no longer, any more, was changed / replaced / removed, now X instead of Y, the user asked, found on ..., fixed in, regression and the like. The list is BANNED in the script.
    • --rule api or --rule comments runs one rule; --list prints every entity with its state.
    • python3 tools/check-docs-history.py (ctest docs-history) applies the same list to the published docs and the webpage, outside code spans.
    • python3 tools/build-api-docs.py --check (ctest api-docs-current) generates the reference into a temporary folder. It fails when QDoc prints a warning (an undocumented parameter, a link to nothing, an \fn that matches no declaration), or when site/api/ differs. It's skipped (exit 77) where no Qt 6 qdoc is installed, or when another qdoc version made the committed pages (site/api/qdoc-version.txt).

    Building the reference

    python3 tools/build-api-docs.py          # site/api/, from doc/ravving.qdocconf
python3 tools/build-api-docs.py --check  # what ctest runs

    It needs Qt 6's qdoc (Arch: qt6-tools; Debian: qdoc-qt6). It uses the first that reports a 6.x version: $QDOC, then Qt 6's host bin or libexec folder (qmake6 -query), then qdoc6 or qdoc on the PATH. /usr/bin/qdoc is Qt 5's on some systems.

    QDoc parses the headers with clang, so the include paths of Qt, KF6 (KI18n, BluezQt), JACK and the project go in a generated cxx-includes.qdocconf. Without them, a class page silently loses its members.

    doc/
  ravving.qdocconf            the project: sources, headers, the include paths
  global/ravving.qdocconf     shared settings (warnings, the template)
  global/html-ravving.qdocconf the page chrome: the webpage's top bar, the sidebar, the footer
  global/style/ravving.css    the theme: site.css's tokens and fonts, a light and a dark mode
  global/ravving-api.js       the theme switch, the sidebar (nav.js) and the search (search.js)
  src/index.qdoc              the landing page and the class groups
  src/header-only.qdoc        the header-only classes and functions

    The generator:

    • runs QDoc;
    • wraps each documented member in a box, since QDoc writes them as loose siblings;
    • writes nav.js (the sidebar: the classes by area) and search.js (every class, property, function, signal and enum) from QDoc's index file;
    • copies the script beside the pages.

    The pages reach the webpage's fonts and wordmarks through ../assets/, so site/api/ works on the public page and on the copy the device serves alike.
