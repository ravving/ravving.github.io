    Writing code documentation

    The QDoc rules for the C++ sources, the checks that enforce them and how the API reference is built.

    ravving's C++ (the app in src/, the backend library in src/backend/, the setup program in setup/) is documented with QDoc, Qt's own documentation tool, and published as the API reference beside these pages: site/api/, generated by tools/build-api-docs.py. The QML in qml/ is not documented there yet: it moves into plugin base types first.

    The rules

    1. Document with QDoc. Every public C++ class, struct and namespace has a /*! ... */ block with \class (\struct, \namespace), \inmodule Ravving, its \ingroup and a \brief; every Q_PROPERTY a \property block; every public method, slot, Q_INVOKABLE and signal a block; every public enum an \enum block with a \value for each value.
    2. Be concise, precise and technical about what the current code does: its inputs and outputs, units (dB or linear gain, milliseconds or seconds, steps or ticks, 0..1), ranges and clamping, the thread it runs on (GUI thread, audio thread, a worker), who owns what it hands out, its invariants and its side effects (what it saves, emits, starts).
    3. Never write history or AI-style context, in a QDoc block or in any // comment: no used to, was changed, previously, no longer, now X instead of Y, no dates (found 2026-10-12), no the user asked, no story of a past bug or of why something was changed. A // comment inside the code is welcome only when it explains a non-obvious technical reason that is true of the code as it is ("muted rather than unlinked, so the jacks' sink keeps clocking the graph"). A measurement that justifies a constant is a fact and may stay, stated plainly ("30 %: the lowest still readable in a lit room"). Also out: bug report numbers, on milo or measured on/measured with, paths to docs or notes pages, lineage (the way zynthbox-qml does, as easyrave's…, ported from; keep a zynthbox-qml or libzynthbox reference only as a contract the code depends on), and wording from the request that created a feature.
    4. A class overview describes the class, not the screen: no pages, dialogs, rows, toasts, toolbars or "on screen" in a \class block; what QML sees is its context property and the meaning of its properties and signals.
    5. Every new or changed C++ API comes with its QDoc in the same commit, and python3 tools/build-api-docs.py is run so site/api/ follows (it is committed, like site/docs/). ctest checks both (below).

    Where the documentation goes

    The documentation lives in the .cpp files, next to the definitions, as Qt's own sources have it; the headers hold the declarations and short // notes on private members only.

    • A block right before a function's definition documents that function. Parameters are named with \a, every one of them (QDoc warns about a missing one), and a function that returns something says so with "Returns".
    • What has no definition in the .cpp (a signal, a pure virtual, an inline function in the header, a static constant) gets a block anywhere in the .cpp with \fn and the full signature (or \variable). The class's own block, its \property, \enum and \fn blocks go together after the includes.
    • When the definition's parameter names differ from the header's, start the block with the \fn signature as the header has it, so \a names what the reader sees.
    • A header with no .cpp of its own (audioinsert.h, zbcall.h, filesuffixes.h) is documented in doc/src/header-only.qdoc; the header says so in one line.
    • Overrides of Qt's virtuals (rowCount(), data(), paint()) and of ravving's own base classes are \reimp, with a line on what this one adds when it adds something.
    /*!
    \class History
    \inmodule Ravving
    \ingroup ravving-studio

    \brief The project's undo history, published to QML as \c studio.history.

    Participants register once with add() and report each change with record(). ...
*/

/*!
    \property History::undoText
    \brief the name of the step undo() would undo; empty when there is none.
*/

/*!
    \fn void History::undone(const QString &what)

    Emitted after undo() went back over a step; \a what is its name.
*/

/*!
    Registers \a participant. Its state now is where its history starts. The participant
    must outlive the history or be removed with remove() first.
*/
void History::add(HistoryParticipant *participant)

    A property's \brief is a noun phrase that QDoc puts after "This property holds": "the name of...", "whether ...". The groups (\ingroup) are the areas of the reference's landing page: ravving-app, ravving-studio, ravving-machines, ravving-engines, ravving-audio, ravving-system, ravving-setup (defined in doc/src/index.qdoc).

    The checks

    • python3 tools/check-cpp-docs.py (ctest cpp-docs) finds every public class, struct, namespace, property, method, signal, enum and free function the headers of src/ and setup/ declare and fails on any without a QDoc block (the READ, WRITE and NOTIFY members of a documented property, destructors and deleted functions are exempt). It also reads every comment of src/**/*.cpp|h and setup/ for history: dates, used to, previously, no longer, any more, was changed / replaced / removed, now X instead of Y, the user asked, found on ..., fixed in, regression and the like (the list is BANNED in the script). --rule api or --rule comments runs one rule; --list prints every entity with its state. python3 tools/check-docs-history.py (ctest docs-history) applies the same list to the published docs (the pages tools/build-site-docs.py renders), outside code spans.
    • python3 tools/build-api-docs.py --check (ctest api-docs-current) generates the reference into a temporary folder and fails when QDoc printed a warning (an undocumented parameter, a link to nothing, an \fn that matches no declaration) or when site/api/ differs from it. It is skipped (exit 77) where no Qt 6 qdoc is installed, and when the committed pages were made by another qdoc version (site/api/qdoc-version.txt), whose output differs.

    Building the reference

    python3 tools/build-api-docs.py          # site/api/, from doc/ravving.qdocconf
python3 tools/build-api-docs.py --check  # what ctest runs

    It needs Qt 6's qdoc (Arch: qt6-tools; Debian: qdoc-qt6): $QDOC, else Qt 6's host bin or libexec folder (qmake6 -query), else qdoc6 or qdoc on the PATH, whichever reports a 6.x version (/usr/bin/qdoc is Qt 5's on some systems). QDoc parses the headers with clang, so the include paths of Qt, KF6 (KI18n, BluezQt), JACK and the project are passed in a generated cxx-includes.qdocconf; without them a class page loses its members silently.

    doc/
  ravving.qdocconf            the project: sources, headers, the include paths
  global/ravving.qdocconf     shared settings (warnings, the template)
  global/html-ravving.qdocconf the page chrome: the webpage's top bar, the sidebar, the footer
  global/style/ravving.css    the theme: site.css's tokens and fonts, a light and a dark mode
  global/ravving-api.js       the theme switch, the sidebar (nav.js) and the search (search.js)
  src/index.qdoc              the landing page and the class groups
  src/header-only.qdoc        the header-only classes and functions

    The generator runs QDoc, wraps each documented member in a box (QDoc writes them as loose siblings), writes nav.js (the sidebar: the classes by area) and search.js (every class, property, function, signal and enum) from QDoc's index file, and copies the script beside the pages. The pages reach the webpage's fonts and wordmarks through ../assets/, so site/api/ works on the public page and on the copy the device serves alike.
