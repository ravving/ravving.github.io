    Translations

    KI18n in the app, keys against display text, the contexts, the glossary, the webpage's catalogs, adding a language, the release review.

    ravving speaks English, Spanish and Japanese. Every text on its screen goes through KI18n, KDE's gettext layer, and the webpage (site/) is translated from catalogs of its own. The docs stay in English.

    Language App catalog Webpage catalog
    Spanish (es) po/es/ravving.po po-site/es/ravving-site.po
    Japanese (ja) po/ja/ravving.po po-site/ja/ravving-site.po

    How it works

    • The domain. Localization (src/backend/localization.cpp) sets the application domain ravving right after the QGuiApplication is made, as the KI18n guide asks. It also adds the build tree's locale/ folder, so a build runs translated before it's installed.
    • The catalogs install to /usr/share/locale/<lang>/LC_MESSAGES/ravving.mo, through CMake's ki18n_install(po). The AppImage's default-app.sh install copies them too.
    • QML. KLocalization::setupLocalizedContext(&engine) (KF 6.8 and later) puts i18n, i18nc, i18np and i18ncp on the root context, so QML calls them bare.
    • SETTINGS · LANGUAGE. SYSTEM (the default) follows the device's own language; English, Español and 日本語 pick one. The choice is kept in the profile settings (ui/language).
    • Live switching. A change sets KLocalizedString::setLanguages, sends QEvent::LanguageChange to the application and calls QQmlEngine::retranslate(). Every binding that calls i18n… runs again, so the screen changes at once.
    • C++ models whose rows carry display text (the video tiers, FILES, the USB page, the audio outputs) catch LanguageChange, as the Qt guide does for plain QObjects, and emit NOTIFY.
    • Numbers and dates. C++ formats them through KI18n (subs(value, 0, 'f', 1)); QML uses Rave.num(value, decimals), the locale of the language picked. Dates use QLocale of the first language KI18n uses.

    Keys stay keys

    Only display text is translated, where it's drawn. Text that's stored, compared, sent or looked up stays English:

    • the machine roles, preset and kit names, scale names and group names;
    • the effect and knob names in data/engines.json;

    • the menu ids, the fifo names and the CUIA names.

    • QML: Rave.kli18nc(context, key) marks a key for extraction and returns it unchanged (the QML side of KI18n's kli18nc, as Qt's QT_TR_NOOP). The helpers translate at draw time: Rave.group, Rave.drumRow, Rave.param, Rave.paramGroup, Rave.effect, Rave.choice, Rave.tuning, Rave.stringInstrument, Rave.inputMode. Menus dispatch by id, never by the text shown.

    • C++: tables of display text are KLazyLocalizedString (kli18nc), turned into text with .toString() when read, so a language change shows at once. A message with values is a KLocalizedString template (ki18nc(…).subs(…)) passed on and finished where it is shown.
    • List models carry a display role beside the key, as Qt's QAbstractListModel examples do: the key for the logic, the display text for the screen.
    • Data. tools/i18n-data.py writes the data files' vocabulary as i18nc calls into the extraction, as KDE's rc.cpp does, under the helpers' contexts. That's the drum rows, the engines' knobs and cards, effects, scales, tunings and groups.

    Contexts and markers

    Every call is i18nc with a context saying what the text is, starting with a KDE UI marker: @action:button, @option:check, @option:radio, @label, @title:window, @title:group, @item:inlistbox, @info, @info:status, @info:placeholder. The context names the music meaning when a word has several ("SONG" the page, "SONG" the PLAY mode). All sound vocabulary shares one context, so a knob name is translated once.

    Names printed on the device stay English in every language: MENU, ALT, MODE, BACK, SELECT, PLAY, STOP, RECORD, X, Y. So do product and machine names (SAMPLE KING, PAD SAMPLER, POLY-6, the engines and kits), MIDI, USB, HDMI, SBC-XQ and LIVE FX. tools/check-ui.py's text-translatable rule finds a display text that skips i18n…; its keep list holds these.

    Lengths

    Spanish runs about a third longer than English. ActionButton and Chip shrink their text to fit, down to 75 % of its size; a text still too long is elided. Look at every page in Spanish after adding text.

    The workflow

    sh tools/i18n-extract.sh              # sources → po/ravving.pot and po-site/ravving-site.pot, merged into every catalog
# translate what it marked: empty or fuzzy entries (Lokalize, Poedit or a text editor)
python3 tools/check-translations.py   # the ctest translations-current
python3 tools/site-i18n.py render     # po-site → site/es/ and site/ja/

    check-translations.py fails when:

    • a template is stale, or a catalog doesn't compile (msgfmt --check);
    • a text is untranslated or fuzzy;
    • a translation drops a placeholder (%1) or a markup tag (<b>, <a>);
    • the rendered pages are older than their catalogs.

    The webpage

    tools/site-i18n.py extract collects the text of site/index.html, site/features.html and the user guide's pages (site/docs/get-ravving.html, machines.html, first-beat.html, as tools/build-site-docs.py renders them) into po-site/ravving-site.pot:

    • every block of text (a heading, a paragraph, a row's words), with its inline <b>, <a> and <br>;
    • the alt, title, aria-label and placeholder attributes;
    • site.js's captions and marks.

    render writes site//index.html, site//features.html, site//docs/ (the guide's pages) and site//site.js. A link to a translated page stays in the language; any other goes to the English one, so the manual and the developer docs stay English. The language switcher in the top bar links the three languages.

    Text sitting loose beside other elements (<h3>Five keys. <span>…</span></h3>) can't become a message: extract warns about it, and the page wraps it (<b>Five keys.</b>). <kbd>, <code> and anything marked translate="no" stay as they are.

    The page's catalogs live in po-site/, not po/: ki18n_install compiles every catalog in po/ into the device's install.

    Adding a language

    1. msginit --no-translator --no-wrap -l <lang> -i po/ravving.pot -o po/<lang>/ravving.po, and the same from po-site/ravving-site.pot into po-site//ravving-site.po.
    2. Translate both, following the glossary above (add a column for the new language).
    3. Add the language to the Languages table in src/backend/localization.cpp, by its own name.
    4. Add its link to the switchers in site/index.html and site/features.html, and their hreflang alternates.
    5. Run the workflow, then look at every page in the new language on the device.

    Every release: review the translations

    Before every release, someone who reads the language reviews what changed in each catalog since the last release: new and changed texts, and the screens they appear on. Run git diff v<last> -- po po-site, take the screenshot tour in each language, and check that ctest -R translations-current passes. A release does not ship with fuzzy or untranslated texts.
