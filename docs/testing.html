Testing on the device

device.sh, the fifo hooks, the suites, the screenshot tour.

Every tool used to drive, hear, measure and watch ravving on a Zynthbox, from the laptop. The pieces are small scripts in tools/; this page is the recipe book that strings them together. For the first-time set-up (SSH, the build loop) see README.md; for what each backend piece does, docs/architecture.md; for the sound and timing checks that were run when a feature was built, docs/debugging.md and docs/quality.md.

The rule for every test: iterate with a local build (tools/device.sh deploy), never the AppImage; the AppImage and its release check (docs/packaging.md) are for minor releases.

The tools

Tool What it does
tools/device.sh deploy rsync the source, build on the device, install, restart, wait until the audio is wired
tools/device.sh cuia NAME… press device keys by CUIA name through the remote-control fifo (SWITCH_NUMBER_5_RELEASED, SWITCH_ARROW_UP_RELEASED, SWITCH_STEP5_PRESSED + _RELEASED, SWITCH_MODE_RELEASED = LIVE, KNOB0_UP…KNOB3_DOWN, SWITCH_ALT_PRESSED / _RELEASED, SWITCH_PLAY_RELEASED, SWITCH_STOP_RELEASED, SWITCH_BACK_RELEASED, SWITCH_SELECT_RELEASED)
(object names) a machine key, studio, ravving, input, take, or a dotted path into an object's properties: pads.kit, bass.sound; any other name is a QML item's objectName (padsModule, samplerModule, padsWaveEditor, samplerWaveEditor): set padsModule modifiersExpanded true, call padsWaveEditor open 16, set ravving currentPage 4, set ravving samplerMachine 1; mouse is the MouseWatcher (get mouse hasMouse). QML items are found in the item tree (a page's items are visual children, not always QObject children), popups in the object tree. A QML function is called through the script engine, so its arguments arrive as plain numbers, booleans or text (call chordsModule moveView 1, call padsWaveEditor open 16); a C++ method gets its arguments converted to the parameter types
tools/device.sh set OBJECT PROPERTY VALUE set a backend property (set pads selectedPad 3); plain setters are not reachable by call, properties are
tools/device.sh get OBJECT PROPERTY read a backend property (get pads muted, get studio playing): ravving logs it, the script reads it back
tools/device.sh call OBJECT METHOD ARGS… call a backend method: a machine by its kits.json key (pads, sampler, drums1, bass, chords, lead), studio, input, take, exporter, music (and music.library), profile, drives (USB sticks: call drives eject /dev/sda1), usb (the USB page: call usb scan, call usb importEntry samples /media/root/EVS/x.wav, call usb exportEntry soundfonts /zynthian/…/x.sf2; usbPopup opens it: call controlCenter run usb), bluetooth (call bluetooth startDiscovery, get bluetooth devices, call bluetooth pair AA:BB:…, call bluetooth useAsOutput AA:BB:… true, call bluetooth sendFile AA:BB:… /path), or a QML item by objectName (window showPlayer true, window showRecorder true, exportPopup open, settingsPopup open, bluetoothPopup open, projectPicker open then projectPicker actionTriggered 4 for IMPORT (the index counts the dividers: OPEN 0, EXPORT 1, NEW 2, TEMPLATES 3, IMPORT 4, SAVE AS NEW 6), playerPage, controlCenter); any Q_INVOKABLE or slot, arguments converted (call pads loadSample 0 /path.wav, call pads setFlag 0 looping true, call pads loadPreset "Boom Bap", call input record, call input record true for a RECORDER take; set input.effects preset OVERDRIVE; get input.tuner frequency; call ravving setLogRules "ravving.cuia.debug=true" turns a log category on while running: each key, who took it and the focus chain), video (set video countdown 0, call video start / stop / toggle, get video state / lastFile / lastInfo, set video quality high) and computer (call computer setup HOST USER PASSWORD 22, check, send /path, forget), files (the FILES browser: get files kinds, call files entries videos, call files presetFile "pattern::bass-presets.json::My Bassline 1"; filesPopup open, filesPopup showKind presets, filesPopup openFolder BASS: the drawer's dialogs open by script only once the MENU drawer has been shown since the start, so press MENU twice first); the journal logs each call
tools/device.sh tap X Y a touch at a screen pixel (the panel is 1280 × 800); a hold is xdotool mousemove X Y mousedown 1; sleep 1; xdotool mouseup 1 over ssh with DISPLAY=:0 XAUTHORITY=/root/.Xauthority
tools/device.sh shot FILE.png a screenshot, copied here (crop with ImageMagick to read details)
tools/device.sh animations every running animation and repeating Timer, with its item, whether it is shown, its QML file and position: what keeps the window drawing (an idle screen should draw nothing)
tools/audio-impact.sh [SECONDS] [idle\|playing\|both] what the screen, polls and watchers cost the sound: frames/s, CPU per thread group, realtime-thread page faults, xruns (docs/quality.md §10); idle presses nothing, so it is safe while someone plays
tools/device.sh gallery [DIR] one screenshot per page
tools/device.sh log [SECONDS] ravving's journal
tools/device.sh bt [ADDR] [SINCE] / bt capture [SECONDS] [FILE] why a Bluetooth device does (not) connect or play, read-only (tools/bt-diagnose.sh: config, endpoints, codecs, the device's journal and a tally of failures), and an HCI trace with btmon while you connect it (docs/debugging.md, docs/bluetooth.md)
tools/device.sh play FILE.mid play a MIDI file into ravving as an external keyboard (tools/midifile.py makes one)
tools/device.sh default … switch between ravving and zynthbox-qml, install, purge, status
tools/meter.py (on the device: tools/device.sh tools copies it to /tmp) pw-jack python3 /tmp/meter.py PORT --seconds 2: RMS, brightness and crest of a JACK port
tools/record.py, tools/analyse.py, tools/repeatcheck.py record ports to numpy, analyse, check periodicity
tools/soundfont.py presets · ranges · render · categorise FILE… look inside an SF2 / SF3 before making it a kits.json sound source (categorise --json proposes the entries, a category from the name and folder: Strings, Organ, Keys, Bass, Guitar, Winds, Voices, Synth, Alien for the drones, Drums, Other; mute fonts left out): its presets (bank:program), the key and velocity ranges of its zones (a velRange 0–0 font is mute everywhere: SynStrings, LaString, MelloString, Organ on the image), and an offline render of one chord through fluidsynth with the level every quarter second
tools/mididump.py PORT SECONDS (on the device, pw-jack python3) what an engine really receives on a JACK MIDI port: notes, controllers, program changes, bends (the clock and ticks with --clock)
tools/profile-taps.sh, tools/qml-profile.sh, tools/boot-timing.sh responsiveness, QML profiling, start-up time (docs/quality.md)
tools/static-analysis.sh clang-tidy / clazy
tools/pads-test.sh the PAD SAMPLER feature suite (below)
tools/sections-test.sh SECTIONS heard: sections picked at random moments while the master records, tools/sections-test.py checks every 8th sounds once and on time, a change only on a bar line, a rest in whole bars (below)
tools/bluetooth-setup.sh [--check] set a device up for Bluetooth (packages, the two drop-ins, services) and check every step (docs/bluetooth.md)
tools/soundfont-check.sh every soundfont kits.json uses, checked on the device: exists, can sound, the preset exists, a chord comes out offline (docs/quality.md §7)
tools/drums-test.sh the DRUMS page suite (60 checks: 55 on the device, 5 timing checks on the laptop from a recording of the lane): a new project starting clean on every page, the grid (toggle, accent, undo / redo, clear, bars, view bar, cursor and STEP entry), the kit (another loaded, reset), the row mix heard (mute, solo, level, accent, the machine's mute and pause), LIVE (a pad heard, hits recorded while playing), presets (save, load, remove), every SOUND EFFECT on and off with its knobs read back and DRIVE / COMPRESSOR / EQ / PAN heard, the kit's MODS, and tools/hits-timing.py (shared with the chords suite): every 8th within 12 ms, accents louder. It works in a project of its own and puts the previous one back
tools/chords-test.sh the CHORDS page suite (54 checks: 50 on the device, 4 timing checks on the laptop): the key and chord sets (names follow ROOT and the set), the CHORDS view (chords, runs, undo / redo, clear), NOTES (toggle, a step's notes, custom voicings), SLOTS (arm, fill, bars, clear, the steps rebuilt), the octave, the sound source (a soundfont, back to TAL), heard (mute, pause, LIVE keys, a hit recorded), presets, every SOUND EFFECT with EQ / PAN / DRIVE heard, and hits-timing.py on two bars of piano stabs (every 8th within 20 ms)
tools/video-test.sh the video recorder suite (docs/video.md): a recording over the fifo while playing, its MP4 (streams, starts, length, frame rate), the ring's dropped frames, the graph's xruns meanwhile, RECORD / STOP by the keys, the TIMER and its cancel, VIDEO off
tools/share-test.sh [FILE] the phone share (SEND… → PHONE · QR CODE) with the laptop as the phone: the newest video (or FILE) offered over the fifo, its link fetched with curl and compared with the device's file (size, md5), a Range request → 206 of the right length, HEAD, a wrong token and the root → 404, the deliveries counted, the help page at /help/ (200 text/html, its CSS, a missing file and ../ → 404, not an attachment, not counted), the library's pages (openBrowse → the index, a kind's page, a DOWNLOAD link as an attachment, a wrong kind and token → 404, closeBrowse → 404), stop → the link 404 while the help page stays; runs on the laptop (it must reach the device's address, as a phone would)
tools/computer-link-test.sh the computer link end to end against the device's own sshd (a throwaway local user as the computer): set-up with the password, the key installed, Downloads found, a wrong password told apart, a file sent, the key removed → refused
tools/video-voice-check.sh the voice-over mix of a video: the transport playing, tools/tone.py's 1 kHz bursts into the tap's mic ports as the voice, the file measured second by second (the music DUCK dB quieter while the tone is on, the tone LIFT dB louder); DUCK=18 LIFT=0 for other settings; the device must be idle
tools/video-sync-check.sh, tools/video-encode-impact.sh, tools/video-mic-check.sh the video sync mechanism alone; the encoder tiers' cost while playing; a recording with the RECORDER's mic heard and measured
tools/export-test.sh the exports and music player suite (below): a project saved, changed and reopened, a short track export (WAV, then FLAC) checked to the sample, its tags and cover, a .ravv bundle and its import, the player's queue, playback, pause, seek and stop
tools/examples/lofi-say-it.sh a whole project built by script (docs/scripting-projects.md): the recipe for making music over the fifo
tools/appimage-test.sh, tools/store-register.py, tools/store-launch.sh the Store AppImage release check (docs/packaging.md)

Environment switches: QT_LOGGING_RULES="ravving.cuia.debug=true" (set with systemctl --user set-environment and a restart) logs every hardware event with whether it was accepted and the focus chain it travelled; ravving.midi.debug=true the MIDI input.

Where to listen

A machine's track after its effects is TrackPassthrough:Channel{track+1}-lane1-dryOutLeft (kits.json gives the track: drums 0–2, bass 3, chords 4, lead 5, SAMPLE KING 6, PAD SAMPLER 7, the input monitor 9); the master is GlobalPlayback:dryOutLeft. Always compare runs (silent, playing, silent again), never read a single number: a track playing a beat is ~0.02–0.2 RMS, silence is 0.0.

The feature suite

sh tools/pads-test.sh runs every PAD SAMPLER backend feature as a check on the device (load, one-shot, NOTE ON, LOOP + latch + stopAll, the pattern on both tracks, erase, halve / double, MUTE, copy, a card value, a take with SMART stop when a signal is present, the samplers' exclusivity, the folders), PASS / FAIL / SKIP per line with the measured level, and exits with the number of failures. Run it after any change to the machine, the wiring, the paths or libzynthbox; it needs the reference audio in the library and a kick sample in the device's sketchpads. Add a check for every new feature.

SECTIONS on the bar line

sh tools/sections-test.sh (from the laptop) builds a test project on the device: DRUMS 1 alone, a bar of 8ths at 100 BPM, section A a kick, B a closed hat, REST with DRUMS 1 resting. It records the master while A and B are picked 24 times at random moments (0.6–2.6 s apart: some land, some are replaced before their bar), then A and REST in turn, and tools/sections-test.py checks the recordings by their onsets (a kick is dark, a hat bright): every 8th once (no gap near 600 ms, none under 200), on time (each onset within 15 ms of one grid fitted through them all), the sound changing only on an onset that begins a bar, the rests whole bars from a bar line. What was open before is opened again (saved first when it had changes). 2026-10-09 on milo: 7/7, 152 eighths, 13 changes all on bar lines, every 8th within 13.3 ms of a 299.997 ms grid. Read the timing against the grid, not gap by gap: the detector reads a kick 2.7 ms early and a hat 3.0 ms late (each ±2.6 ms), so a gap across a change carries both errors (one gap read 22.7 ms off in an earlier run while every onset was within 11 ms of the grid).

The exports suite

sh tools/export-test.sh runs the exports and the music player as checks on the device against whatever project is open (27 checks, all passing on milo with "Lo-fi Say It"): the profile's author fallback, a 2-bar WAV export that starts busy, plays the transport, stops it, lasts exactly 2 bars + 1 s at the project's tempo (to the sample), is 24-bit at the engine's rate, carries its tags (python3-taglib reads them back), its cover PNG and a sidecar that says the start was placed on the audio clock (headFrom: clock); a 1-bar FLAC; a .ravv bundle (project.json, metadata.json, cover.png, the samples; zip integrity checked by Python) imported as a new project with its sample paths rewritten; the library listing the tracks, playNow sounding on the master (meter.py), the position moving, pause, resume, seek, enqueue, stop. It removes its "Export Test" files (exports, the imported project and its samples) at the end.

A track export by hand over the fifo (JSON in one argument; no | inside):

ssh root@milo.local "printf '%s\n' 'call|exporter|exportAudio|{\"title\":\"My Track\",\"artist\":\"Me\",\"format\":\"flac\",\"bars\":8,\"loops\":2,\"tail\":2}' > /tmp/webconf-writes-to-this-fifo"
tools/device.sh get exporter phase      # preparing · recording · cutting · tagging · done
tools/device.sh get exporter lastFile

Projects that still resolve

A project names what it plays instead of holding it: each instrument's sound source and factory sound by name, its MODS knobs as "CARD/KNOB", a drum kit or a sample by path, automation lanes by knob. A change to data/kits.json, data/engines.json or the device's files can leave a saved project pointing at nothing, and it then opens on another sound, silently. Three checks catch it:

  • On the laptop, every change: ctest -R projects runs tools/check-projects.py over data/demos against the repo's kits.json and engines.json (sources, MODS knobs, automation lanes, kit roles, sections and the song).
  • Over the device's saved projects: tools/device.sh projects (-v for every project) runs it on milo against the installed data and files too: kit soundfonts, samples (a take saved before the takes moved to samples/takes/ is found there, as ravving finds it), imported soundfonts, the TAL factory sounds. Run it after a data change, before a release.
  • In ravving, each time a project opens: the machines note what they could not resolve as they restore it (ProjectCheck, Machine::checkSaved(): nothing is read twice, nothing runs after), and the issues centre shows one warning listing it ("5AM: 2 of what it plays is missing"), cleared by the next project that resolves.

Recipes

A sampler pad from a script. Load, play, loop, latch, stop:

sh tools/device.sh call pads loadSample 0 /zynthian/zynthian-my-data/ravving/samples/refs/movie-intro-16s.wav
sh tools/device.sh call pads audition 0            # one pass
sh tools/device.sh call pads setFlag 0 looping true
sh tools/device.sh call pads setLatched 0 true     # held looping, as a long press does
sh tools/device.sh call pads stopAll               # what STOP does

A pattern on the pads. Fill pads 1–4 with a kick, snare, hat and clap from the device's library (find /zynthian/zynthian-my-data/samples -iname "*kick*.wav" | head -1), then call pads loadPreset "Boom Bap", cuia SWITCH_PLAY_RELEASED, meter the lane, cuia SWITCH_STOP_RELEASED. The step keys write the selected pad's row with LIVE off and play the pads with LIVE on (SWITCH_MODE_RELEASED toggles it; a step key held past half a second latches its pad).

A take into a pad. With something on the input jack (INPUT sets MIC / GUITAR / LINE): call pads setSelectedPad 2, then call input record; with SMART on (studio.input.autoStop, default on) the take ends by itself half a second after the sound stops, else call input stop. The processed take lands on the pad trimmed to its last burst; the journal shows takeReady. Without a signal the take never auto-stops: that is the guard against stopping before anything was played.

The hardware walk. Switch the trace on, then cuia SWITCH_ARROW_UP_RELEASED step by step and read which item accepted each key; ALT + ▲ must land on the header from anywhere. Key 5 opens page 5 and, pressed again, toggles between SAMPLE KING and the PAD SAMPLER; the choice survives restarts, so check the nameplate in a screenshot before sending taps at a panel (a hold on the wrong one writes a step).

Reference audio for sampling tests lives in the library: /zynthian/zynthian-my-data/ravving/samples/refs/ (movie.wav and movie-intro-16s.wav from the user's "04 - Movie", nina-free*.wav); the originals are in ~/Coding/refs/audio/ on the laptop.

The audio graph

tools/device.sh graph all -s 60 checks the PipeWire / JACK graph ravving runs in (rates and periods against the driver's, linked nodes that are not running, the audio threads' priorities, xruns over a minute, the ravving links). docs/routing.md has the map of what ravving wires, the tools (pw-top, pw-dump, pw-dot, jack_iodelay…) and the measurements.

tools/issues-test.sh checks the issues center end to end (reports over the fifo, order, dismiss, clear, the drawer card and the dialog).
