    Testing on the device

    device.sh, the fifo hooks, the suites, Bluetooth and live recording tests, building a project by script.

    The tools that drive, hear, measure and watch ravving on a Zynthbox, from the laptop. The pieces are small scripts in tools/; this page is the recipe book that strings them together. For the build loop see building.md; for what each backend piece does, architecture.md; for the device recipes and the code checks, debugging.md and quality.md.

    The rule for every test: iterate with a local build (tools/device.sh deploy), never the AppImage; the AppImage and its release check (packaging.md) are for minor releases.

    The tools

    Like zynthbox-qml, ravving reads CUIA commands from webconf's fifo (echo cuia/SWITCH_PLAY_RELEASED > /tmp/webconf-writes-to-this-fifo), and the call, get and set lines below; tools/device.sh writes them over ssh.

    Tool What it does
    tools/device.sh deploy rsync the source, build on the device, install, restart, wait until the audio is wired
    tools/device.sh cuia NAME… press device keys by CUIA name through the remote-control fifo (SWITCH_NUMBER_5_RELEASED, SWITCH_ARROW_UP_RELEASED, SWITCH_STEP5_PRESSED + _RELEASED, SWITCH_MODE_RELEASED = LIVE, KNOB0_UP…KNOB3_DOWN, SWITCH_ALT_PRESSED / _RELEASED, SWITCH_PLAY_RELEASED, SWITCH_STOP_RELEASED, SWITCH_BACK_RELEASED, SWITCH_SELECT_RELEASED)
    (object names) a machine key, studio, ravving, input, take, or a dotted path into an object's properties: pads.kit, bass.sound; any other name is a QML item's objectName (padsModule, samplerModule, padsWaveEditor, samplerWaveEditor): set padsModule modifiersExpanded true, call padsWaveEditor open 16, set ravving currentPage 4, set ravving samplerMachine 1; mouse is the MouseWatcher (get mouse hasMouse). QML items are found in the item tree (a page's items are visual children, not always QObject children), popups in the object tree. A QML function is called through the script engine, so its arguments arrive as plain numbers, booleans or text (call chordsModule moveView 1, call padsWaveEditor open 16); a C++ method gets its arguments converted to the parameter types
    tools/device.sh set OBJECT PROPERTY VALUE set a backend property (set pads selectedPad 3); plain setters are not reachable by call, properties are
    tools/device.sh get OBJECT PROPERTY read a backend property (get pads muted, get studio playing): ravving logs it, the script reads it back
    tools/device.sh call OBJECT METHOD ARGS… call a backend method: a machine by its kits.json key (pads, sampler, drums1, bass, chords, lead), studio, input, take, exporter, music (and music.library), profile, drives (USB sticks: call drives eject /dev/sda1), usb (the USB page: call usb scan, call usb importEntry samples /media/root/EVS/x.wav, call usb exportEntry soundfonts /zynthian/…/x.sf2; usbPopup opens it: call controlCenter run usb), bluetooth (call bluetooth startDiscovery, get bluetooth devices, call bluetooth pair AA:BB:…, call bluetooth useAsOutput AA:BB:… true, call bluetooth sendFile AA:BB:… /path), or a QML item by objectName (window showPlayer true, window showRecorder true, exportPopup open, settingsPopup open, bluetoothPopup open, projectPicker open then projectPicker actionTriggered 4 for IMPORT (the index counts the dividers: NEW 0, TEMPLATES 1, IMPORT 2, SAVE AS NEW 4, EXPORT 6), playerPage, controlCenter); any Q_INVOKABLE or slot, arguments converted (call pads loadSample 0 /path.wav, call pads setFlag 0 looping true, call pads loadPreset "Boom Bap", call input record, call input record true for a RECORDER take; set input.effects preset OVERDRIVE; get input.tuner frequency; call ravving setLogRules "ravving.cuia.debug=true" turns a log category on while running: each key, who took it and the focus chain), video (set video countdown 0, call video start / stop / toggle, get video state / lastFile / lastInfo, set video quality high) and computer (call computer setup HOST USER PASSWORD 22, check, send /path, forget), files (the FILES browser: get files kinds, call files entries videos, call files presetFile "pattern::bass-presets.json::My Bassline 1"; filesPopup open, filesPopup showKind presets, filesPopup openFolder BASS: the drawer's dialogs open by script only once the MENU drawer has been shown since the start, so press MENU twice first); the journal logs each call
    tools/device.sh tap X Y a touch at a screen pixel (the panel is 1280 × 800); a hold is xdotool mousemove X Y mousedown 1; sleep 1; xdotool mouseup 1 over ssh with DISPLAY=:0 XAUTHORITY=/root/.Xauthority
    tools/device.sh shot FILE.png a screenshot, copied here (crop with ImageMagick to read details)
    tools/device.sh animations every running animation and repeating Timer, with its item, whether it is shown, its QML file and position: what keeps the window drawing (an idle screen should draw nothing)
    tools/audio-impact.sh [SECONDS] [idle\|playing\|both] what the screen, polls and watchers cost the sound: frames/s, CPU per thread group, realtime-thread page faults, xruns (quality.md); idle presses nothing, so it is safe while someone plays
    tools/device.sh gallery [DIR] one screenshot per page
    tools/device.sh log [SECONDS] ravving's journal
    tools/device.sh bt [ADDR] [SINCE] / bt capture [SECONDS] [FILE] why a Bluetooth device does (not) connect or play, read-only (tools/bt-diagnose.sh: config, endpoints, codecs, the device's journal and a tally of failures), and an HCI trace with btmon while you connect it (debugging.md)
    tools/device.sh play FILE.mid play a MIDI file into ravving as an external keyboard (tools/midifile.py makes one)
    tools/device.sh default … switch between ravving and zynthbox-qml, install, purge, status
    tools/meter.py (on the device: tools/device.sh tools copies it to /tmp) pw-jack python3 /tmp/meter.py PORT --seconds 2: RMS, brightness and crest of a JACK port
    tools/record.py, tools/analyse.py, tools/repeatcheck.py record ports to numpy, analyse, check periodicity
    tools/soundfont.py presets · ranges · render · categorise FILE… look inside an SF2 / SF3 before making it a kits.json sound source (categorise --json proposes the entries, a category from the name and folder: Strings, Organ, Keys, Bass, Guitar, Winds, Voices, Synth, Alien for the drones, Drums, Other; mute fonts left out): its presets (bank:program), the key and velocity ranges of its zones (a velRange 0–0 font is mute everywhere: SynStrings, LaString, MelloString, Organ on the image), and an offline render of one chord through fluidsynth with the level every quarter second
    tools/mididump.py PORT SECONDS (on the device, pw-jack python3) what an engine really receives on a JACK MIDI port: notes, controllers, program changes, bends (the clock and ticks with --clock)
    tools/profile-taps.sh, tools/qml-profile.sh, tools/boot-timing.sh responsiveness, QML profiling, start-up time (quality.md)
    tools/static-analysis.sh clang-tidy / clazy
    tools/pads-test.sh the PAD SAMPLER feature suite (below)
    tools/sections-test.sh SECTIONS heard: sections picked at random moments while the master records, tools/sections-test.py checks every 8th sounds once and on time, a change only on a bar line, a rest in whole bars (below)
    tools/bluetooth-setup.sh [--check] set a device up for Bluetooth (packages, the two drop-ins, services) and check every step (packaging.md)
    tools/soundfont-check.sh every soundfont kits.json uses, checked on the device: exists, can sound, the preset exists, a chord comes out offline (quality.md)
    tools/drums-test.sh the DRUMS page suite (60 checks: 55 on the device, 5 timing checks on the laptop from a recording of the lane): a new project starting clean on every page, the grid (toggle, accent, undo / redo, clear, bars, view bar, cursor and STEP entry), the kit (another loaded, reset), the row mix heard (mute, solo, level, accent, the machine's mute and pause), LIVE (a pad heard, hits recorded while playing), presets (save, load, remove), every SOUND EFFECT on and off with its knobs read back and DRIVE / COMPRESSOR / EQ / PAN heard, the kit's MODS, and tools/hits-timing.py (shared with the chords suite): every 8th within 12 ms, accents louder. It works in a project of its own and puts the previous one back
    tools/chords-test.sh the CHORDS page suite (54 checks: 50 on the device, 4 timing checks on the laptop): the key and chord sets (names follow ROOT and the set), the CHORDS view (chords, runs, undo / redo, clear), NOTES (toggle, a step's notes, custom voicings), SLOTS (arm, fill, bars, clear, the steps rebuilt), the octave, the sound source (a soundfont, back to TAL), heard (mute, pause, LIVE keys, a hit recorded), presets, every SOUND EFFECT with EQ / PAN / DRIVE heard, and hits-timing.py on two bars of piano stabs (every 8th within 20 ms)
    tools/video-test.sh the video recorder suite (architecture.md, "Live recordings"): a recording over the fifo while playing, its MP4 (streams, starts, length, frame rate), the ring's dropped frames, the graph's xruns meanwhile, RECORD / STOP by the keys, the TIMER and its cancel, VIDEO off
    tools/share-test.sh [FILE] the phone share (SEND… → PHONE · QR CODE) with the laptop as the phone: the newest video (or FILE) offered over the fifo, its link fetched with curl and compared with the device's file (size, md5), a Range request → 206 of the right length, HEAD, a wrong token and the root → 404, the deliveries counted, the help page at /help/ (200 text/html, its CSS, a missing file and ../ → 404, not an attachment, not counted), the library's pages (openBrowse → the index, a kind's page, a DOWNLOAD link as an attachment, a wrong kind and token → 404, closeBrowse → 404), stop → the link 404 while the help page stays; runs on the laptop (it must reach the device's address, as a phone would)
    tools/computer-link-test.sh the computer link end to end against the device's own sshd (a throwaway local user as the computer): set-up with the password, the key installed, Downloads found, a wrong password told apart, a file sent, the key removed → refused
    tools/video-voice-check.sh the voice-over mix of a video: the transport playing, tools/tone.py's 1 kHz bursts into the tap's mic ports as the voice, the file measured second by second (the music DUCK dB quieter while the tone is on, the tone LIFT dB louder); DUCK=18 LIFT=0 for other settings; the device must be idle
    tools/video-sync-check.sh, tools/video-encode-impact.sh, tools/video-mic-check.sh the video sync mechanism alone; the encoder tiers' cost while playing; a recording with the RECORDER's mic heard and measured
    tools/export-test.sh the exports and music player suite (below): a project saved, changed and reopened, a short track export (WAV, then FLAC) checked to the sample, its tags and cover, a .ravv bundle and its import, the player's queue, playback, pause, seek and stop
    tools/examples/lofi-say-it.sh a whole project built by script ("Building a project by script", below): the recipe for making music over the fifo
    tools/appimage-test.sh, tools/store-register.py, tools/store-launch.sh the Store AppImage release check (packaging.md)

    Environment switches: QT_LOGGING_RULES="ravving.cuia.debug=true" (set with systemctl --user set-environment and a restart) logs every hardware event with whether it was accepted and the focus chain it travelled; ravving.midi.debug=true the MIDI input.

    Where to listen

    A machine's track after its effects is TrackPassthrough:Channel{track+1}-lane1-dryOutLeft (kits.json gives the track: drums 0–2, bass 3, chords 4, lead 5, SAMPLE KING 6, PAD SAMPLER 7, the input monitor 9); the master is GlobalPlayback:dryOutLeft. Always compare runs (silent, playing, silent again), never read a single number: a track playing a beat is ~0.02–0.2 RMS, silence is 0.0.

    The feature suite

    sh tools/pads-test.sh runs every PAD SAMPLER backend feature as a check on the device (load, one-shot, NOTE ON, LOOP + latch + stopAll, the pattern on both tracks, erase, halve / double, MUTE, copy, a card value, a take with SMART stop when a signal is present, the samplers' exclusivity, the folders), PASS / FAIL / SKIP per line with the measured level, and exits with the number of failures. Run it after any change to the machine, the wiring, the paths or libzynthbox; it needs the reference audio in the library and a kick sample in the device's sketchpads. Add a check for every new feature.

    SECTIONS on the bar line

    sh tools/sections-test.sh (from the laptop) builds a test project on the device: DRUMS 1 alone, a bar of 8ths at 100 BPM, section A a kick, B a closed hat, REST with DRUMS 1 resting. It records the master while A and B are picked 24 times at random moments (0.6–2.6 s apart: some land, some are replaced before their bar), then A and REST in turn, and tools/sections-test.py checks the recordings by their onsets (a kick is dark, a hat bright): every 8th once (no gap near 600 ms, none under 200), on time (each onset within 15 ms of one grid fitted through them all), the sound changing only on an onset that begins a bar, the rests whole bars from a bar line. What was open before is opened again (saved first when it had changes). Read the timing against the grid, not gap by gap: the detector reads a kick 2.7 ms early and a hat 3.0 ms late (each ±2.6 ms), so a gap across a change carries both errors.

    The exports suite

    sh tools/export-test.sh runs the exports and the music player as checks on the device against whatever project is open (27 checks): the profile's author fallback, a 2-bar WAV export that starts busy, plays the transport, stops it, lasts exactly 2 bars + 1 s at the project's tempo (to the sample), is 24-bit at the engine's rate, carries its tags (python3-taglib reads them back), its cover PNG and a sidecar that says the start was placed on the audio clock (headFrom: clock); a 1-bar FLAC; a .ravv bundle (project.json, metadata.json, cover.png, the samples; zip integrity checked by Python) imported as a new project with its sample paths rewritten; the library listing the tracks, playNow sounding on the master (meter.py), the position moving, pause, resume, seek, enqueue, stop. It removes its "Export Test" files (exports, the imported project and its samples) at the end.

    A track export by hand over the fifo (JSON in one argument; no | inside):

    ssh root@milo.local "printf '%s\n' 'call|exporter|exportAudio|{\"title\":\"My Track\",\"artist\":\"Me\",\"format\":\"flac\",\"bars\":8,\"loops\":2,\"tail\":2}' > /tmp/webconf-writes-to-this-fifo"
tools/device.sh get exporter phase      # preparing · recording · cutting · tagging · done
tools/device.sh get exporter lastFile

    Projects that still resolve

    A project names what it plays instead of holding it: each instrument's sound source and factory sound by name, its MODS knobs as "CARD/KNOB", a drum kit or a sample by path, automation lanes by knob. A change to data/kits.json, data/engines.json or the device's files can leave a saved project pointing at nothing, and it then opens on another sound, silently. Three checks catch it:

    • On the laptop, every change of text: sh tools/i18n-extract.sh, translate what it marks, then ctest -R translations-current (tools/check-translations.py: templates current, catalogs compile, nothing untranslated or fuzzy, placeholders and markup kept, the translated pages rendered). To test a language on the device: device.sh set localization language es (ja, en, or empty for the system's), then run the page suites in it: a suite that reads a display text instead of a key fails there.
    • On the laptop, every change: ctest -R projects runs tools/check-projects.py over data/demos against the repo's kits.json and engines.json (sources, MODS knobs, automation lanes, kit roles, sections and the song).
    • Over the device's saved projects: tools/device.sh projects (-v for every project) runs it on the device against the installed data and files too: kit soundfonts, samples (an older take outside samples/takes/ is found there too, as ravving finds it), imported soundfonts, the TAL factory sounds. Run it after a data change, before a release.
    • In ravving, each time a project opens: the machines note what they could not resolve as they restore it (ProjectCheck, Machine::checkSaved(): nothing is read twice, nothing runs after), and the issues centre shows one warning listing it ("5AM: 2 of what it plays is missing"), cleared by the next project that resolves.

    Recipes

    A sampler pad from a script. Load, play, loop, latch, stop:

    sh tools/device.sh call pads loadSample 0 /zynthian/zynthian-my-data/ravving/samples/refs/movie-intro-16s.wav
sh tools/device.sh call pads audition 0            # one pass
sh tools/device.sh call pads setFlag 0 looping true
sh tools/device.sh call pads setLatched 0 true     # held looping, as a long press does
sh tools/device.sh call pads stopAll               # what STOP does

    A pattern on the pads. Fill pads 1–4 with a kick, snare, hat and clap from the device's library (find /zynthian/zynthian-my-data/samples -iname "*kick*.wav" | head -1), then call pads loadPreset "Boom Bap", cuia SWITCH_PLAY_RELEASED, meter the lane, cuia SWITCH_STOP_RELEASED. The step keys write the selected pad's row with LIVE off and play the pads with LIVE on (SWITCH_MODE_RELEASED toggles it; a step key held past half a second latches its pad).

    A take into a pad. With something on the input jack (INPUT sets MIC / GUITAR / LINE): call pads setSelectedPad 2, then call input record; with SMART on (studio.input.autoStop, default on) the take ends by itself half a second after the sound stops, else call input stop. The processed take lands on the pad trimmed to its last burst; the journal shows takeReady. Without a signal the take never auto-stops: that is the guard against stopping before anything was played.

    The hardware walk. Switch the trace on, then cuia SWITCH_ARROW_UP_RELEASED step by step and read which item accepted each key; ALT + ▲ must land on the header from anywhere. Key 5 opens page 5 and, pressed again, toggles between SAMPLE KING and the PAD SAMPLER; the choice survives restarts, so check the nameplate in a screenshot before sending taps at a panel (a hold on the wrong one writes a step).

    Reference audio for sampling tests lives in the library's samples/refs/ folder (/zynthian/zynthian-my-data/ravving/samples/refs/).

    The audio graph

    tools/device.sh graph all -s 60 checks the PipeWire / JACK graph ravving runs in (rates and periods against the driver's, linked nodes that are not running, the audio threads' priorities, xruns over a minute, the ravving links). routing.md has the map of what ravving wires and the tools (pw-top, pw-dump, pw-dot, jack_iodelay…).

    tools/issues-test.sh checks the issues center end to end (reports over the fifo, order, dismiss, clear, the drawer card and the dialog).

    Bluetooth

    The basic checks: sh tools/bluetooth-setup.sh --check. With a device at hand, over the fifo:

    tools/device.sh call bluetooth startDiscovery; sleep 10; tools/device.sh get bluetooth devices
tools/device.sh call bluetooth pair 84:D3:52:35:80:99        # a speaker pairs without a prompt
tools/device.sh get bluetooth pairing                        # a phone: {kind confirm, passkey} → answerPairing true
tools/device.sh call bluetooth useAsOutput 84:D3:52:35:80:99 true
tools/device.sh cuia SWITCH_PLAY_RELEASED                    # heard on the speaker
tools/device.sh call bluetooth sendFile AA:BB:CC:DD:EE:FF "/zynthian/zynthian-my-data/ravving/exports/Lo-fi Say It.wav"

    What to measure:

    Metric How, on the device
    signal (RSSI, dBm: −30 excellent, −67…−70 good, below −80 drops) bluetoothctl info ADDR (RSSI while scanning), hcitool rssi ADDR once connected
    link quality / packet loss hcitool lq ADDR (255 = best); btmon -w /tmp/bt.snoop during playback and count retransmissions
    A2DP codec and latency pw-cli info <bluez sink id> (api.bluez5.codec: SBC by default, aptX / LDAC when both sides have it); pw-top for the sink node's quantum and the graph's (the studio stays at 256 / 48000; the Bluetooth node runs its own)
    OBEX throughput transfer.transferred over time (get bluetooth transfer)
    what BlueZ sees btmon (HCI trace), busctl --system tree org.bluez, journalctl -u bluetooth
    what WirePlumber does journalctl --user -u wireplumber, with systemctl --user set-environment WIREPLUMBER_DEBUG=3 and a restart for the monitor's own lines

    Building a project by script

    Everything a finger does on the device, a script can do through the remote-control fifo: load samples, write patterns, pick sounds, set the key and the tempo, save the result as a project. tools/examples/five-am/ (the 5AM demo: sections and the song by script, build.py writing the lines, run.sh sending them) and tools/examples/lofi-say-it.sh (a lo-fi hip hop project built on the changes of "Say It (Over and Over Again)") are complete ones; copy one for the next. A loop in the shell that reads a file line by line and calls tools/device.sh loses all but the first line (the ssh inside reads the loop's stdin): send the lines from one script on the device (run.sh) or use ssh -n.

    The loop

    FIFO=/tmp/webconf-writes-to-this-fifo
send() { timeout 2 sh -c "echo \"$1\" > $FIFO"; sleep 0.2; }
call() { local line="call"; for a in "$@"; do line="$line|$a"; done; send "$line"; }
setp() { send "set|$1|$2|$3"; }
get()  { send "get|$1|$2"; journalctl --user -u ravving --since '-5s' --no-pager | grep 'fifo get' | tail -1 | sed 's/.*= //'; }

    A script runs on the device (copy it there, as the example does with itself); every call is one line on the fifo and takes about a fifth of a second, so a full project is a few hundred lines and a couple of minutes. tools/device.sh call|set|get do the same one at a time from the laptop.

    The recipe, in order

    Step Calls
    keep what is there, start clean get studio.projects dirty, call studio.projects saveAs NAME; call studio.projects newProject
    tempo, swing, key set studio bpm 74, set studio swing 0.58 (and set studio swingEighths true for jazz: the off-beat 8ths swing, not the 16ths; the header's SWING 8 / 16, tapped), call header setKey ROOT SCALE (root 0–11 from C, scale an index into Rave.scales: 0 natural minor, 1 major, 2 Dorian…). NEW resets the key to C minor: set it before writing anything in a key
    drums call drumsN clear, call drumsN toggleStep ROW STEP, toggleAccent STEP; rows by get drumsN rows; call drumsN saveAsPreset keeps the beat as "My Beat N"
    chords set chords bars 8 (the most a pattern holds), set chords viewBar B, then per step call chords setStepNotes STEP "48,52,55,58" (MIDI notes; a note outside the key makes the voicing chromatic). A run of the same voicing on consecutive steps is one held chord; an empty step ends it. Diatonic shortcuts: setChord STEP DEGREE, or SLOTS: assignSlot SLOT DEGREE + cycleSlotBars SLOT. saveAsPreset keeps a chart as "My Progression N" (a longer form = several presets to switch between)
    bass, lead set bass bars 8, set bass viewBar B, call bass setNote STEP NOTE (MIDI; C2 = 36 for the bass, C4 = 60 for the lead, see kits.json baseNote), setNoteLength STEP STEPS (a note lasts one step unless set: a half note is 8, up to 64, into the next bars), toggleAccent STEP, toggleSlide STEP; any note is accepted, in the key or not, and a preset keeps it exactly (the chart's ALTER and HOLD lanes)
    drum kits call drums1 loadKit PATH: a kit file, or a preset inside a soundfont with chosen rows (…/FluidR3Mono_GM.sf3#128:32?CYMBAL=51&HAT=44, the Jazz kit with its ride and hi-hat foot; engines.md); call drumsN setRowLevel ROW 0..1
    sounds call bass chooseSoundSource Upright (names from get bass soundSources), call chords loadSoundPreset NAME for TAL's factory sounds, call bass.sound setValue CARD KNOB 0..1 for the synth's own SOUND MODIFIERS
    pads call pads clearPad N, call pads loadSample N PATH [start length], call pads chopRegions N COUNT FIRSTPAD, set pads selectedPad N + call pads setValue MIX VOLUME 0.95, set pads bars 8, set pads viewBar B + toggleStep PAD STEP; a long one-shot (a 16 s intro) needs a loop long enough not to retrigger it: 8 bars at 74 BPM is 26 s
    SAMPLE KING call sampler loadSample SLOT PATH; set ravving samplerMachine 1 puts the pads on key 5
    save call studio.projects saveAs NAME (a name typed in the dialog would do the same); get studio.projects current to check
    sections and the song the section on screen is what the calls above edit; call studio.sections rename s1 DROP, duplicate s1 (a copy, placed after the section ON SCREEN, which it becomes), setBars ID 1–8, set MACHINE paused true (it rests in this section), move FROM TO (the list), removeFromSong 0 / appendToSong ID / setRepeats INDEX N (the song), set studio.sections mode 1 (SONG), pick ID (the one on screen when saved)
