    Using ravving / README.md

    The manual

    The five pages and what plays on them, the shortcuts, sound sources, presets, templates, sections and the song, exports, files, USB sticks, Bluetooth, the RECORDER, the issues center.

    A groovebox app for the Zynthbox, modelled on easyrave.com's page. It replaces zynthbox-qml on the device and starts the same way, but it is a separate program: a C++ Qt 6 app on top of libzynthbox, with no Python.

    Each of the five left-column number keys opens a page:

    Key Page Machines What plays (the nameplate shows it)
    1 Drums (press 1 again to cycle) DRUMS 1 · 2 · 3 FluidSynth with a drum kit each: Roland TR909, Roland TR808 and LINN9000 to start, any kit from the device's SFZ Drum Machines folder from the nameplate
    2 Chords CHORDS TAL NoiseMaker (jalv) with its factory sounds, or a soundfont instrument (Rhodes, vibes, organ, strings…)
    3 Bass BASS DISTRHO Nekobi (jalv), or a soundfont bass (upright, acoustic, finger, fretless, synth)
    4 Lead LEAD Calf Monosynth (jalv), or a soundfont instrument (Rhodes, vibes, guitar, sax, flute…)
    5 Sampler (press 5 again to switch) SAMPLE KING · PAD SAMPLER libzynthbox's SamplerSynth: four banks of eight slots, or sixteen MPC-style pads on the step keys with takes, pad FX, 16 levels and a shared wave editor

    All five share the top bar: key and scale, transport, tempo and swing, live FX, the instruments strip and master; every machine has a mix strip, SOUND MODIFIERS, its pattern editor and a SOUND EFFECTS chain; a song is made of SECTIONS that change on the bar line, and the whole session lives in projects.

    Status: every page plays and is saved. Each machine runs on libzynthbox (patterns, SyncTimer, the mixer chain, the sampler) with its engine started and wired by ravving; a project keeps patterns, sounds, effects, samples and the key, tempo and mix. See docs/architecture.md for the pieces, docs/engines.md for the engines and docs/mpc-sampler-plan.md for the PAD SAMPLER.

    Build and run on the device

    The build folders, the build options and how long a build takes are in docs/building.md: the development build (build/) compiles the QML as bytecode with precompiled Qt headers (a clean build 426 s → 190 s), the AppImage's (build-release/) compiles it fully; what the device must have is in docs/packaging.md, "What the device needs". The CMake project is split by target ("Project layout" there): the top-level CMakeLists.txt holds the project, its options, dependencies and install rules; src/backend/CMakeLists.txt the ravving_backend library; src/CMakeLists.txt the ravving app with its Ravving QML module (the QML stays in qml/); setup/ and tests/ their own programs.

    What ravving is made of, all taken from the device (nothing is bundled, by the AppImage either): ravving runs on the Zynthbox QtQuick Controls style (qml-style-zynthbox, picked by name in main.cpp, so there is no build-time check: a missing style shows the Basic look and unthemed controls), and that style imports io.zynthbox.ui (ZUI, from qml-module-zynthbox: Button, CheckBox, Switch, Menu and TextField read their theme from it) and the KDE Frameworks it draws with (Kirigami, KSvg, Plasma). The audio engine comes from libzynthbox (io.zynthbox.components) and zyncoder, both loaded at run time. So the order is: libzynthbox + zyncoder, qml-module-zynthbox, qml-style-zynthbox, then ravving; on a stock Zynthbox they are the installed libzynthbox, qml-module-zynthbox and qml-style-zynthbox packages, and a rebuilt module or style must be installed before ravving is tried. The music player plays through Qt Multimedia (qt6-multimedia-dev to build; libqt6multimedia6 with its FFmpeg plugin at run time, both on the image; its sound goes out through PulseAudio, so ravving's service wants pipewire-pulse.service, which a Zynthbox has but leaves off; measured on milo with pw-top, the service and the player's stream leave the graph at its 256-frame, 48 kHz quantum with no new xruns, the player's own stream running adapted at 1680 frames), and the exports use TagLib (libtag1-dev), zlib and libsndfile with its FLAC, Vorbis and LAME encoders.

    The sound itself comes from programs and data the Zynthbox image ships, started and wired by ravving at run time and bundled by nothing: jalv (the LV2 host) with the LV2 plugins the machines and effects name by URI in data/kits.json and src/backend/ (TAL NoiseMaker, DISTRHO Nekobi, Calf Monosynth, Calf Crusher and Phaser, Dragonfly Room Reverb, TAP Echo; tools/lv2probe.sh checks a URI on the device), FluidSynth 2 for the drum kits and the soundfont sound sources, the soundfonts under /zynthian/zynthian-data/soundfonts (the SFZ Drum Machines kits, SF2 Instruments with FluidR3Mono_GM.sf3 and ACBass.sf3), and PipeWire's JACK (pw-jack) with Zynthbox's MIDI routing (ZLRouter, a2j). A machine whose plugin or soundfont is missing starts silent and says so in the journal; docs/engines.md has what each engine does and expects.

    Build dependencies

    On the device (Debian 13 arm64, as a Zynthbox image is) the build needs, by Debian name:

    For Packages
    the toolchain cmake, ninja-build, g++, pkg-config
    Qt 6 (Core, Gui, Qml, Quick, QuickControls2, Concurrent, Network, DBus, Multimedia) qt6-base-dev, qt6-declarative-dev, qt6-multimedia-dev
    Bluetooth (KDE's BluezQt over BlueZ's D-Bus API) libkf6bluezqt-dev
    the audio processors and the graph probe (JACK's API; PipeWire's library at run time) libjack-jackd2-dev
    exports: the audio files, their tags, the .ravv bundles libsndfile1-dev, libtag-dev (TagLib 2; libtag1-dev on older images), zlib1g-dev
    the tools (tools/*.py) and syncing a checkout python3, rsync

    Everything else ravving needs it finds at run time on a stock Zynthbox: libzynthbox and zyncoder, qml-module-zynthbox and qml-style-zynthbox with the KDE Frameworks they draw with (Kirigami, KSvg, Plasma), libqt6multimedia6 with its FFmpeg plugin, PipeWire with pipewire-jack (pw-jack), pipewire-bin (pw-loopback, pw-link, pw-dump, pw-top) and pipewire-pulse (left off by the image; ravving's service wants it), udisks2 and util-linux (USB sticks: udisksctl, lsblk), jalv with the LV2 plugins and FluidSynth with the soundfonts named below. Bluetooth needs three packages the image lacks, bluez-obexd, libspa-0.2-bluetooth and libkf6bluezqt6, plus two drop-ins ravving installs: tools/bluetooth-setup.sh does all of it (docs/bluetooth.md).

    tools/device.sh deploy                 # from the laptop: sync, build, install, restart, wait
# or by hand (rsync without -a: older laptop mtimes would make ninja skip changed files)
rsync -rlp --checksum --exclude build --exclude .git ./ root@milo.local:/root/ravving/
ssh root@milo.local
cd /root/ravving
cmake -S . -B build -G Ninja -DCMAKE_INSTALL_PREFIX=/usr
cmake --build build && cmake --install build
systemctl --user daemon-reload
systemctl --user start ravving        # try it once: stops zynthbox-qml (the services conflict)
systemctl --user start zynthbox-qml   # and back

    To make ravving the device's UI (it starts at boot, and zynthbox-qml is masked so nothing brings it back), and to return to stock Zynthbox with nothing of ravving left in systemd:

    /usr/share/ravving/default-app.sh ravving
/usr/share/ravving/default-app.sh zynthbox           # add --purge to uninstall ravving too
/usr/share/ravving/default-app.sh status

    From the laptop, tools/device.sh default ravving|zynthbox|status does the same. default-app.sh run ravving|zynthbox switches for the session only (the boot default stays), which is what ravving's own menu offers under POWER → ZYNTHBOX.

    Sending to a phone

    Every SEND… button (the FILES browser, VIDEO SAVED, the music player's tracks, the presets dialogs, the sound picker) has a third destination beside the USB sticks and the computer: PHONE · QR CODE. It opens a dialog with a QR code of a link to the file, served by ravving itself (FileShare, a one-file HTTP server on port 8098 or the next free one, at a path of 128 random bits); point the phone's camera app at the screen, open the link it shows, and Safari or Chrome saves the file to the phone's Downloads (Files on an iPhone). The phone must be on the same Wi-Fi as the device (the link is the device's Wi-Fi address; the dialog says when the device is on no network); no pairing, no app and no account are needed, which makes it the way to an iPhone (Bluetooth's file push does not exist there). The link lives while the dialog is open, 15 minutes at most; closing it stops the server. One file at a time: given several, the first one goes and the dialog says so. The dialog shows the link in words too (to type it), and WAITING FOR THE PHONE / SENDING n % / DOWNLOADED ✓ as it goes; a toast says when the whole file has reached the phone. tools/share-test.sh checks it from the laptop (docs/testing.md); over the fifo: call share offer /path/file, get share url, get share status, call share stop.

    The same server carries the ravving page (site/, the instructions, the features and every hardware shortcut): SETTINGS → HELP → OPEN shows its address as a QR code (get share helpUrl, http://<device>:8098/help/), since the device has no browser of its own; a phone's camera opens it, a laptop types it. The site is installed beside the data (share/ravving/site) and served while ravving runs, from any folder under it, nothing above. The same page is public at https://ravving.github.io/ (the dialog's QR code is that one, reachable from anywhere; the device's own address is under it for a Wi-Fi without internet): tools/publish-site.sh pushes this repository's site/ into the ravving/ravving.github.io repository, whose workflow deploys it (docs/building.md).

    Distribution: the Store AppImage

    For everyone else ravving comes from the Zynthbox Store's Apps category as an AppImage built on the device (tools/device.sh appimage). The AppImage opens a setup page over Zynthbox with four choices: try it, make it the default, Zynthbox at boot again, remove. tools/appimage-test.sh builds it and walks all of that on the device as the release check. See docs/packaging.md.

    The QML is compiled into the binary (the Ravving QML module: qmlcachegen bytecode and C++ for typed bindings), so a QML change is a rebuild like any other, and QML errors show at build time. To try QML on the device without rebuilding, copy the qml/ folder over and start ravving with RAVVING_QML_DIR pointing at it.

    Run on a desktop

    cmake -S . -B build -G Ninja && cmake --build build
RAVVING_WINDOWED=1 RAVVING_NO_ZYNTHBOX=1 RAVVING_STYLE=Basic ./build/ravving
# or straight from the source tree's QML, no rebuild between QML edits:
RAVVING_WINDOWED=1 RAVVING_NO_ZYNTHBOX=1 RAVVING_STYLE=Basic RAVVING_QML_DIR=$PWD/qml ./build/ravving

    On a desktop without a terminal, Qt logs to journald; add QT_FORCE_STDERR_LOGGING=1 to see QML warnings.

    Keys (they send the same events as the device): 1–5 number keys · q w e r t y u i a s d f g h j k the 16 step keys · arrows · Enter select · Esc back · Space play · Backspace stop · o metronome · m menu · z/x, c/v, b/n knobs 1–3 down/up · ,/. big knob.

    Shortcuts on the device: ALT + ▲ jumps to the app header from anywhere; ALT + step keys 1–8 toggle the header's LIVE FX in their order (DROP, NO KICK, ONLY KICK, CRUSH, LO PASS, HI PASS, STUTTER, LOOP; the keys light orange while ALT is held and the pads show their key numbers); ALT + knobs 1–3 move PHASER, ECHO and HEAVY; ALT + the big knob is the master volume. A long press on a machine's S (the strip's or the header's) solos it alone. MODE walks the instrument on screen OFF → LIVE → STEP + LIVE → OFF. STOP while stopped is the panic: every instrument's held notes end (a note left sounding). In STEP entry ◀ ▶ move the entry cursor a step, and keys held together go into the same step (a chord in one column). LIVE on the melodic pages: bass, lead and the chords page's NOTES tab play the scale on all 16 step keys with ▲ ▼ shifting the octave; the chords page's CHORDS and SLOTS tabs play the seven chord keys. In STEP entry with the transport stopped, SELECT writes the editor's selected row (a note, or the chord on CHORDS) at the cursor, and with LIVE and STEP on (playing or not) ▲ ▼ walk the rows instead of the octave, each row sounding as it is reached, to find the note by ear first. On a piano roll and the chord roll one finger drags sideways to page the bars (a piano roll also drags its rows up and down; past eight semitones the octave shifts); two fingers pinch to zoom; a tap still toggles a note. The first SAVE asks for the project's name (the on-screen keyboard comes up), later saves write over it after a second press within three seconds (AGAIN?), and the button reads SAVED, asleep, until the next change; SAVE AS NEW asks again. PROJECT ▾ lists the projects and the demos: a tap opens one (a second tap when there are unsaved changes), a long press or ★ makes it a favourite; its one row of actions works on the project open: NEW, TEMPLATES, IMPORT | SAVE AS NEW | EXPORT. The pointer is shown only while a mouse is plugged in.

    Undo (docs/history.md): the header's ↶ ↷ (and ALT + ◀ ▶ on the machine pages) walk the project's timeline back and forth, a change that touched several machines at once (CLEAR ALL, a key change snapping the bass and the lead) being one step; a machine's toolbar ↶ ↷ undo that machine's own changes only. Patterns and slots are undone, and so is the arrangement: a section removed comes back with its content, a rename, a colour, a length and the song's edits go back too (picking a section is not a step). Sounds, the mix and the project's settings are not undone.

    LOCK (every pattern toolbar, first): the note grids write nothing while it is on: a tap on a cell, a step key, STEP entry, SELECT's moves and note knobs are refused, and LOCK flashes to say why; the grids still scroll, page and audition. Pressing PLAY locks them, so a stray touch cannot change what plays, and STOP unlocks them again. Tap LOCK to edit while it plays (it then stays unlocked past the stop), or to lock the grids while stopped (it then stays locked). One lock for every page; a take (●) still records.

    SELECT (bass, lead and chords, in the pattern toolbar beside ♭♯): while it is on, a tap on the grid picks a note instead of writing one (again: unpicks; on a held note's tail, the note), on any bar, and ▲ ▼ move every picked note one note of the key up or down (a semitone with ♭♯ on), keeping its length, accent and slide; each move is one UNDO. On the chords page the CHORDS view picks chords and moves them a degree, the NOTES view picks single notes; a held chord always moves as one. A long press on SELECT turns it on with every note (or chord) of the pattern picked, in all its bars, to move the whole pattern at once. Turning SELECT off drops the picks.

    A note's own settings (bass and lead): with SELECT on and notes picked, the device's knobs 1–3 set them, the picked notes together, and a readout at the grid's top right shows the first one's with its knob badges (the big knob stays the volume; a focused dial group keeps its knobs):

    Knob Setting A detent
    1 LENGTH, 1 step to 4 bars (the lighter cells; a long press on a cell sets it too) a step
    2 VELOCITY, 1–127, over the plain or ACCENT one; the ACCENT lane's cell fills to it (bright red when accented), and a tap there still flips the accent: full, or back to the plain velocity (clearing the note's own) 4
    3 NUDGE, half a step early to half a step late, from where the swing puts the note (a LIVE take with Q off records one) a 16th of a step

    They move with the note (▲ ▼ ◀ ▶ in SELECT), are one UNDO a detent, and are kept with the project and in a saved pattern preset (the chart's HOLD lane, and VELOCITY and NUDGE, by step: a velocity, a % of a step).

    SLOTS (chords page) composes with whole chords, after easyrave's: tap a slot, play a chord key (the next slot arms itself), set each slot's length (1, 2, 4 or 8 bars, never past the pattern's eight in all: "n / 8 BARS"); the slots write the chord pattern and PLAY plays them in order, the slot playing lit with its bar. ＋ adds four more slots (up to eight), − takes them away. The slots generate the pattern: once the CHORDS or NOTES view changes it, the view says PATTERN CHANGED and dims the slots, and editing a slot rebuilds from them (UNDO brings the edits back).

    Theme

    ravving wears one theme, fixed in code: RAVVING_THEME in the top-level CMakeLists.txt names the folder under data/plasma/desktoptheme/ that ships with the app (ravving-theme: the Miko theme). The app makes its bundled config/plasmarc its only plasmarc, so neither zynthbox-qml's theme chooser (~/.config/plasmarc) nor any user file can change it; the journal line ravving: theme … says what a run wears. To change the look, change the theme folder or RAVVING_THEME, and rebuild.

    Sound sources

    Bass, lead and chords can sound like something other than their synth: a tap on the nameplate opens the machine's sounds, its own engine first (the 303, Calf Monosynth, TAL NoiseMaker and its factory sounds) and then soundfont instruments played by FluidSynth (an upright and other basses, Rhodes, vibes, organ, strings, sax, flute…; the list is sources in data/kits.json, from the device's General MIDI and instrument soundfonts). Choosing one stops the engine and starts the other in its place, wired the same way; a soundfont source has SOUND MODIFIERS of its own (FILTER, ENVELOPE, MOTION). The choice is kept with the project. Acoustic sources for jazz and the like: Grand piano (Fazioli) and Upright piano (Kawai) and a Jazz guitar on CHORDS, Alto and Tenor sax and a Grand piano on LEAD, the Upright on BASS.

    The drum machines' kit picker has an ACOUSTIC group: General MIDI kits picked inside FluidR3's font (Jazz and Brush with the ride and the hi-hat foot on their rows, or with the crash; Standard, Room; presetKits in data/kits.json, see docs/engines.md). Bass and lead notes can last longer than a step (a long press on a cell stretches the row's note up to it; setNoteLength by script), and the header's swing, tapped on its caption, swings the 8ths as jazz does (SWING 8) or the 16ths (SWING 16).

    Pattern presets with their sound and MODS. SAVE CURRENT AS NEW in the presets dialog (PRESET on a pattern toolbar) keeps the machine's sound with the pattern, under the preset's optional "sound" next to its "chart": a subset of the machine's sound state (soundSource, soundPreset, the MODS sound, sourceSound and sourceSounds; the drums' kit and the kit's MODS). SAVE PATTERN AS has WITH ITS SOUND (the source or kit playing, its factory sound) and WITH ITS MODS (the MODS that are set: one nobody turned is left out, PresetLibrary::setParts), both on each time it opens; both off, the pattern alone. A curated pack may name just a source or a kit, or add MODS too (data/secret/patternkit.py). Such presets say ♪ and the sound's name under their genre, "+ MODS" when they keep MODS, and the dialog then shows WITH ITS SOUND and WITH ITS MODS (off by default, remembered in the profile under presets/withSound and presets/withMods): loading one also switches the machine to its sound, and sets its MODS, only the parts the preset names (PresetLibrary::soundParts, Machine::applySoundParts, the path MY SOUNDS takes): a preset with no MODS leaves the machine's MODS as they are. Turning SOUND on turns MODS on too (a sound is heard with its MODS); MODS then turns off on its own, and on alone it brings a preset's MODS to the sound already playing. Both off, only the pattern loads, as before. A source or kit this device does not have leaves that part of the sound as it is (one line in the log). The samplers' presets keep no sound (theirs is in their banks), nor do the shipped ones; a preset copied to a stick carries its sound in its file. Beside it, WITH ITS BARS (on by default, presets/withBars): off, a preset keeps the pattern's bar count instead of bringing its own, laid over it from the first bar (a shorter preset repeats to fill it, a longer one is cut; PresetLibrary::fitChart), so the bar pages stay as they are. The presets dialog is organised as the sound pickers are: a GROUP chip per genre, SORT (as listed / A–Z) and ★ favourites (a long press, the ★ at a preset's corner, ALT + SELECT), kept per library (favourites/presets-drums, -bass…) by the preset's name, so a stick's preset and the same one taken in share their ★; it opens on ALL when the group last shown would hide the preset on screen.

    A whole project can be built by script over the remote-control fifo, samples, patterns, sounds and all: tools/examples/lofi-say-it.sh is one, docs/scripting-projects.md the recipe.

    Templates. PROJECT ▾ → TEMPLATES (beside NEW) lists project templates: a template is how a project starts, its tempo, swing, key (root and scale) and LIVE FX knobs (PHASER, ECHO, HEAVY). SOURCE picks the device's or a USB stick's (read straight from its ravving/presets/templates/), as the pattern presets' dialog does. Choosing one is NEW with those set (asking first over unsaved changes, as NEW does). SAVE TEMPLATE keeps the session's own as one of the device's (DELETE removes it); the USB dialog's PRESETS copies templates either way. Every genre pack in data/secret ships one beside its patterns (or more: the Vuelo pack has one per key).

    A new project starts clean. NEW, and NEW from a template, put every page back to its defaults: an empty pattern on each machine (no preset loaded), its own engine and the default sound, mix, MODS and SOUND EFFECTS, one section "A", the LIVE FX at rest; a template sets only its tempo, swing, key and LIVE FX knobs on top (Studio::cleanProjectState). The shipped demo patterns come back only through a project or a preset.

    Demos. Ravving ships three projects to open from PROJECT ▾ → DEMOS: Autumn Leaves (a jazz trio and alto sax at 146 BPM, swung 8ths, sections A1 A2 B C and a solo chorus) and 5AM (dark electronic pop at 188 BPM in D harmonic minor over Dm – Gm – A – Dm, the changes of Grimes' "4ÆM", everything else written for ravving: a 909 two-step on a breakbeat, an acid bass, a pumping pad and a lead hook, in six sections with a four-bar HUSH before the last drop; its generator is tools/examples/five-am/) and B3rlin (dark techno at 135 BPM in G Phrygian after Native Instruments' dark techno and Minimal Audio's hard techno write-ups: a 909 floor with light layers of drive on the kick, the 909's ride and a rim on a three-bar loop, the 808's toms on a five-bar one, a sidechained bass rumble, a filtered lead sequence falling a minor second, a sinister pad and a stab; INTRO · RUMBLE · RIDE · PEAK ×2 · BREAK (no kick, the bass on, a snare roll) · PEAK ×2 · OUTRO; tools/examples/b3rlin/). They live in data/demos/ (installed read-only beside kits.json) and use only the image's own soundfonts, so they play the same on any Zynthbox. A demo opens like a project; SAVE keeps the changes as a project of the user's under the demo's name, the demo itself never changes, and it cannot be deleted. A new demo is a project JSON dropped into data/demos/ that names no sample or file outside /zynthian/zynthian-data.

    Sections and the song

    A song is more than one loop. A section holds every machine's pattern at once (an intro, a verse, a bridge) and which machines rest in it; the sounds, effects, levels, tempo and key stay the project's, so a change of section never restarts an engine. Sections are live: the one on screen is the one you edit, and what you edit stays in it when you pick another.

    • LOOP | ONCE (on each machine's strip, beside ❚❚, kept per section like it). A section lasts as long as its longest pattern, or its LENGTH. A shorter pattern LOOPs through it by default (2 bars of drums play twice under a 4-bar lead); on ONCE it plays its own bars once and rests until the section starts again. The rest is exact: the machine's clip is told to play the section's length, the bars past its own kept empty, so nothing is cut and a tail rings out. While it rests no playhead shows and a hit played live is heard, not written.

    • When a switch lands: SWITCH · BAR | SECTION (the SONG page, kept with the project). BAR: a section picked while playing takes over on the next bar. SECTION: it waits for the section playing to finish its pass (its key blinks, the one playing stays lit; picking the one playing again lets it go; stopping plays it at once), then switches on that pass's bar line, in LOOP and in SONG (the song jumps to the picked section's entry). A one-bar section ends every bar. In LOOP the picks queue up, up to three: each plays one pass, then the next takes over, the last looping on; the keys wear their place (1 blinking: next), a queued key picked again leaves the queue, the one playing picked empties it, a fourth pick is refused (QUEUE FULL), stopping puts the first in place and drops the rest. In SONG one pick waits, a new one taking its place. There is no BEAT: libzynthbox's playfield swaps clips on a bar line only.

    • Switching on the bar line. A section picked while the transport plays takes over on the next bar, sample-accurately: each machine writes it into its track's other clip and libzynthbox swaps the two on the bar's first tick, so no note drops or doubles (a machine whose part does not change keeps playing). Stopped, a pick is immediate. Measured with tools/sections-test.sh: every change on a bar line, every 8th on the grid.
    • The plate. The header's project plate wears the section on screen as a square key with its number, in its colour, blinking while it waits for the bar; a tap opens the SONG page.
    • X and Y (the two keys beside the big knob) go to the previous and the next section from any page or dialog, wrapping round, as a section key would pick it (from the next bar while playing, at once when stopped); pressed again before the switch lands, they move the pick on rather than queue another. With one section a toast says to add more on the SONG page.
    • ALT + step keys 9–16 pick sections 1–8 from any page (lit in their colours while ALT is held; ALT + 1–8 stay the LIVE FX pads). With the section keys in the header, ALT + 1–16 pick sections 1–16, and while their group has the focus (the header's ◀ ▶ onto it) the step keys alone pick them, lit in the sections' colours.
    • The section keys in the header. A long press on the project plate, or ALT + MODE (MODE lights orange while ALT is held; MODE alone still cycles the entry mode), puts the section keys where the LIVE FX pads are (the same again brings the pads back): the SONG page's keys, at the pads' size, without their dots. A tap picks one (on the next bar while it plays), ▶ marks the one sounding and its progress fills it, a swipe up removes one (it follows the finger and fades; past half its height it flies off; never the last), more than fit swipe sideways (the strip slides to the section that becomes current or that the song reaches), the keys grouped on a slab in the song's colour with ＋ pinned at its end, always in reach.
    • Seeing the change. As the section sounding changes (a SONG part, or a LOOP pick landing on the bar line) the plate sweeps in its colour and the instrument page glows round its frame in it, once; the section keys (here and on the SONG page) fill with the section's progress.
    • The SONG page, under the header like the MIXER (ALT + 1 from anywhere, again to go back), wears its own nameplate as an instrument does and follows easyrave's SECTIONS shelf at a finger's size, in a frame as the instruments' grids: square keys wearing their number with the name under (eight a row, the first row being the ALT keys), a dot per sounding machine; tap picks, double tap renames, hold and drag moves, × deletes (a second tap), ＋ copies the section on screen (A → A′). Under them: RENAME, NEW (empty), COLOUR, LENGTH (1–8 bars or AUTO, the longest pattern), MOVE, ADD TO SONG. The song is a strip of blocks as wide as their bars × repeats: a block picked moves, repeats (×1–×16) or goes. Keys: ◀ ▶ walk, ▲ ▼ between keys and blocks, SELECT or a step key picks, ALT + ◀ ▶ moves, knob 1 the length, knob 2 the repeats, BACK leaves.

    SONG mode. LOOP | SONG on the SONG page says what PLAY plays: the section on screen, looped, or the song through. In SONG the first part's section is in place before the first note, each next part is cued as the last bar of the one before begins, and the song stops on the bar line after its end; the block playing shows its progress and the plate the part ("6/9"). While the song plays the instrument pages follow it, their note grids locked as whenever the music plays (LOCK, below); unlocked, an edit goes into the section playing. ▶ PLAY FROM HERE starts it at any block; a section picked by hand while it plays jumps to its first part (one the song does not have goes back to LOOP). EXPORT → WHAT: SONG records the whole song in one take, its own length plus the tail; LOOP is BARS × LOOPS.

    Up to 16 sections; saved with the project (a project from before opens as one section, "A"). The design and what each phase measured: docs/sections-plan.md.

    CHORDS also carries the image's pad soundfonts, grouped by name in its picker: Strings (Ensemble, Fat, Digital, Rise, Bowed, Piano), Organ (Phaser, Pipe 16+8+4, House, Extreme) and Alien (the "Ambients & Drones" fonts: The Thing, Strange voices, Crystal voice, Glassy, Winds, Chaos, The Pulse), each a FluidSynth preset from /zynthian/zynthian-data/soundfonts. A sustained, polyphonic machine suits them: the chords hold while the voicing lasts, and the key keeps them in tune with the bass and lead. tools/soundfont.py categorise --json FONT… proposes entries for more fonts. The sound pickers group their lists (GROUP chips, ★ for the favourites you mark with the star or ALT + SELECT, SORT as listed or A–Z) and remember the group and sort per instrument.

    UI rules

    ravving's screens share one look (easyrave's machines: rails and a face in their own finish, controls grouped on strips, work areas in wells, a dark header band). docs/ui-rules.md has the rules: squared ActionButtons for actions and rounded chips for states, one ✕ (CloseButton) to leave and no CLOSE / CANCEL buttons, an EmptyNote in every empty view, Chassis / PageHeader for pages, and palettes readable by WCAG contrast. tools/check-ui.py checks them (ctest -R ui-rules, tools/static-analysis.sh ui) from tools/ui-rules.json, where new rules go.

    Languages

    ravving speaks English, Spanish and Japanese, with the words musicians use in each (BATERÍA, BOMBO, COMPÁS; ドラム, キック, 小節). MENU → SETTINGS → LANGUAGE: SYSTEM (the default) follows the device's own language, or pick English, Español or 日本語; the screen changes at once. The keys printed on the device (MENU, ALT, SELECT…) and the machines' names stay as printed. The webpage has Spanish and Japanese pages too (the switcher in its top bar); the docs are in English. It is KI18n with gettext catalogs: one catalog per language for the app (po/) and one for the page (po-site/), so a new language is two files to translate. Every release has its translations reviewed. docs/translations.md has how it works, the glossary and the steps.

    Startup splash

    ravving shows its logo while it starts (StartupSplash, qml/Splash.qml and SplashLook.qml), from the moment libzynthbox is up until the page is ready, then plays a short show into the page. MENU → SETTINGS → STARTUP picks the look, from the next start: ANIME (fast cuts through the five flow-lens logos into the glow one), GLOW (one at random, its halo swelling), STILL (one at random, a fade), ZOOM (the fluid logo rushing out past the screen) or OFF. While the studio loads the splash is a still picture: an animation meanwhile kept the screen redrawn every frame and made the start 2–3 s longer on milo; with the still it costs about 0.2–0.35 s. The show plays in the page's own window (kwin keeps a full-screen window above a "stay on top" one). The logos are the effect SVGs drawn without their backgrounds (data/branding/make-splash.sh); the album art's wordmark is data/branding/ravving-wordmark.svg.

    Exports and the music player

    PROJECT ▾ → EXPORT writes the project out of the device, into the library's exports/ folder:

    • A track: the whole production as the speakers hear it, recorded while the project plays from its first beat for BARS × LOOPS bars plus a TAIL for the echoes, cut to the sample, in WAV 24-bit, FLAC, OGG Vorbis or MP3, with its tags (title, artist, album / mixtape, genre, composer, comment, date, BPM), a cover drawn for it (from the title and the artist, with MADE WITH RAVVING) and a JSON sidecar. The master's level is kept as it is: a track that peaks over full scale is pulled down to −0.1 dBFS and the sidecar says so.
    • A bundle: a .ravv zip of the project with every sample it uses, for another ravving to play it the same; PROJECT ▾ → IMPORT lists the bundles found in exports/ (and the library's root, where a transfer lands) and makes a project of one.

    The ARTIST and COMPOSER start from the profile's author (MENU → SETTINGS: USER and AUTHOR); the ALBUM and GENRE last typed are offered again.

    MENU → SETTINGS → INTERACTIONS: NOTES OUTSIDE THE SCALE (on by default). On, a key played outside the key (a MIDI keyboard's) on the lead, the bass or the chords' NOTES sounds and records in a row of its own on the roll; off, it is muted there and never recorded. The drums, the samplers and the chords played on a degree ignore it.

    Video recordings and the computer link

    The control center's LIVE REC card records the session: a tap opens a dialog that asks WHAT, a VIDEO (the screen or a USB camera with the master's sound, an MP4 in the library's videos/ folder) or AUDIO ONLY (the sound alone, a 24-bit WAV among the TRACKS in the exports folder), whether the MIC is in, and START (the dialog is the confirmation, so a stray tap never starts a recording; ending one is a single tap; a new project switches LIVE REC off). While LIVE REC is on, the device's RECORD key starts a recording and STOP ends it (the music goes on), from any page; SETTINGS · VIDEO has the QUALITY (three tiers measured at 0 xruns), the TIMER counted down before a recording, the SOURCE, MIC (the RECORDER's input in the video's sound) and VOICE, the voice-over mix: while the mic carries a voice the music ducks under it (DUCK −6 / −12 / −18 dB, −12 by default) and the voice is lifted (+6 / +12 dB) and made crisp (a low cut and a presence lift), so a voice over the playing is heard on top rather than buried; a voice is the mic 12 dB over what the speakers are heard to leak into it (the beat does not duck itself), the mix goes through a look-ahead limiter rather than clipping, and the mic's LEVEL is metered from the moment VIDEO is on (in SETTINGS and standing on the project plate; MIC TOO HOT when its peaks pass −6 dBFS: turn the RECORDER's GAIN down); with the RECORDER on GUITAR or LINE the input is summed as it is. Both apply to a recording under way. VIDEO SAVED or LIVE REC SAVED, when one ends, offers DELETE at its left (a second tap within three seconds confirms), RENAME (the file keeps its extension) and SEND… through one dialog that lists every USB stick, every computer and the phone; an audio recording also has METADATA…, the export dialog over the file, which tags it (title, artist, album, genre, composer, comment), draws its cover, writes it in the format chosen (WAV, FLAC, OGG, MP3) and sends it on, through the track export's own finishing; the same SEND… is on the music player's tracks, in FILES and in the presets dialogs, and the export dialog can send a new track or bundle to a computer as it is written.

    SETTINGS · COMPUTERS holds any number of computers (laptops or PCs on the network, over SSH): ADD A COMPUTER asks for its host, user and password, the password is used once to install the device's one key there, and files land in that computer's Downloads folder; each has CHANGE (set up again, TEST, FORGET). docs/video.md has the design, the measurements and the tests (tools/video-test.sh, tools/video-voice-check.sh, tools/computer-link-test.sh).

    Files

    The control center's FILES card browses everything in the library by kind (projects, templates, presets, samples, takes, the RECORDER's takes, recordings, tracks, bundles, soundfonts, MIDI files, videos, received files), newest first, each entry with SEND… (the standard dialog: a USB stick's ravving folder, one of the computers or the phone) and DELETE. It is the one place files leave the device or are deleted; the PROJECT dialog opens, saves and exports, and the USB page brings a stick's files in. PHONE · BROWSE in its header shows a QR code of the same library as pages for a phone (or a laptop) on the Wi-Fi: every kind with its count, each kind's files with their detail, size and date, and a DOWNLOAD per file, served by ravving itself (FileShare.openBrowse, a random path that lives until 15 minutes pass with no request from the phone, the dialog closed or not; get share browseUrl over the fifo); a project or anything that is a folder is listed as "on the device"; a link that ran out says so on the phone.

    USB sticks

    A stick plugged in shows up as a USB row in the export dialog (a Zynthbox runs udisks but mounts nothing by itself; ravving mounts the stick when it needs it): the track or bundle is written to the library as always and copied to the stick's ravving/ exports/ or ravving/projects/ folder, then EJECT (in the dialog or on the USB page) flushes, unmounts and powers it off so it can be pulled. PROJECT ▾ → TO USB bundles the highlighted saved project onto the stick, and IMPORT lists the bundles found on every stick (its ravving/projects/ and its root) beside the device's own. The project dialog also keeps favourites (★, a long press).

    The drawer's USB card opens the USB page (usb, UsbLibrary): ON USB lists what the stick holds by kind (SAMPLES, SOUNDFONTS, PROJECTS, TRACKS, MIDI FILES: found anywhere on it, its ravving/<kind> folders first, system folders skipped), each with IMPORT (✓ ON DEVICE once the library has it); FROM DEVICE lists the library's, each with TO USB. Samples land in samples/imported/<stick>/ keeping the stick's folders, soundfonts in soundfonts/, MIDI files in midi/, tracks in exports/ (the music player lists them), projects through the bundle import. One copy at a time, through a part file, a copy onto the stick synced before it counts. The presets dialog (a pattern toolbar's PRESET) has a SOURCE row when a stick is in: DEVICE, or USB · , which lists that machine's pattern presets in the stick's ravving/presets/<drums|bass|lead|chords>/patterns and plays the one picked straight from there, without taking it in (usb.patternPresets / usb.loadPattern; one UNDO puts the pattern back). The dialog opens on the source the pattern on screen came from (the stick a preset was played from, while it is in), with that preset marked. data/secret/jazz-presets/ (not installed) builds a pack laid out that way: five jazz patterns for each of the drums, the bass, the lead and the chords, to copy to a stick. IMPORT ALL beside the folder path brings every new file of the folder on screen and its folders in one go (a sample pack is one tap: IMPORTING 12 / 229 · STOP, one look through the stick and one message at the end; 229 samples in well under a minute). ◀ ▶ the kinds, ALT + ◀ ▶ the side, ▲ ▼ the files, SELECT copies, EJECT in the header. With more than one stick (or partition) plugged in, the card names each stick and a tap asks which one to open. A read-only stick (an installer's ISO image, a locked stick) says so: nothing is offered to copy to it, exports and TO USB skip it, and its page shows FORMAT, which erases the whole stick into one writable FAT32 partition labelled RAVVING (EJECT and FORMAT both want a second press within three seconds).

    A soundfont brought in is used at once (Studio.refreshImported, also at every start): one that looks like a drum kit (three drum roles or more in its sample names) joins the kit picker under IMPORTED, and every preset of every imported font is a chords / bass / lead source, " · ", grouped by font in the sound pickers.

    Bluetooth

    MENU → BLUETOOTH works the way a phone's does: the switch, SCAN (a short scan of classic devices; it starts on its own only while no speaker plays, since a scan breaks up a playing Bluetooth link on the Pi's shared radio), and VISIBLE (milo can be found for three minutes, so a phone can send it a file); the devices connected first, then paired, then in range. A tap on one opens its row: PAIR (a passkey to confirm or a PIN to type is asked in the head), CONNECT / DISCONNECT, SEND… (an exported track or bundle, picked next; the progress runs along the bottom), PLAY THROUGH for a speaker or headphones (the whole studio's sound switches to it, DEVICE OUTPUT brings it back; the same choice sits in the drawer's AUDIO OUTPUT card with the jacks and HDMI) and FORGET. Files sent to milo land in the library's incoming/ folder: a bundle shows in PROJECT ▾ → IMPORT, a track in the music player under "Received". Built on KDE's BluezQt over BlueZ; sound through PipeWire's Bluetooth plugin (libspa-0.2-bluetooth) and files through bluez-obexd, both installed on the image by ravving's setup. Ravving also ships the drop-in that lets bluetooth.service start at all on a Zynthbox (its own drop-in names a bluetoothd path Debian 13 moved), and a WirePlumber drop-in that lets its Bluetooth monitor run without a logind seat. The whole setup, with its checks and the troubleshooting table, is docs/bluetooth.md; tools/bluetooth-setup.sh applies it to a device.

    Connecting behaves like a phone too. A speaker that does not answer (asleep, waking up, or busy with a phone) is paged again three more times over about 35 s (the row reads "waking…"; DISCONNECT from the fifo stops it) before COULD NOT CONNECT. One audio device plays at a time: BlueZ keeps one A2DP endpoint per codec for every device, and PipeWire registers one SBC source, so while the Sony headphones stream SBC an SBC-only speaker (the LG SJ1) cannot set up its audio (bluetoothd logs "Unable to select SEP", the call fails with br-connection-create-socket) however often it is retried. A device that answered but could not connect while another audio device is connected is therefore handed the link: SWITCHING FROM · the other device, which is disconnected, and the connection is made again. PLAY THROUGH routes once the connection is made. When Bluetooth comes on (a start, the switch) the output kept is connected again, once, if nothing else plays; ravving never pages in a loop, since a speaker in standby wakes up when paged.

    MENU → MUSIC PLAYER (and DASHBOARD to come back) is a full-screen player for the exported tracks and the ● recordings: TRACKS (sorted), ALBUMS and ARTISTS on the left, the cover, transport, position and volume on the right over the QUEUE. Keys 1 2 3 switch the views, ▲ ▼ pick, SELECT plays, PLAY pauses, STOP stops, the big knob is the volume and knob 1 the position, BACK leaves. Opening the player stops the transport and leaving it stops the player.

    Audio output

    MENU → AUDIO OUTPUT picks where the studio's sound goes: the device's jacks (the default), HDMI, or any Bluetooth speaker or headphones connected in the BLUETOOTH dialog. The jacks stay the JACK graph's clock whatever is chosen; another output is fed through a loopback of ravving's own with a 2048-frame buffer, the master's output linked to it and the jacks muted (not unlinked: an unlinked jacks sink is suspended and the Bluetooth transport becomes the graph's clock, which stalled everything silently once, 2026-10-12), so the sound is glitch-free and comes out of one place only (making the Bluetooth sink PipeWire's default sink did neither, as measured on milo). The choice is kept: when the output goes away (headphones turned off) the sound falls back to the jacks, and it goes back to the output once it is there again (a restart, a reconnection; a Bluetooth output's address is kept with it, so that Bluetooth can connect it when it comes on); picking the jacks forgets it. The dialog's list follows PipeWire while it is open. The music player, which plays beside the master, follows the output picked too. The drawer's OUTPUT slider (knob 2) sets the amplifier's level on the jacks and the chosen sink's own level otherwise. Each paired speaker or headphones has its own SBC-XQ chip in the BLUETOOTH dialog (open its row): off plays it on plain SBC, sturdier over a weak link, whatever SETTINGS says for the rest; a device without its own choice follows SETTINGS. A Bluetooth output gets its codec first and is routed to once its new sink is there, whether it comes back on its own or is picked: routing first and switching the codec after replaced the sink under a live loopback. While another output plays, ravving listens to what goes into its loopback and what comes out: music going in with silence coming out for six seconds is routed again once (a fresh loopback), and if it is still silent the issues center says the output plays no sound (2026-10-12: after a Bluetooth codec switch the LG speaker went silent with every node "running" and nothing said so).

    The RECORDER

    MENU → RECORDER is a full-screen page (as the music player) for recording the input freely, as played (docs/recorder-plan.md). The transport keeps going, so a take can be played over the beat. The input is a tab (MIC · GUITAR · LINE); under the bar, MONITOR and its LEVEL, the jack lights, the GAIN with the meter, ● REC beside a graph of the incoming level, KEEP TAKES IN (SAMPLES: samples/recordings, the samplers' browsers list them; TRACKS: the library's recordings, the music player lists them) and the EFFECTS made for the input (on GUITAR the amps and pedals: AMP, OVERDRIVE, FUZZ, TUBE, WAH, HOT AMP, from the guitarix LV2s on the image). A take is kept as it came in: no compression, no trim, no SMART stop. On the right the RECORDINGS of both places, newest first: ▶ PLAY, TRIM and NORMALISE (a new recording beside it), TO SAMPLE KING / TO PADS (into a slot or a pad), CHOP… (onto SAMPLE KING's bank or the pads, the samplers' wave editor), TO TRACKS / TO SAMPLES, RENAME, DELETE (twice).

    On GUITAR the page has a TUNER, on the dry input (before the effects): the note heard and its cents on a ±50 scale, the strings of the tuning as buttons. AUTO goes through the strings from the lowest: a string held within 3 cents for 0.8 s is marked ✓ and the next one is up, until ALL STRINGS IN TUNE; MANUAL keeps the string tapped. TUNING picks a tuning (guitar standard, half and full step down, drop D and C, DADGAD, open D, G, E and C; bass 4 and 5 strings, drop D; ukulele GCEA and baritone), A4 the reference (430–450 Hz). The pitch is McLeod's method as guitarix's tuner has it (src/backend/pitchdetector.h, tested in tests/tst_pitchdetector.cpp); its JACK client runs only while the tuner is on screen.

    Keys: ◀ ▶ the input, ▲ ▼ the recordings, RECORD a take, SELECT or PLAY hears the recording picked (STOP stops it), the number keys move the knobs between INPUT (1), TUNER (2) and EFFECTS (3), the big knob is the gain, BACK leaves.

    The issues center

    MENU → the ISSUES icon card (beside MUSIC PLAYER, SETTINGS and the USB card) says what is wrong on the device right now, in plain words, with what to do about it: ALL GOOD, or the count lit in the worst severity's colour, and the full list in the dialog, worst first, each with its detail, a suggestion and an action button where one exists (RESTART RAVVING, GDB OFF · RESTART). Every component runs its own check pass and reports: the sound engine missing, an engine that could not start, audio connections that never appeared, audio dropouts (xruns counted every minute), the device's keys dying (zyncoder's GPIO thread, read off stderr), the music player without its PulseAudio bridge, Bluetooth unavailable, an export that failed, a USB stick that would not mount, storage nearly full, the gdb aid left on. New errors and warnings also show as a toast. Under the list, the last warnings ravving printed. docs/extending.md says how a component reports.

    The audio graph

    Everything runs in PipeWire's graph through its JACK library, at the sound card's 48 kHz and 256 frames: libzynthbox's passthroughs, the jalv inserts, and FluidSynth, which is told the graph's clock so its node is neither resampled nor buffered beyond two periods. tools/device.sh graph all checks the clocks, the links, the threads and the xruns in one go; docs/routing.md maps what ravving wires and records what was measured (among it: running ravving under gdb costs the graph 20 to 40 xruns a minute, so the RAVVING_GDB aid is for crash hunts only).

    Where ravving keeps its files

    Nothing of ravving's goes into zynthbox-qml's folders, and nothing of zynthbox-qml's is written: ravving reads the device's sample library and writes only to its own places (src/backend/paths.h), following the XDG base directories:

    Root On the device What
    config ~/.config/ravving settings (the input set-up, the UI's choices)
    state ~/.local/state/ravving the live session (session.json, the sequence); removed by a purge
    cache ~/.cache/ravving rebuildable: reversed samples, raw takes, the LV2 port cache
    library /zynthian/zynthian-my-data/ravving the user's work, kept across reinstalls: projects/, presets/, samples/ (takes in samples/takes/, the RECORDER's in samples/recordings/, imported bundles' samples in samples/imported/), recordings/ (the master's and the RECORDER's TRACKS), exports/

    On a desktop the library is ~/.local/share/ravving. An older ravving's files are moved into this layout at the first start, and the session's and projects' sample paths with them.

    Environment variables

    Variable Effect
    RAVVING_WINDOWED=1 windowed instead of fullscreen
    RAVVING_NO_ZYNTHBOX=1 skip libzynthbox (UI only)
    RAVVING_STYLE Quick Controls style (default Zynthbox)
    RAVVING_QML_DIR read the QML from this folder (a source tree's qml/) instead of the copy compiled in
    RAVVING_DATA_DIR read kits.json and the theme (plasma/desktoptheme/) from this folder (desktop: $PWD/data; the plasmarc then comes from build/config/)
    RAVVING_HOME one folder for everything ravving writes (config/, state/, cache/, library/), for a sandboxed run
    RAVVING_LIBRARY the library alone (projects, presets, samples, recordings) somewhere else
    RAVVING_PROJECT_DIR the session folder alone (older name; default ~/.local/state/ravving)
    RAVVING_SCREENSHOT_DIR capture every page to PNGs there, then quit
    RAVVING_GDB=1 (service) run under gdb, backtrace to the journal
    QT_LOGGING_RULES="ravving.cuia.debug=true" log every hardware event (CUIA, knobs)

    For the service, set them with systemctl --user set-environment NAME=value and clear them with unset-environment.
