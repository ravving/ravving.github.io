    Using ravving / docs/bluetooth.md

    Bluetooth

    Speakers and headphones, files to and from a phone, what a Zynthbox needs for it and how to troubleshoot.

    Ravving's Bluetooth does what a phone's does: pair, connect, send a file, play through a speaker or headphones, receive a file. This page records what a Zynthbox needs for that to work at all (a stock image cannot even start the Bluetooth service), how the pieces fit, how to test them, and what to look at when something fails.

    What the stock image lacks, and the fix

    Found on milo (Zynthbox on a Raspberry Pi 5, Debian 13, BlueZ 5.82, PipeWire 1.4.2, WirePlumber 0.5.8), 2026-10-08:

    Problem Cause Fix (shipped by ravving)
    bluetooth.service fails at boot (status 203/EXEC), the adapter stays DOWN, the control center says "its service is not running" zynthian-sys's drop-in /etc/systemd/system/bluetooth.service.d/01-disable-sap-plugin.conf starts /usr/lib/bluetooth/bluetoothd, which Debian 13 moved to /usr/libexec/bluetooth/ data/systemd/50-ravving-bluetoothd-path.conf, installed to the same drop-in folder: the same flags (--compat --experimental --noplugin=sap) with the path that exists
    a speaker or headphones pair but will not connect: org.bluez.Error.Failed br-connection-profile-unavailable; the adapter's UUIDs (bluetoothctl show) list no Audio Source / Audio Sink WirePlumber's Bluetooth monitor (monitors/bluez.lua) waits for a logind "active" seat before creating the BlueZ handle that registers the A2DP endpoints; the root startx session never reports one, so the monitor never starts and BlueZ has nothing to connect the device to data/wireplumber/50-ravving-bluetooth.conf, installed to /etc/wireplumber/wireplumber.conf.d/: wireplumber.profiles.main.monitor.bluez.seat-monitoring = disabled
    no audio over Bluetooth at all libspa-0.2-bluetooth (PipeWire's A2DP / HFP plugin with the SBC, aptX, FastStream, LDAC codecs) is not installed apt install libspa-0.2-bluetooth, then a WirePlumber restart (it loads the plugin at start)
    no file transfer bluez-obexd (the OBEX daemon, obex.service in the user session, D-Bus activated as org.bluez.obex) is not installed apt install bluez-obexd
    the Qt side ravving links KDE's BluezQt (libkf6bluezqt6, present on the image; libkf6bluezqt-dev to build) —

    tools/bluetooth-setup.sh does all of it on a device and checks every step (--check only checks); cmake --install puts the two drop-ins in place as well. After the setup bluetoothctl show lists Audio Source, Audio Sink, Handsfree and Handsfree Audio Gateway.

    How it fits

    • Backend Bluetooth (src/backend/bluetooth.*, QML bluetooth), on BluezQt: the adapter (power, discovery, discoverable for three minutes), the devices (connected first, then paired, then by signal; private-address phones without a name hidden until paired), a pairing Agent (DisplayYesNo: a passkey to confirm or a PIN to type lands in pairing, answered with answerPairing), pair → trust → connect, forget, OBEX Object Push sending (sendFile, progress in transfer), an ObexAgent accepting pushes into the library's incoming/ folder, and the audio switch (useAsOutput).
    • Audio. When an audio device connects, WirePlumber makes a sink node bluez_output.<address>.1 (and an input / capture node for HFP). useAsOutput hands it to AudioOutputs (outputs, also the control center's AUDIO OUTPUT card), which does not make it the default sink: that would clock the whole JACK graph by the Bluetooth transport in 256-frame chunks (glitches, measured on milo with the Sony WH-CH720N) and leave the master's links to the jacks in place (sound from both). Instead the jacks keep the clock, a pw-loopback of ravving's own (ravving-out, a virtual sink whose playback stream targets the Bluetooth sink with a 2048-frame buffer) is started, the master's two output ports are linked to it with pw-link (its inputs have no JACK name, so libzynthbox's JackConnectionHandler cannot) and the jack links are dropped. Measured: the Bluetooth node runs at 48 kHz SBC, the HiFiBerry node goes idle, the sound is clean and the jacks silent. Off, on disconnect, forget or exit, the loopback stops and the jack links come back.
    • Files. Sending opens an OBEX session (Target: opp) and pushes the file; receiving needs milo VISIBLE (discoverable + pairable, three minutes) and lands under library/incoming/, which PROJECT ▾ → IMPORT lists as "received" and the music library as the album "Received".
    • UI. BluetoothPopup from the control center's BLUETOOTH card.

    Testing it

    The basic checks: sh tools/bluetooth-setup.sh --check. With a device at hand, over the fifo (docs/testing.md):

    tools/device.sh call bluetooth startDiscovery; sleep 10; tools/device.sh get bluetooth devices
tools/device.sh call bluetooth pair 84:D3:52:35:80:99        # a speaker pairs without a prompt
tools/device.sh get bluetooth pairing                        # a phone: {kind confirm, passkey} → answerPairing true
tools/device.sh call bluetooth useAsOutput 84:D3:52:35:80:99 true
tools/device.sh cuia SWITCH_PLAY_RELEASED                    # heard on the speaker
tools/device.sh call bluetooth sendFile AA:BB:CC:DD:EE:FF "/zynthian/zynthian-my-data/ravving/exports/Lo-fi Say It.wav"

    What to measure (the user's QA notes, 2026-10-08):

    Metric How, on the device
    signal (RSSI, dBm: −30 excellent, −67…−70 good, below −80 drops) bluetoothctl info ADDR (RSSI while scanning), hcitool rssi ADDR once connected
    link quality / packet loss hcitool lq ADDR (255 = best); btmon -w /tmp/bt.snoop during playback and count retransmissions
    A2DP codec and latency pw-cli info <bluez sink id> (api.bluez5.codec: SBC by default, aptX / LDAC when both sides have it); pw-top for the sink node's quantum and the graph's (the studio stays at 256 / 48000; the Bluetooth node runs its own)
    OBEX throughput transfer.transferred over time (get bluetooth transfer)
    what BlueZ sees btmon (HCI trace), busctl --system tree org.bluez, journalctl -u bluetooth
    what WirePlumber does journalctl --user -u wireplumber, with systemctl --user set-environment WIREPLUMBER_DEBUG=3 and a restart for the monitor's own lines

    Measured on milo (2026-10-08)

    Sony WH-CH720N (84:D3:52:35:80:99), paired and connected, playing through the loopback route; the adapter is the Pi's own (hci0, UART, BCM43455 class 0x6c0000). The tools are hcitool, l2ping, busctl (BlueZ's D-Bus objects) and pw-dump, all on the image.

    What Command Result
    link quality hcitool lq <addr> 255 / 255 (the best the firmware reports)
    RSSI hcitool rssi <addr> 0 (the firmware reports "in the golden range", not dBm)
    transmit power hcitool tpl <addr> 12 dBm
    adaptive hopping hcitool afh <addr> 30 of 79 channels in use (the Wi-Fi band is cut out)
    round trip l2ping -c 5 <addr> 18.7 ms, 0 % loss
    codec negotiated pw-dump → api.bluez5.codec sbc; busctl … MediaTransport1 Configuration = 17 21 2 53: 48 kHz joint stereo, 16 blocks, 8 subbands, loudness, bitpool 2–53 (SBC "high quality", ~345 kb/s)
    codecs the device offers the device's sep* endpoints (MediaEndpoint1 Codec) 0 = SBC, 2 = AAC; the image has no AAC plugin (Debian ships none), it has aptX, LDAC, LC3, Opus, FastStream for devices with those
    SBC-XQ ravving's WirePlumber drop-in sets bluez5.enable-sbc-xq a second profile a2dp-sink-sbc_xq appears (wpctl set-profile <dev> <index> to use it, bitpool up to 76, ~550 kb/s); WirePlumber still picks plain a2dp-sink by default
    transport delay MediaTransport1 Delay 14 (1/10 ms; what the headphones claim, a nominal value)
    playback buffer the loopback's node.latency 2048 / 48000 = 43 ms before the codec; the headphones add their own (SBC devices are typically 150–250 ms end to end)
    xruns over 20 s of a full project pw-top ERR on the bluez sink before / after 19 / 19 (none new); the HiFiBerry node idle, the graph's quantum stays 256
    battery bluetoothctl info → Battery Percentage reported (70 %)

    Not measured yet: OBEX throughput (needs a phone), end-to-end audio latency (needs a microphone at the headphones: play a click through the route and record it).

    Two traps found while testing: - A scan starves the audio link. The Pi has one radio for Bluetooth and Wi-Fi; a discovery (inquiry) while headphones play makes the sound break up, and a long one gets the headphones dropped. The dialog therefore scans for 12 s only (DiscoverySeconds) and does not scan on its own while an audio device is connected: SCAN is the user's call then. - A dual-mode speaker found by its LE advertisement pairs the wrong side. The LG S20A advertises LE Audio (Audio Stream Control, Published Audio Capabilities, Telephony and Media Audio) as well as classic A2DP; paired from the LE advertisement it had no Audio Sink UUID, PipeWire made no sink for it, and ravving offered no PLAY THROUGH. BlueZ can play LE Audio only with its experimental features on and a kernel with ISO sockets, and the Pi's firmware has none, so ravving scans classic (BR/EDR) only (setDiscoveryFilter {Transport: bredr}), where the A2DP side pairs. By hand: bluetoothctl remove <addr>, bluetoothctl scan bredr, pair again. - A WirePlumber restart leaves a connected device on the headset profile only (the A2DP endpoints are registered after the device reconnected): bluetoothctl disconnect then connect, and the a2dp-sink profile is back. Also seen at connect time (2026-10-11, the WH-CH720N): bluetoothd logs a2dp_select_capabilities() Unable to select SEP and the device offers only headset-head-unit (mono, 16 kHz): the sink is playback_MONO. ravving's output loopback mixes down to it (it once linked only the left channel: a track panned fully to one side went silent); disconnect and connect for stereo. - SBC-XQ is offered, not chosen. With bluez5.enable-sbc-xq = true the WH-CH720N lists a2dp-sink-sbc_xq beside a2dp-sink (plain SBC), but WirePlumber connects with plain SBC. ravving switches it: SETTINGS · BLUETOOTH · SBC-XQ (on by default, AudioOutputs.preferSbcXq) sets the output in use to SBC-XQ when it offers it, or back to plain SBC when off, once per connection (wpctl set-profile <device id> <index>; WirePlumber kept no profile for it). The switch replaces the sink node under the same name; ravving routes to it again (AudioOutputs notices the node id changing). Measured: the WH-CH720N plays SBC-XQ cleanly (2026-10-11).

    One audio device at a time (the LG speaker against the Sony, 2026-10-10)

    The user's report: the Sony WH-CH720N headphones connect every time; the LG speaker is "flaky", and after a night idle it reconnects at once from a phone but not from milo. Read with tools/device.sh bt (journals of 2026-10-08 to 10-10; milo: BlueZ 5.82, PipeWire 1.4.2, WirePlumber 0.5.8).

    The two devices.

    LG SJ1(D8) 6C:5A:B5:49:35:D8 Sony WH-CH720N 84:D3:52:35:80:99
    radio BR/EDR only (not the dual-mode LG S20A of the trap above) BR/EDR + LE
    profiles A2DP sink, AVRCP (no HFP) A2DP sink, AVRCP, HFP, HSP, Sony's own
    codecs (BlueZ's endpoint cache) 01=01:00:00:3fff0241: one sink endpoint, SBC only SBC, AAC (no AAC plugin on Debian: plays SBC)
    record paired, bonded, trusted paired, bonded, trusted
    who connects milo must page it the headphones page milo themselves at power-on

    What happened. Every one of the LG's 11 tries failed; none opened an A2DP transport. Nine went like this, with the Sony connected and playing (since 01:39) the whole time:

    03:48:03 ravving: bluetooth: BLUETOOTH CONNECTED · LG SJ1(D8)
03:48:03 bluetoothd: profiles/audio/a2dp.c:a2dp_select_capabilities() Unable to select SEP
03:48:03 kf.bluezqt: PendingCall Error: "br-connection-create-socket"
03:48:03 ravving: bluetooth: COULD NOT CONNECT · LG SJ1(D8) · br-connection-create-socket
03:48:04 ravving: bluetooth: BLUETOOTH DISCONNECTED · LG SJ1(D8)
03:48:20 ravving: bluetooth: NO AUDIO FROM · LG SJ1(D8)

    (03:48:03, 03:48:08, 03:48:44, 03:49:18, 03:49:21, 03:49:38, 03:49:43, 03:49:55, 03:58:09.) The link comes up, so the speaker answered, but its audio is refused. The other two were page timeouts, where the speaker never answered (off, in standby, or held by the phone):

    2026-10-08 16:00:49 bluetoothd: avdtp_connect_cb() connect to 6C:5A:B5:49:35:D8: Host is down (112)
2026-10-08 16:00:49 ravving: bluetooth: COULD NOT CONNECT · LG SJ1(D8) · br-connection-page-timeout
2026-10-10 03:51:40 (the same)

    ravving tried once each time and gave up. WirePlumber logged nothing for the LG: it never got a transport to make a sink from.

    Why. BlueZ keeps its local A2DP stream endpoints (SEPs) per adapter, shared by every device (a2dp.c: server->seps), and a local SEP carries one stream at a time (avdtp.c: lsep->info.inuse is set by avdtp_set_configuration and cleared only in stream_free; avdtp_find_remote_sep skips an in-use SEP). PipeWire registers one endpoint per codec, and SBC-XQ reuses the SBC one (a2dp-codec-sbc.c: .endpoint_name = "sbc"), so milo has exactly one SBC source endpoint (/MediaEndpoint/A2DPSource/sbc). The Sony streams SBC through it. The LG takes nothing but SBC. So while the Sony plays, BlueZ finds no free SEP for the LG ("Unable to select SEP"), the connection fails with create-socket, and retrying cannot help. The Sony looked reliable because it was the device already holding the endpoint, and because headphones page their last host themselves. A phone has no such conflict because it plays to one audio device at a time and lets the previous one go. The "after a night" case also needs milo to page: a speaker that wakes up pages its last host only, and that was the phone. Configuration cannot give a second SBC endpoint. An AAC plugin would let the Sony use AAC and free SBC, but Debian ships none (libfdk-aac is non-free).

    What ravving does now (src/backend/bluetooth.cpp):

    • Hand-over. When a device answered but could not connect while another audio device is connected, ravving lets the other device go. It shows SWITCHING FROM · the other, disconnects it, waits 1 s for BlueZ to free the endpoint and connects again. The sound falls back to the jacks in between, and PLAY THROUGH then routes to the new device. Only a connection the user asked for does this; ravving's own reconnect never takes the link from a playing device.
    • Pages retried. A page timeout (Host is down) is retried after 2, 5 and 10 s. That is about 37 s with BlueZ's 5.12 s page, and the row reads "waking…". Disconnecting or forgetting the device stops it. Only then does COULD NOT CONNECT appear, with a hint: NOT ANSWERING: OFF, ASLEEP OR WITH A PHONE?
    • PLAY THROUGH waits for the connection. It used to start its 15 s sink poll at the same moment as the connect, so a slow connection ended in NO AUDIO FROM. Now the poll starts once the connection is made.
    • The kept output comes back. AudioOutputs keeps the Bluetooth address of the output picked. When Bluetooth comes on (a start, the switch), that device is connected once, 3 s later, if it is paired and nothing else plays. ravving never repeats this in a loop: paging a speaker in standby wakes it up (LG's Bluetooth standby), so a loop would keep switching on a speaker that went to sleep.

    Device settings proposed (not applied; they need a bluetoothd / WirePlumber restart, which drops the audio). In order of value:

    Applied on milo (2026-10-10): FastConnectable = true in /etc/bluetooth/main.conf (btmgmt info lists fast-connectable), and bluetooth.autoswitch-to-headset-profile = false, now part of data/wireplumber/50-ravving-bluetooth.conf (installed with ravving). The main.conf line is a device setting (BlueZ reads no drop-in folder): set it by hand on a new image.

    1. /etc/bluetooth/main.conf, under [General]: FastConnectable = true. milo then scans for pages more often, so a speaker or headphones paging milo (their last host, waking up) connect within a fraction of a second instead of waiting up to the default 1.28 s scan window. The cost is power, which does not matter on a Pi.
    2. /etc/wireplumber/wireplumber.conf.d/51-ravving-a2dp-only.conf:

    wireplumber.settings = { bluetooth.autoswitch-to-headset-profile = false }

    Today it is true, and WirePlumber exposes bluez_input.<addr> for the Sony: anything that records from it switches the headphones to HFP (mono, 16 kHz) and their A2DP sink goes away. This does nothing for the LG, which has no HFP. It belongs in data/wireplumber/50-ravving-bluetooth.conf once tested. 3. /etc/bluetooth/main.conf, under [BR]: PageTimeout = 16384 (10.24 s against the default 8192 = 5.12 s). Do this only if a capture (device.sh bt capture) shows the speaker answering just after 5.12 s. Each page holds the shared radio for that long. 4. Leave [Policy] ReconnectAttempts / ReconnectIntervals at their defaults (7; 1, 2, 4, 8, 16, 32, 64 s). They act on a link lost by timeout only, not on a speaker that went to standby and disconnected cleanly. JustWorksRepairing does not matter for a bonded device.

    To confirm on milo. With the Sony connected and playing, open BLUETOOTH, tap the LG and press PLAY THROUGH (or device.sh call bluetooth useAsOutput 6C:5A:B5:49:35:D8 true). Expected: SWITCHING FROM · WH-CH720N, the Sony disconnects, then BLUETOOTH CONNECTED · LG, PLAYING THROUGH · LG SJ1(D8), and the journal shows a sep…/fd… ready for dev_6C_5A_B5_49_35_D8. device.sh bt 6C:5A:B5:49:35:D8 -1h should tally an A2DP transport opened. Then switch the LG off (or let it sleep), press PLAY THROUGH again, and switch it on during the "waking…" phase: it should connect on a later page. Finally, with the LG as the output, restart ravving with the Sony off: the LG should come back on its own about 3 s after the start.

    Troubleshooting

    Symptom Look at Likely
    control center: "its service is not running" / bluetooth.state unavailable systemctl status bluetooth → 203/EXEC the bluetoothd path drop-in missing (run the setup)
    the adapter shows but Powered: no after a power on rfkill list (soft blocked), bluetoothctl power on rfkill: rfkill unblock bluetooth
    the link comes up, then COULD NOT CONNECT · br-connection-create-socket and DISCONNECTED a second later journalctl -u bluetooth: Unable to select SEP; device.sh bt ADDR another audio device streams the same codec (SBC): one local endpoint per codec. Disconnect it; ravving hands the link over itself when you connect from the dialog
    COULD NOT CONNECT · br-connection-page-timeout (bluetoothd: Host is down) is the device on, in Bluetooth mode, not connected to a phone? device.sh bt capture while connecting it did not answer the page; ravving pages it again for about 37 s ("waking…"). A speaker that was last used with a phone connects only once milo pages it
    pairs but br-connection-profile-unavailable on connect bluetoothctl show has no Audio Source / Sink WirePlumber's monitor not running: the seat drop-in missing, or WirePlumber started before libspa-0.2-bluetooth was installed (restart it)
    connected, but no bluez_output.* node in wpctl status journalctl --user -u wireplumber the device connected HFP only, or the A2DP transport failed: disconnect and connect again
    PLAYING THROUGH says so but nothing is heard pgrep -af pw-loopback, pw-link -l \| grep -A1 ravving-phaser:out_l (should show ravving-out:playback_FL), pw-top (the bluez sink R, the HiFiBerry S) the loopback did not start (pipewire-bin missing?) or its links failed: pick the jacks and the device again; the journal has "master linked to ravving-out" when it worked
    sound from the device and the Bluetooth device pw-jack jack_lsp -c system:playback_1 the speaker links were not dropped: pick the jacks and the device again
    glitchy sound over Bluetooth pw-top: is the bluez sink the driver of ravving's nodes? the default sink was switched by hand (wpctl set-default): put the jacks back as default, ravving routes through the loopback instead; Wi-Fi on the same antenna also costs (the Pi's radio is shared)
    sending fails at once: "COULD NOT REACH" busctl --user list \| grep obex, systemctl --user status obex obexd missing or not activatable; the phone must have OBEX push enabled (Android: accept the incoming file prompt)
    a phone cannot see milo bluetoothctl show → Discoverable: no VISIBLE lasts three minutes; press it again
