    Bluetooth

    Devices, pairing, file transfer and audio output over BlueZ and PipeWire.

    How ravving uses BlueZ and PipeWire for Bluetooth: devices, pairing, file transfer and audio output. The classes are in the API reference; the system setup is on Running on a Zynthbox.

    Ravving's Bluetooth does what a phone's does: pair, connect, send a file, play through a speaker or headphones, receive a file. What a Zynthbox needs for it is in packaging.md ("Bluetooth on a fresh device"), the tests in testing.md and the troubleshooting table in debugging.md.

    • Backend Bluetooth (src/backend/bluetooth.*, QML bluetooth), on BluezQt: the adapter (power, discovery, discoverable for three minutes), the devices (connected first, then paired, then by signal; private-address phones without a name hidden until paired), a pairing Agent (DisplayYesNo: a passkey to confirm or a PIN to type lands in pairing, answered with answerPairing), pair → trust → connect, forget, OBEX Object Push sending (sendFile, progress in transfer), an ObexAgent accepting pushes into the library's incoming/ folder, and the audio switch (useAsOutput).
    • Discovery. The Pi has one radio for Bluetooth and Wi-Fi, and an inquiry breaks up a playing A2DP link, so a scan lasts 12 s (DiscoverySeconds) and starts on its own only while no audio device is connected. It scans classic devices only (setDiscoveryFilter {Transport: bredr}): a dual-mode speaker paired from its LE advertisement gets no A2DP sink, and the Pi's firmware has no LE Audio.
    • Audio. When an audio device connects, WirePlumber makes a sink node bluez_output.<address>.1 (and an input / capture node for HFP). useAsOutput hands it to AudioOutputs (outputs, also the control center's AUDIO OUTPUT card), which does not make it the default sink: that would clock the whole JACK graph by the Bluetooth transport in 256-frame chunks (glitches) and leave the master's links to the jacks in place (sound from both). Instead the jacks keep the clock, a pw-loopback of ravving's own (ravving-out, a virtual sink whose playback stream targets the Bluetooth sink with a 2048-frame buffer) is started, the master's two output ports are linked to it with pw-link (its inputs have no JACK name, so libzynthbox's JackConnectionHandler cannot) and the jacks are muted, not unlinked: an unlinked jacks sink is suspended and the Bluetooth transport would become the graph's clock. Off, on disconnect, forget or exit, the loopback stops and the jack links come back. A device connected on the headset profile only (playback_MONO) gets a mono mix-down.
    • The codec. PipeWire offers a2dp-sink-sbc_xq beside plain SBC (ravving's WirePlumber drop-in sets bluez5.enable-sbc-xq) but WirePlumber connects with plain SBC. SETTINGS · BLUETOOTH · SBC-XQ (AudioOutputs.preferSbcXq, on by default) switches the output in use to SBC-XQ when it offers it, or back to plain SBC, once per connection (wpctl set-profile); each paired device can override it with its own chip in the BLUETOOTH dialog (AudioOutputs.sbcXqByDevice, setSbcXqFor()), since a device may advertise the bitpool and still not sustain it. A codec switch replaces the sink node under the same name: AudioOutputs notices the node id changing and routes to the new one; a Bluetooth output gets its codec first and is routed to once its new sink is there.
    • The silence watch. While another output plays, OutputWatch listens to what goes into the loopback and what comes out: music going in with silence coming out for six seconds is routed again once (a fresh loopback), and if it is still silent the issues center says the output plays no sound.
    • One audio device at a time. BlueZ keeps one local A2DP endpoint per codec, shared by every device, and a local endpoint carries one stream; PipeWire registers one SBC source (SBC-XQ reuses it). So while one device streams SBC, a second SBC device cannot set up its audio (Unable to select SEP, br-connection-create-socket). When a device the user is connecting answered but could not connect while another audio device is connected, ravving shows SWITCHING FROM · the other, disconnects it, waits 1 s for BlueZ to free the endpoint and connects again; ravving's own reconnect never takes the link from a playing device.
    • Pages retried. A page timeout (Host is down) is retried after 2, 5 and 10 s (about 37 s with BlueZ's 5.12 s page; the row reads "waking…"; disconnecting or forgetting stops it) before COULD NOT CONNECT with the hint NOT ANSWERING: FREE IT FROM A PHONE, OR TURN IT OFF AND ON. PLAY THROUGH's sink poll (15 s) starts once the connection is made.
    • The kept output comes back. AudioOutputs keeps the Bluetooth address of the output picked. When Bluetooth comes on (a start, the switch), that device is connected once, 3 s later, if it is paired and nothing else plays. Never in a loop: paging a speaker in standby wakes it up.
    • Files. Sending opens an OBEX session (Target: opp) and pushes the file; receiving needs the device VISIBLE (discoverable + pairable, three minutes) and lands under library/incoming/, which PROJECT ▾ → IMPORT lists as "received" and the music library as the album "Received".
    • UI. BluetoothPopup from the control center's BLUETOOTH card.
