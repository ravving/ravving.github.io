    Architecture

    The layers, the hardware input flow and the focus model, the libzynthbox bridge, files, the theme.

    Layers

     ┌──────────────── QML (qml/: the Ravving module, compiled in) ────────┐
 │ Main.qml: RaveHeader + StackLayout of the five pages + MENU drawer   │
 │ pages/:   DrumsPage ChordsPage BassPage LeadPage SamplerPage         │
 │ components/: the shared parts every page is built from               │
 └───────────────▲──────────────────────────────▲──────────────────────┘
                 │ context properties           │ Zynthbox QQC style (SVG theme)
 ┌───────────────┴──────── C++ app (src/) ──────┴──────────────────────┐
 │ Ravving         page state, hardware → HardwareEvent   "ravving"    │
 │ Hardware        the `Hardware.on…` attached property  import Ravving│
 │ StyleHost       what the Zynthbox style needs          "zynqtgui"   │
 │ ZynthboxBridge  loads libzyncoder + libzynthbox        "zynthbox"   │
 │ HardwareSwitches  polls the buttons → MidiRouter's CUIA queue        │
 │ HardwareKnobs   polls the 4 knobs (turns / pot positions)            │
 │ UnixSignals     SIGTERM → LEDs off, then _exit (as zynthbox-qml)     │
 └───────────────▲─────────────────────────────────────────────────────┘
                 │ dlopen + meta-object calls (headers are not installed yet)
 ┌───────────────┴──────────── libraries ──────────────────────────────┐
 │ libzynthbox (sequencer, sampler, mixer, MIDI router, engines)        │
 │ libzyncoder (buttons, knobs) · qml-style-zynthbox · KF6 Kirigami     │
 └─────────────────────────────────────────────────────────────────────┘

    Rule: ravving runs no Python. When it needs something zynthbox-qml does in Python, that piece is ported to C++ under src/, and the class doc names the Python it came from.

    Input flow: the Hardware attached property

    The device's keys and knobs reach QML the way the keyboard does through Keys: as events delivered to the item with active focus, bubbling to its parents until a handler accepts them.

    device button ─► HardwareSwitches (zyncoder poll, 20 ms)
                   └► MidiRouter.enqueueCuiaCommand("SWITCH_STEP3_RELEASED")
MIDI-mapped CUIA ─► MidiRouter ─► cuiaEvent ─► ZynthboxBridge ─► Ravving::handleCuia ─┐
device knob ─► HardwareKnobs (zynpot poll) ─► Ravving::handleKnobTurn / handleKnobMove ─┤
keyboard (dev) ─► Main.qml Shortcuts ─► ravving.simulateCuia / simulateKnob ────────────┤
                                                                                         ▼
                        HardwareEvent ─► Hardware::dispatch(window): activeFocusItem,
                                          then each parent, until one accepts it

    import Ravving
FocusScope {
    Hardware.onKnob1Up: event => level += event.delta        // knob 1 clockwise
    Hardware.onBigKnobDown: event => select(index - 1)
    Hardware.onKnob2Moved: event => cutoff = event.value     // Z2_V5B fixed pot, 0..1
    Hardware.onStepPressed: event => grid.toggle(event.index)
    Hardware.onUpPressed: event => { if (atTop) event.accepted = false }  // bubble on
}

    Signals: knob1Up/Down … knob3Up/Down, bigKnobUp/Down, knob1Moved … knob3Moved, generic knobTurned / knobMoved, up/down/left/right/select/back/menu/play/stop/record/metronome Pressed, stepPressed (index 0–15), numberPressed (index 0–4), and pressed for anything else. As with Keys, the specific signal goes first and the generic one gets whatever is still not accepted. A handler that runs accepts the event unless it sets event.accepted = false.

    Focus model: - The open page (a RavePage, i.e. a FocusScope) has the focus. ▲ at a page's top edge is left unaccepted, bubbles to Main.qml, and focuses the header's first group. - In the header, ◀ ▶ move between the KnobGroups and ▼ / BACK return to the page. Step keys always go to the page. A number key nobody handles still switches the page (C++ fallback). - A KnobGroup (FocusScope) hands its targets to the knobs: knob n → targets[n], the big knob → targets[3] or fine steps on targets[0]. It can also hold navItems, which its navKnob (the big knob by default; knob 1 for INSTRUMENTS) steps through and SELECT activates. Targets show a KnobBadge (a tiny knob icon: the knob number, value arc, pulsing while a Z2_V5B pot waits for pick-up). - Inside a page the big knob is always the volume of the machine on screen (RavePage.module, MachineModule.nudgeLevel()); the fader wears the big-knob badge while it is. Groups in a page (ParamCard, the machine strip) set ownsBigKnob: false so it passes through to the page. Popups and the header, outside the page, keep using it. - A machine's strip (role, PAN knob, VOL RaveFader) is a KnobGroup: tap it and knob 1 pans, knob 2 sets the level; BACK or a tap in the grid give the knobs back to the rows (StepGrid.knobsActive is off while the strip has them). - ▲ ▼ walk one vertical order per machine, owned by MachineModule: header → strip → SOUND MODIFIERS cards (only while open) → the editor → SOUND EFFECTS cards (only while open). The sections move the focus themselves (ParamCardRow.released(dy), coming back to the card last used with enter()); a page calls focusUp() / focusDown() when its editor has no further to go (the drums: past the top row / the ACC row; the bass roll: past its top / bottom note row). focusUp() returns false from the strip, so ▲ bubbles to the header; ▼ from the header lands on the page's focusTop() (the strip). - RECORD on an instrument page is that machine's take (the strip's ● shows ● / count-in beat / … / ■); RECORD with the header focused, or ALT + RECORD anywhere, is the global recording (the header's ●, red RECORD LED). - The metronome is libzynthbox's (SyncTimer audibleMetronome) with zynthbox-qml's tick/tock wavs: ZynthboxBridge::setMetronomeSounds() builds the two ClipAudioSources through the exported constructor (no meta-object factory exists) and SamplerSynth's global-sketch1 outputs are wired to the master. - An external MIDI controller plays the machine on screen (on every page; LIVE, which may be left on another machine, is the step keys' only) through the same path as the step keys, so REC records it: GM drum notes 35–59 by role (DrumKit::roleForGmNote), any other note cycling through the rows from C2, velocity ≥ 100 an accent. Plugging one in or out shows a Toast (a dark pill, bottom centre). Debug: QT_LOGGING_RULES="ravving.midi.debug=true". - The key lights (Main.qml's ledColors): ▲ ▼ SELECT BACK ALT MENU always light in a soft white (navigationLight; ALT white while held, MENU while the menu is open); ◀ ▶ light while they switch something on the open page (RavePage.sideKeysLit: the CHORDS views with the editor focused, the drum machines, the sampler banks); PLAY dim green when stopped, bright while playing; STOP dim when stopped, lit while playing; RECORD dim red when ready, red while recording (global or a sampler take), a machine's colour during its take. - ALT + ◀ / ▶ undo and redo the pattern of the machine on screen (the toolbar's ↶ ↷). - ALT + ▲ gives the focus to the app header at once, from wherever it is (a page's rows, a section's cards, the strip): Ravving.headerRequested, raised in C++ before any dispatch. - ALT + 1 opens the SONG page from anywhere, and again goes back to the page (Ravving.songRequested, raised in C++ before any dispatch, its press swallowed too). - The header's INSTRUMENTS chips light the machine on screen only: none while the MIXER, the SONG page, the music player or the RECORDER covers the pages (Session.pageCovered). - AUTO: the header's AUTO arms recording (Studio.recordAutomation): while playing, a SOUND MODIFIERS or SOUND EFFECTS knob turned is written into its machine's pattern at the step playing (Machine automation lanes, step → value, undoable, saved); the toolbar's AUTO plays them back (lit, "•" while there are some; a long press clears them). - SOUND EFFECTS cards (open): SELECT switches the focused card's effect on or off, BACK closes the section and the focus goes back to the editor above (ParamCardRow.selectAndBack). Closed, ▼ past the editor lands on the bar (FxChain.focusBar()): ◀ ▶ ring the chips, SELECT switches the ringed effect, ▼ opens the section on its card, ▲ / BACK go back up. A tap on the ▸ SOUND EFFECTS heading opens it on the effect last touched (the heading is the one way in by touch; the bar has no OPEN button). - Dialogs (RavePopup: ChoicePopup, InputPopup), drop-down lists and the menu darken the page behind them (ModalDim); a dialog takes the keys while open and gives the focus back. Dialogs wear one card look (gradient #1e1c24 → #131118, hairline border, radius 16, DialogHeader: spaced title, hint, ✕); the menu drawer is a settings panel (gradient #211f28 → #16141c, hairline-split sections under small captions, flat wells that light yellow, #f0c832). - MENU opens the control center (ControlCenter in the drawer): MIXER, Wi-Fi, Bluetooth, MIDI, SYSTEM cards, the power row (REBOOT and POWER OFF need a second press within 3 s), OUTPUT and BRIGHTNESS sliders on knobs 2 and 1; ◀ ▶ walk the actions, SELECT runs one. - ✱ (starPressed) opens and closes the MIXER (MixerPage, the StackLayout's sixth view, Main.mixerOpen); a number key leaves it for that page. In it ◀ ▶ or step keys 1–9 pick a strip, knob 1 is its level, knob 2 its pan, the big knob fine level, SELECT mutes, ALT + SELECT solos, BACK or ✱ go back; the step LEDs show the strips (muted dim, picked white). - MODE switches LIVE on the open page's instrument (from anywhere; the MODE LED shows it). ALT is a modifier held in C++ (Ravving.altHeld): ALT + big knob is the master volume wherever the focus is (masterTurned, never dispatched), badged on the MASTER dial, and ALT + knobs 1–3 go straight to Ravving.altKnobTarget (the header's FX SENDS: PHASER, ECHO, HEAVY), a KnobGroup borrowed while ALT is held (badges, frame, pick-up). - A machine's ❚❚ pauses its written pattern (DrumMachine.paused → Sketchpad.setTrackPaused: its clip stops in PlayfieldManager and is left out of the launch at play; resuming rejoins on the next bar); it stays playable live. - LIVE (one machine at a time, Session.liveMachine) turns the step keys into pads (Hardware.onStepDown on the press, onStepPressed on the release): on the drums keys 1–8 play the rows and key 9 held makes accents; with REC on while playing a hit is written at the nearest step (Machine::recordLive, timed against the measured step length), in STEP entry while stopped at the cursor (writeAtCursor). With the toolbar's Q off (Machine.quantise) the hit keeps its distance from that step as the subnote's delay (SyncTimer ticks, negative when early), so it plays back as played; the machine keeps these offsets itself (timing in its state) and puts them back whenever its model rewrites the pattern (syncTiming). The LEDs show the pads (rows in the machine's colour, key 9 red, white while held) and drop the playhead (RavePage.stepKeysArePads). libzynthbox's own live recorder is not used: it only hears controller ports, and pads sent through SyncTimer arrive as sequencer traffic. - The toolbar's ⟲ (Machine.loopBar) plays only the bar on screen: the pattern's playback window moves to it (bankOffset = that bar, patternLength = one bar) while bars keeps the real length, and paging with ‹ › moves the loop. Not saved; attach and restore put the window back.

    The libzynthbox bridge

    libzynthbox doesn't install headers, and its headers pull in all of JUCE. So ZynthboxBridge:

    1. dlopens libzyncoder.so and calls init_zynlib(). libzynthbox needs zyncoder's MIDI router first, the same order as zynthbox-qml.
    2. dlopens libzynthbox.so and resolves three symbols: Plugin::instance(), Plugin::initialize() and Plugin::registerTypes().
    3. Gets the MidiRouter QML singleton and connects to cuiaEvent through the meta-object system.

    Both libraries are opened with RTLD_LOCAL. RTLD_GLOBAL lets libzynthbox's bundled JUCE/tracktion symbols interpose on libraries loaded later, and the app crashes in Kirigami's platform-plugin lookup.

    Distribution

    ravving ships as a Store AppImage that bundles ravving, the data and ravving-setup (setup/), the page the AppImage opens over zynthbox-qml to install ravving and pick the UI the device runs; both lean on tools/default-app.sh. See packaging.md.

    The theme

    ravving wears one theme, set in code: RAVVING_THEME in the top-level CMakeLists.txt names the folder under data/plasma/desktoptheme/ that ships with the app (ravving-theme: the Miko theme). The app makes its bundled config/plasmarc its only plasmarc, so neither zynthbox-qml's theme chooser (~/.config/plasmarc) nor any user file can change it; the journal line ravving: theme … says what a run wears. To change the look, change the theme folder or RAVVING_THEME, and rebuild.

    Where ravving keeps its files

    Nothing of ravving's goes into zynthbox-qml's folders, and nothing of zynthbox-qml's is written: ravving reads the device's sample library and writes only to its own places (src/backend/paths.h), following the XDG base directories:

    Root On the device What
    config ~/.config/ravving settings (the input set-up, the UI's choices)
    state ~/.local/state/ravving the live session (session.json, the sequence); removed by a purge
    cache ~/.cache/ravving rebuildable: reversed samples, raw takes, the LV2 port cache
    library /zynthian/zynthian-my-data/ravving the user's work, kept across reinstalls: projects/, presets/, samples/ (takes in samples/takes/, the RECORDER's in samples/recordings/, imported bundles' samples in samples/imported/), recordings/ (the master's and the RECORDER's TRACKS), exports/

    On a desktop the library is ~/.local/share/ravving. Files of an older layout are moved into this one at start (Paths::initialise()), and the session's and projects' sample paths with them.

    The startup splash

    StartupSplash (qml/Splash.qml and SplashLook.qml) shows the logo from the moment libzynthbox is up until the page is ready, then plays a short show into the page. MENU → SETTINGS → STARTUP picks the look, from the next start: ANIME, GLOW, STILL, ZOOM or OFF. While the studio loads the splash is a still picture, since a moving one keeps the screen redrawn every frame and slows the start; the show plays in the page's own window (kwin keeps a full-screen window above a "stay on top" one). The logos are the effect SVGs drawn without their backgrounds (data/branding/make-splash.sh); the album art's wordmark is data/branding/ravving-wordmark.svg.

    The phone share and the help page

    FileShare (share) is ravving's one-file HTTP server, on port 8098 or the next free one: SEND… → PHONE · QR CODE offers one file at a path of 128 random bits for as long as the dialog is open, 15 minutes at most; FILES → PHONE · BROWSE serves the library as pages (FileShare.openBrowse, a random path that lives until 15 minutes pass with no request); the same server carries the webpage (site/, installed as share/ravving/site) at http://<device>:8098/help/, which SETTINGS → HELP shows as a QR code (get share helpUrl). Over the fifo: call share offer /path/file, get share url, get share status, get share browseUrl, call share stop; tools/share-test.sh checks it from the laptop (testing.md).
