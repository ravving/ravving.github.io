    Quality

    Static analysis, startup timing, QML profiling, the screenshot tour, what the rest costs the sound.

    The checks to run on ravving every so often (and before a release) and what each tool is for. All the tools live in tools/; the laptop ones need no libzynthbox (ravving builds without it), the device ones run against root@milo.local (DEVICE= for another).

    When Run Look at
    after C++ changes tools/static-analysis.sh new lines in analysis/summary.txt against the accepted findings (§1)
    after changes to a shell script (tools/*.sh, data/start.sh) tools/static-analysis.sh shell (ShellCheck, here or on the device) analysis/shellcheck.log: the scripts are kept at zero findings; a finding that is the script's intent (a remote command built on the laptop, a deliberate word split) gets a # shellcheck disable= line with the reason above it
    after adding a pointer handler (Tap / Drag / Pinch / Point / Wheel) to a page or the header tools/static-analysis.sh handlers zero: each binds enabled: … !Session.inputBlocked, else a drag on a dialog reaches it (§1, "Handlers under dialogs")
    after QML changes the screenshot tour (§4) QML warnings in its output; pixel diffs against a reference tour
    after anything that touches startup tools/boot-timing.sh restart 5 the medians against the previous run's
    before a release tools/boot-timing.sh reboot 3, tools/qml-profile.sh boot to first frame; what QML creates before it
    after any UI, animation, poll or watcher change, and in every phase pass tools/audio-impact.sh (§9) idle 0 frames/s; playing ≈ the playhead and meter rates; 0 RT-thread faults from ravving's own code; 0 xruns

    1. Static analysis: clang-tidy and clazy

    tools/static-analysis.sh            # both; or `tidy` / `clazy` alone

    It configures a separate build folder with a compile database (BUILD, default /tmp/ravving-analysis; the normal build/ is never touched), generates moc and the QML type registration, then runs clang-tidy with the repo's .clang-tidy and clazy (levels 0–2 without the Qt-idiom noise listed in the script) over src/ only, in parallel. Reports go to REPORTS (default ./analysis): clang-tidy.log, clazy.log and summary.txt, one count per check. Arch packages: clang (clang-tidy, run-clang-tidy) and clazy. A newer clang-tidy brings new checks: decide for each whether it finds something or restates the house style, and turn the latter off in .clang-tidy with a line saying why.

    ShellCheck

    tools/static-analysis.sh shell runs ShellCheck 0.10 at -S style over every shell script; the baseline is 0. ShellCheck is on the device (apt install shellcheck); on a laptop without it the script sends the files there.

    Handlers under dialogs

    The modal dimmer stops items, not pointer handlers: Qt Quick still hands a press to every handler under it after the dialog's button or field took it, and a page's DragHandler then takes the drag over past its threshold. Disabling the page while a dialog is up is no way out (a disabled ComboBox closes its own list at once). So the modal layers (dialogs, the MENU drawer, a drop-down's list) register in Session.overlays by identity (a repeated open cannot leave the page blocked), and every handler on a page or the header binds enabled: !Session.inputBlocked. tools/check-handlers.py (static-analysis.sh handlers, also in all) fails on a new one that does not.

    The accepted findings

    What is left is known and accepted; anything not in this list is new and worth reading.

    Check Count Why it stays
    bugprone-implicit-widening-of-multiplication-result 12 soundfont record offsets (index * Size) and the track lanes: int-sized files and lists
    bugprone-signed-bitwise 11 MIDI status / channel and LED colour byte masks on int; values are 0..255
    bugprone-incorrect-roundings 3 int(x + 0.5) on frame counts, which are never negative
    bugprone-multi-level-implicit-pointer-conversion 2 jack_free(ports) and QMetaObject's void * arguments: the C APIs' own types
    bugprone-inc-dec-in-conditions 1 m_editGroup > 0 && --m_editGroup == 0: the decrement is meant to be guarded
    readability-redundant-nested-if 1 LiveFx: the two conditions read as two decisions
    clang-analyzer-cplusplus.NewDeleteLeaks 1 false: the QFutureWatcher is parented to the machine and deleteLater()s itself
    clazy range-loop-detach 24 loops over temporaries (toList(), split()) on load paths; a member list looped often would be worth fixing (DrumKit::rows() was)
    clazy writing-to-temporary 2 QSettings(...).setValue(): the temporary's destructor writes it
    clazy connect-non-signal 2 clazy cannot follow a for over signal pointers (Studio); its own message calls it a clazy bug
    clazy qproperty-without-notify 1 HardwareEvent::accepted: a per-event object, never bound

    2. Startup time

    main() writes the phases of a start to the journal (src/startuptimer.h):

    ravving: startup main 0 ms           process up (after startx, X and the binary loading)
ravving: startup application 18 ms   QGuiApplication
ravving: startup libzynthbox 649 ms  libzynthbox's singletons and engines
ravving: startup studio 2922 ms      machines, effects, the session (Studio)
ravving: startup qml 3681 ms         Main.qml created
ravving: startup first-frame …       the first frame on screen
ravving: startup wired …             audio and MIDI connected

    tools/boot-timing.sh restart 5      # service restarts: CSV + medians, ms from the service starting
tools/boot-timing.sh reboot 3       # reboots (ravving the default UI): also kernel boot → first frame
tools/boot-timing.sh last           # the last start, without restarting anything

    Compare medians, never single runs: the first frame moves by up to 3 s between runs because kwin starts beside ravving (start.sh) and the window is not shown before kwin manages it.

    The start depends on the page the session restores, since only the page on screen is built first: DRUMS is the heaviest (all three drum machines' step grids), BASS a typical one. Compare runs on the same restored page ("page" in the session.json: 0 drums … 4 sampler), and before blaming a change for a slower start, compare against an old build (a git worktree, deployed) on the same day, project and page: the device's state moves the times too.

    Restart sparingly. Every restart stops and starts the HiFiBerry's PCM, and after a few dozen in a session the Pi's RP1 audio DMA driver can oops (the device reboots itself). Prefer 3–5 runs per measurement, and take boot-timing.sh last after a start that happens anyway.

    Deploy with checksums. rsync -a keeps the laptop's modification times, so a file edited before the device last built another tree arrives older than that build's objects and ninja skips it. tools/device.sh deploy syncs with rsync -rlp --checksum; after switching trees by hand, find src qml -exec touch {} + on the device before building.

    What keeps the start short: 1. Only the page on screen is built before the first frame (Main.qml's PageLoader): the other four pages and the mixer are built one per 40 ms tick once the first frame is up. main.cpp restores the page before loading the QML, so the first page built is the right one. 2. KnobBadge builds its drawing on first show (shown, not visible): most badges stay hidden. 3. The LV2 ports are cached on disk (JalvPlugin::readPorts, ~/.cache/ravving/lv2-ports.json) instead of lv2info running for each plugin built at start. Each entry carries its bundle's and binary's modification times; an installed or upgraded plugin does not match and is asked again. Delete the file to force a full re-read. 4. Imported soundfonts cost next to nothing: only each font's preset list ("pdta") is read, found by walking the RIFF chunk headers (SoundFontFile::presetData, which steps over an unpadded odd-sized chunk too). The journal says what it cost: ravving: kits N ms, imported soundfonts: F fonts, S sources, M ms (also after a USB import, refreshImported); that line is the check after adding a font whose writer is new.

    3. QML profiling

    tools/qml-profile.sh NAME           # ./NAME.qtd and ./NAME-summary.txt
tools/qml-profile-summary.py NAME.qtd --type Creating --top 40
tools/qml-profile-summary.py NAME.qtd --from 2 --to 4

    A systemd drop-in sets RAVVING_QML_DEBUG=10002,block: main.cpp opens the QML debug server and waits for qmlprofiler before loading any QML; the script attaches on the device, waits for startup wired, flushes the trace, then removes the drop-in and restarts ravving. The summary lists self time per event type, per file and per event: look at Creating first (how many of what were built) and the call counts (1436 calls of one component is the finding, not its 0.1 ms each). Never probe the debug port by connecting to it: the server takes the first connection as its client.

    4. Visual checks: the screenshot tour

    RAVVING_STYLE=Basic QT_QPA_PLATFORM=offscreen QT_FORCE_STDERR_LOGGING=1 RAVVING_NO_ZYNTHBOX=1 \
RAVVING_DATA_DIR=$PWD/data RAVVING_PROJECT_DIR=/tmp/tour/project RAVVING_SCREENSHOT_DIR=/tmp/tour/shots \
    build/ravving 2>&1 | grep -v -i jack

    It visits every page and a few dialogs, saves PNGs and quits (main.cpp). Start from an empty project folder each time (the tour turns knobs, and the session keeps them), build the reference from the previous commit the same way, and compare with compare -metric AE ref.png new.png null: (ImageMagick). QT_FORCE_STDERR_LOGGING matters: without a terminal Qt logs to the journal and the run looks silent. The Zynthbox style is not on the laptop, hence RAVVING_STYLE=Basic.

    5. Making ravving the device's UI

    tools/device.sh default ravving       # or on the device: /usr/share/ravving/default-app.sh ravving
tools/device.sh default status
tools/device.sh default zynthbox      # back to stock; add --purge to uninstall ravving too

    default-app.sh masks zynthbox-qml in root's user units (a --user disable cannot undo its global enable in /etc/systemd/user, and updates re-enable it globally; the mask wins over both) and enables ravving. Going back unmasks and starts zynthbox-qml, disables and resets ravving, and drops the development environment (RAVVING_GDB, RAVVING_QML_DIR).

    6. The Store AppImage: the release check

    tools/appimage-test.sh builds the AppImage on the device, installs it the way the Store does and walks every choice of the setup page and ravving's ZYNTHBOX button by touch, with an assertion on the device's state after each step. Run it after a version bump or any change to setup/, tools/default-app.sh, data/ravving.service or packaging/. About eight minutes; results in analysis/appimage-test-<date>/. Details in packaging.md.

    7. Soundfonts and engines: when one is added

    sh tools/soundfont-check.sh (on the device, from the laptop) takes every soundfont data/kits.json names (the drum kits, the machines' default engines, every FluidSynth sound source) and checks each: the file exists, its zones can sound (a font whose instrument zones declare a velocity range of 0–0 is mute at any velocity: SynStrings, LaString, MelloString and Organ.sf3 on the image are such, and are left out), the preset the entry asks for (bank:program) exists in the font, and a chord rendered through fluidsynth offline on that preset (a kick, snare and hat for a kit, low notes for a bass, three seconds for pads that swell slowly) actually comes out. PASS / FAIL per font, exit status = failures. Run it after editing the sources in kits.json, after an image update (the fonts live in /zynthian/zynthian-data/soundfonts), and before a release.

    Behind it, tools/soundfont.py (presets · ranges · render · categorise) looks inside one font and proposes kits.json entries for new ones (categorise --json), and tools/mididump.py shows what an engine's JACK MIDI port really carries, for a source that stays silent in ravving but sounds offline (testing.md). A new engine type (a SoundEngine subclass) gets the same treatment: its sources into kits.json, the check run, and a pw-top look at its nodes' rate and quantum against the graph's (48000 / 256 on the device).

    pipewire-pulse and the music player

    ravving's music player needs pipewire-pulse (Qt's audio output on Linux is PulseAudio), so the unit wants it. Its stream runs at its own adapted quantum and leaves the graph at 256 / 48000; the graph's rate is pinned (clock.allowed-rates = [ 48000 ]), so a 44.1 kHz file cannot switch it. After a PipeWire update, check with pw-top -b -n 2: idle, with an MP3 playing, and with the MP3 plus the transport, the driver must stay at 256 / 48000 with its xrun count unchanged.

    8. The audio graph: routing, clocks and xruns

    When an engine, insert or route is added or changed, and in every phase pass:

    tools/device.sh graph all -s 60      # rates, idle-but-linked nodes, threads, xruns over 60 s, the links

    Expected on a Zynthbox: the driver is the sound card's playback node at 48000 / 256; every ravving-* audio node at 48000 with a period of 256 (jalv) or 512 (FluidSynth's stream, by design); no node with links that is not running; 0 xruns in 60 s, idle and with the reference project playing (run it twice, once with device.sh cuia SWITCH_PLAY_RELEASED first). Any steady xrun rate means a stall somewhere: the first thing to check is systemctl --user show-environment for RAVVING_GDB=1 (gdb costs 20–40 a minute), then graph-check.py threads for a render thread without realtime priority or one above PipeWire's data loops. What each column means, the tools behind it and the numbers PipeWire's data loops. What each column means and the tools behind it are in routing.md.

    9. What the rest costs the sound

    The sound comes first on this device: a feature, a poll, a watcher or an animation may not cost the audio anything it can hear. ravving's audio threads run at realtime priority, so other work cannot preempt them directly; what it can do is load the CPUs and the memory bus they share, stall a cycle with a page fault on a realtime thread, or hold a lock the audio side needs. Measure it, before and after:

    tools/audio-impact.sh               # 30 s idle, then 30 s with the transport playing
tools/audio-impact.sh 20 idle       # only the idle window (no keys pressed: safe while someone plays)
tools/device.sh animations          # what keeps the window drawing, item by item

    audio-impact.sh prints, per state: the frames per second the window put on screen (Ravving.framesSwapped, counted on the render thread), CPU in % of one core for the render thread, the GUI thread, ravving's realtime threads (policy FIFO / RR: the JACK clients, SyncTimer, MidiRouter…) and the rest, the page faults the realtime threads took, and the graph's xruns over the window (graph-check.py xruns, summed over the nodes: one graph-wide dropout counts once per node). playing presses PLAY and STOP: never run it while someone plays; idle only reads.

    What healthy looks like (a Pi 5, a full project):

    idle playing
    frames/s 0 16 (the 16ths' playhead and the 10 Hz meters)
    render / GUI thread 0 % / 3 % about 13 % / 10–15 %
    realtime threads about 14 % about 20 %
    RT page faults / 20 s 0–2 (PipeWire's own data loops) some in libzynthbox's SyncTimerThread, none in ravving's code
    xruns 0 0

    The rules

    • An idle screen draws nothing. Before shipping UI work, tools/audio-impact.sh 20 idle must read 0 frames/s; if not, device.sh animations names the item.
    • No Animator (Opacity/Scale/Rotation/XAnimator…) inside a Behavior: use NumberAnimation. No Behavior on something the transport changes at every step or every meter reading: those values change instantly.
    • Anything fed by the audio side (positions, levels) is published at the rate the eye needs (15 Hz for a moving line, 10 Hz for meters), never per audio block.
    • An infinite animation (loops: Animation.Infinite) runs only while its state lasts (a take waiting, a latched pad) and only while its item is shown.
    • A grid, a play position or a progress reads the step playing only while visible: the hidden pages stay built in their StackLayout and must not follow the playhead.
    • A poll that forks or blocks runs only while what it feeds is on screen, unless it watches for something that has to be noticed at once (a USB stick); measure it with this tool.

    10. List models

    Views fed a plain list (a QVariantList from the backend, a JS array) rebuild every delegate whenever the list is set again; on the Pi a row with a Zynthbox Button costs ~1.4 ms to make (five SVG frames). The long or often-updated lists go through KeyedListModel (src/, tests in tests/: cmake -DRAVVING_TESTS=ON build && ctest --test-dir build): a new list is applied as the fewest row changes, matched by a key; the longest also set reuseItems. Its roles only grow (a reset would rebuild everything), and a test keeps it so. Use KeyedListModel for any list that is long or updated often; small fixed lists (the banks, the kinds) stay plain. AFTER=script tools/qml-profile.sh profiles an interaction instead of a start.

    11. Phase passes

    Every phase of a feature ends with this pass, run with ravving under gdb on the device (systemctl --user set-environment RAVVING_GDB=1, then a restart: start.sh prints a backtrace to the journal on a crash) while the suites run, and gdb off again for the timing rows:

    Check How
    clang-tidy / clazy tools/static-analysis.sh: back to the accepted findings (§1)
    start-up (gdb off) tools/boot-timing.sh restart 3: the medians against the last pass
    QML profile tools/qml-profile.sh NAME: what the phase adds to Creating
    screenshot tour §4: every shot, no QML errors
    feature suites (gdb on) the page's suite and any the change touches (testing.md)
    what it costs the sound tools/audio-impact.sh (§9)
    valgrind memcheck on the offscreen tour (laptop) with --leak-check=no; read only the frames that name ravving (Qt's aeshash128 and forkfd reports are known false positives); it takes about 25 min
