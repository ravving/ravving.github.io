Quality

Static analysis, startup timing, QML profiling, the baselines.

The checks to run on ravving every so often (and before a release), what each tool is for, what the last run found, and the traps met on the way. All the tools live in tools/; the laptop ones need no libzynthbox (ravving builds without it), the device ones run against root@milo.local (DEVICE= for another).

When Run Look at
after C++ changes tools/static-analysis.sh new lines in analysis/summary.txt against the baseline below
after changes to a shell script (tools/*.sh, data/start.sh) tools/static-analysis.sh shell (ShellCheck, here or on the device) analysis/shellcheck.log: the scripts are kept at zero findings; a finding that is the script's intent (a remote command built on the laptop, a deliberate word split) gets a # shellcheck disable= line with the reason above it
after adding a pointer handler (Tap / Drag / Pinch / Point / Wheel) to a page or the header tools/static-analysis.sh handlers zero: each binds enabled: … !Session.inputBlocked, else a drag on a dialog reaches it (§1, "Handlers under dialogs")
after QML changes the screenshot tour (below) QML warnings in its output; pixel diffs against a reference tour
after anything that touches startup tools/boot-timing.sh restart 5 the medians against the table below
before a release tools/boot-timing.sh reboot 3, tools/qml-profile.sh boot to first frame; what QML creates before it
after any UI, animation, poll or watcher change, and in every phase pass tools/audio-impact.sh (§10) idle 0 frames/s; playing ≈ the playhead and meter rates; 0 RT-thread faults from ravving's own code; 0 xruns

1. Static analysis: clang-tidy and clazy

tools/static-analysis.sh            # both; or `tidy` / `clazy` alone

It configures a separate build folder with a compile database (BUILD, default /tmp/ravving-analysis; the normal build/ is never touched), generates moc and the QML type registration, then runs clang-tidy with the repo's .clang-tidy and clazy (levels 0–2 without the Qt-idiom noise listed in the script) over src/ only, in parallel. Reports go to REPORTS (default ./analysis): clang-tidy.log, clazy.log and summary.txt, one count per check. Arch packages: clang (clang-tidy, run-clang-tidy) and clazy. A newer clang-tidy brings new checks: decide for each whether it finds something or restates the house style, and turn the latter off in .clang-tidy with a line saying why.

ShellCheck (2026-10-07)

tools/static-analysis.sh shell runs ShellCheck 0.10 at -S style over every shell script. The first run found 42 things (the suite's $? after A && B, unquoted xrandr arguments in start.sh, a stray unused variable, A && B || C used as if-then-else); all fixed or justified in place, so the baseline is 0. ShellCheck is on milo (apt install shellcheck); on a laptop without it the script sends the files there.

Handlers under dialogs (2026-10-09)

A sideways drag on the EXPORT or USB dialog paged the chords roll underneath (bar 1 → 4, reproduced on milo with xdotool). The modal dimmer stops items, not pointer handlers: Qt Quick still hands the press to every handler under it after the dialog's button or field took it, and BarSwipe's DragHandler then takes the drag over past its threshold. Disabling the page while a dialog is up was tried and dropped: a disabled ComboBox closes its own list at once, so the drop-downs (ROOT, SCALE, CHORD SET) stopped opening. What stays: the modal layers (dialogs, the MENU drawer, a drop-down's list) register in Session.overlays by identity (a repeated open cannot leave the page blocked), and every handler on a page or the header binds enabled: !Session.inputBlocked (five of them). tools/check-handlers.py (static-analysis.sh handlers, also in all) fails on a new one that does not; it found the five before the fix. Measured after: drags from the dialogs' fields, buttons, rows and blank parts, the drawer and a drop-down's list move nothing below; the page pages again after each and the focus is back on it.

Fixed in this pass

  • Machine::stepTicks(): integer division multiplier / 32 (exact only while libzynthbox's BeatSubdivisions is a multiple of 32) is now / 32.0.
  • The four machines are final: their constructors call their own restoreContent(), refresh() and revoice(), which is exact only while nothing derives from them.
  • DrumKit::rows() returns a const reference: ten loops in DrumMachine iterated a copy of the kit's rows (clazy range-loop-detach).
  • Uninitialised jack_status_t and loop counters, QJsonValue / QString loop copies in InputPorts, a const local that blocked a return move, by-value std::function, #include <QtConcurrent> (the whole module) → <QtConcurrentRun>, an unnormalised Q_ARG, mismatched parameter names, four last-use copies now moved.

2. Startup time

main() writes the phases of a start to the journal (src/startuptimer.h):

ravving: startup main 0 ms           process up (after startx, X and the binary loading)
ravving: startup application 18 ms   QGuiApplication
ravving: startup libzynthbox 649 ms  libzynthbox's singletons and engines
ravving: startup studio 2922 ms      machines, effects, the session (Studio)
ravving: startup qml 3681 ms         Main.qml created
ravving: startup first-frame …       the first frame on screen
ravving: startup wired …             audio and MIDI connected

tools/boot-timing.sh restart 5      # service restarts: CSV + medians, ms from the service starting
tools/boot-timing.sh reboot 3       # reboots (ravving the default UI): also kernel boot → first frame
tools/boot-timing.sh last           # the last start, without restarting anything

Compare medians, never single runs: the first frame moves by up to 3 s between runs because kwin starts beside ravving (start.sh) and the window is not shown before kwin manages it.

Before and after (milo, Raspberry Pi 5, 2026-10-05)

Median Before After (BASS restored) After (DRUMS restored)
restart: service start → first frame 6709 ms 4937 ms (−26 %) 5596 ms (−17 %)
restart: QML (studio → qml) 2068 ms 695 ms (−66 %) 1211 ms (−41 %)
restart: qml → first frame 1178 ms 765 ms 888 ms
reboot: kernel boot → first frame 17.28 s 14.67 s (−2.6 s)
reboot: service start → first frame 11013 ms 9168 ms

Since only the page on screen is built first, the start now depends on the page the session restores: DRUMS is the heaviest (all three drum machines' step grids, 864 KeyCaps), BASS a typical one. Before, every page was built whatever the page, so "before" holds for both. Compare runs on the same restored page ("page" in the session.json: 0 drums … 4 sampler).

Restart sparingly. Every restart stops and starts the HiFiBerry's PCM, and after a few dozen in a session milo's RP1 audio DMA driver oopses (dma2chan4, a use-after-free; the device reboots itself; see the Zynthbox bug log). Prefer 3–5 runs per measurement, and take boot-timing.sh last after a start that happens anyway.

Then the LV2 port cache (below) took the C++ side down too:

Median Before With the cache
restart: studio phase (libzynthbox → studio) 2292 ms 877 ms (−1.4 s)
restart: service start → first frame 5596 ms (DRUMS) 3502 ms (LEAD)
one cold boot: kernel boot → first frame 14.67 s 14.11 s

What made the difference (from the QML profile, below): 1. Only the page on screen is built before the first frame (Main.qml's PageLoader): the other four pages and the mixer are built one per 40 ms tick once the first frame is up. main.cpp restores the page before loading the QML, so the first page built is the right one. 2. KnobBadge builds its drawing on first show (shown, not visible): 1436 badges were created at startup, nearly all hidden. 3. The LV2 ports are cached on disk (JalvPlugin::readPorts, ~/.cache/ravving/lv2-ports.json): lv2info ran synchronously for each of the 8 plugins built at start (70–80 ms each, 561 ms for TAL-NoiseMaker: ~1 s). Each entry carries its bundle's and binary's modification times; an installed or upgraded plugin no longer matches and is asked again. Delete the file to force a full re-read.

Where the rest goes (next steps)

  • studio is ~0.9 s now (was 2.3 s before the LV2 port cache). The input ports' pw-dump (~0.18 s, synchronous, InputPorts) is the next piece to move off the start.
  • The Zynthbox style's QML is compiled at every start (~200 ms "Compiling" in the profile): qml-style-zynthbox ships no qmlcachegen output.

  • Cold boots spend ~3 s from the service starting to main (X and kwin from SD).

  • DrumsPage builds all three drum machines although one shows (its panels Repeater): the other two could follow the PageLoader pattern, ~0.5 s off a DRUMS start. Mind the panels.count > 0 ? panels.itemAt(…) binding in DrumsPage (§3).

Imported soundfonts (2026-10-08)

Every font in the library's soundfonts/ folder is read at start: its preset list becomes sources for bass, chords and lead, and its sample names a drum kit when they give three roles. The journal says what it cost: ravving: kits N ms, imported soundfonts: F fonts, S sources, M ms (also after a USB import, refreshImported).

Only the preset list ("pdta") is read, found by walking the RIFF chunk headers (SoundFontFile::presetData). Two of three SF3 files tried leave an odd-sized sdta chunk unpadded, which broke the first walk and fell back to reading the last 8 MB of each font. The walk now steps over an unpadded chunk too. Measured on milo with three imported fonts (Guitars Universal 1.4, FluidR3Mono_GM, jRhodes4: 43 MB, 263 sources), caches dropped before each of three restarts:

the scan studio step start → wired
no imported fonts 2 ms 1474 ms 5156 ms
3 fonts, 8 MB tail read 195 ms ~+300 ms
3 fonts, chunk walk 17 ms 1503 ms 5144 ms

So imported fonts cost nothing measurable at start; the scan's line in the journal is the check after adding a font whose writer is new.

An A/B before blaming a change (2026-10-09)

Start → wired read 7.9–8.1 s on milo, against the 5.1 s above, after SECTIONS phase 1. The build from before the day's work (6fda638, from a git worktree, deployed, three cold starts on the same project and page) gave the same 7.85–8.0 s: the time went with the device's state, not with the code. The QML step on the DRUMS page grew from 1.2 to 3.4 s in both, which is where to look next. The rule: compare against an old build on the same day, project and page before calling a slower start a regression.

Deploying to measure: the mtime trap

rsync -a keeps the laptop's modification times. A file edited on the laptop before the device last built another tree (the baseline) arrives older than that build's objects, and ninja skips it: the binary mixes old and new objects. Changing a header's ABI that way (DrumKit::rows() by value → by reference) crashed ravving at start in a later, partial rebuild. Sync with rsync -rlp --checksum (no times: changed files get the device's clock), or find src qml -exec touch {} + on the device before building after switching trees.

3. QML profiling

tools/qml-profile.sh NAME           # ./NAME.qtd and ./NAME-summary.txt
tools/qml-profile-summary.py NAME.qtd --type Creating --top 40
tools/qml-profile-summary.py NAME.qtd --from 2 --to 4

A systemd drop-in sets RAVVING_QML_DEBUG=10002,block: main.cpp opens the QML debug server and waits for qmlprofiler before loading any QML; the script attaches on the device, waits for startup wired, flushes the trace, then removes the drop-in and restarts ravving. The summary lists self time per event type, per file and per event: look at Creating first (how many of what were built) and the call counts (1436 calls of one component is the finding, not its 0.1 ms each). Never probe the debug port by connecting to it: the server takes the first connection as its client.

Traps met

  • StackLayout's attached properties are not ready during creation: StackLayout.index reads −1 and isCurrentItem flips while the layout adopts its items. A Loader keyed on them built every page, then destroyed and built them again. Give each page its index.
  • Asynchronous Loaders break the count/itemAt() idiom: an incubating Repeater reports its count before its items exist, and bindings like panels.count > 0 ? panels.itemAt(i) : null settle on null for good (silently: no error). The pages are therefore built synchronously, spread over ticks.
  • A model reset rebuilds every delegate: a periodic refresh that re-sorts (the Wi-Fi scan) took the text being typed and the keyboard's layout with it. Freeze the order while a row is open (WifiNetworks::frozen, plasma-nm's DelayModelUpdatesRole).
  • A tap on the on-screen keyboard is a press outside a popup: dialogs and the drawer must not close on outside presses while Qt.inputMethod.visible; a button next to a text field must not take the focus (focusPolicy: Qt.NoFocus), or the keyboard hides.

4. Visual regression: the screenshot tour

RAVVING_STYLE=Basic QT_QPA_PLATFORM=offscreen QT_FORCE_STDERR_LOGGING=1 RAVVING_NO_ZYNTHBOX=1 \
RAVVING_DATA_DIR=$PWD/data RAVVING_PROJECT_DIR=/tmp/tour/project RAVVING_SCREENSHOT_DIR=/tmp/tour/shots \
    build/ravving 2>&1 | grep -v -i jack

It visits every page and a few dialogs, saves PNGs and quits (main.cpp). Start from an empty project folder each time (the tour turns knobs, and the session keeps them), build the reference from the previous commit the same way, and compare with compare -metric AE ref.png new.png null: (ImageMagick). QT_FORCE_STDERR_LOGGING matters: without a terminal Qt logs to the journal and the run looks silent. The Zynthbox style is not on the laptop, hence RAVVING_STYLE=Basic.

5. Making ravving the device's UI

tools/device.sh default ravving       # or on the device: /usr/share/ravving/default-app.sh ravving
tools/device.sh default status
tools/device.sh default zynthbox      # back to stock; add --purge to uninstall ravving too

default-app.sh masks zynthbox-qml in root's user units (a --user disable cannot undo its global enable in /etc/systemd/user, and updates re-enable it globally; the mask wins over both) and enables ravving. Going back unmasks and starts zynthbox-qml, disables and resets ravving, and drops the development environment (RAVVING_GDB, RAVVING_QML_DIR).

6. The Store AppImage: the release check

tools/appimage-test.sh builds the AppImage on the device, installs it the way the Store does and walks every choice of the setup page and ravving's ZYNTHBOX button by touch, with an assertion on the device's state after each step. Run it after a version bump or any change to setup/, tools/default-app.sh, data/ravving.service or packaging/. About eight minutes; results in analysis/appimage-test-<date>/. Details in packaging.md.

7. Soundfonts and engines: when one is added

sh tools/soundfont-check.sh (on the device, from the laptop) takes every soundfont data/kits.json names (the drum kits, the machines' default engines, every FluidSynth sound source) and checks each: the file exists, its zones can sound (a font whose instrument zones declare a velocity range of 0–0 is mute at any velocity: SynStrings, LaString, MelloString and Organ.sf3 on the image are such, and were dropped), the preset the entry asks for (bank:program) exists in the font, and a chord rendered through fluidsynth offline on that preset (a kick, snare and hat for a kit, low notes for a bass, three seconds for pads that swell slowly) actually comes out. PASS / FAIL per font, exit status = failures; 35 of 35 pass on milo (2026-10-07). Run it after editing the sources in kits.json, after an image update (the fonts live in /zynthian/zynthian-data/soundfonts), and before a release.

Behind it, tools/soundfont.py (presets · ranges · render · categorise) looks inside one font and proposes kits.json entries for new ones (categorise --json), and tools/mididump.py shows what an engine's JACK MIDI port really carries, for a source that stays silent in ravving but sounds offline (docs/testing.md). A new engine type (a SoundEngine subclass) gets the same treatment: its sources into kits.json, the check run, and a pw-top look at its nodes' rate and quantum against the graph's (48000 / 256 on the device).

pipewire-pulse and the music player (2026-10-07)

zynthbox-qml keeps pipewire-pulse off because a Qt Multimedia stream once cost latency. ravving's music player needs it (Qt's audio output on Linux is PulseAudio), so the unit wants it, and the cost was measured with pw-top -b -n 2 on milo, idle, with an MP3 playing, and with the MP3 plus the transport: the driver (alsa_output.platform-soc…) stays at quantum 256 / 48000 in all three, its xrun count stays put (3159 before and after), and only the player's own node runs at its larger adapted quantum (1680 frames, 48000). The graph's rate is pinned (clock.allowed-rates = [ 48000 ]), so a 44.1 kHz file cannot switch it either. Re-measure the same way after a PipeWire update.

9. The audio graph: routing, clocks and xruns

When an engine, insert or route is added or changed, and in every phase pass:

tools/device.sh graph all -s 60      # rates, idle-but-linked nodes, threads, xruns over 60 s, the links

Expected on a Zynthbox: the driver is the sound card's playback node at 48000 / 256; every ravving-* audio node at 48000 with a period of 256 (jalv) or 512 (FluidSynth's stream, by design); no node with links that is not running; 0 xruns in 60 s, idle and with the reference project playing (run it twice, once with device.sh cuia SWITCH_PLAY_RELEASED first). Any steady xrun rate means a stall somewhere: the first thing to check is systemctl --user show-environment for RAVVING_GDB=1 (gdb costs 20–40 a minute), then graph-check.py threads for a render thread without realtime priority or one above PipeWire's data loops. What each column means, the tools behind it and the numbers measured so far are in docs/routing.md.

10. What the rest costs the sound

The sound comes first on this device: a feature, a poll, a watcher or an animation may not cost the audio anything it can hear. ravving's audio threads run at realtime priority, so other work cannot preempt them directly; what it can do is load the CPUs and the memory bus they share, stall a cycle with a page fault on a realtime thread, or hold a lock the audio side needs. Measure it, before and after:

tools/audio-impact.sh               # 30 s idle, then 30 s with the transport playing
tools/audio-impact.sh 20 idle       # only the idle window (no keys pressed: safe while someone plays)
tools/device.sh animations          # what keeps the window drawing, item by item

audio-impact.sh prints, per state: the frames per second the window put on screen (Ravving.framesSwapped, counted on the render thread), CPU in % of one core for the render thread, the GUI thread, ravving's realtime threads (policy FIFO / RR: the JACK clients, SyncTimer, MidiRouter…) and the rest, the page faults the realtime threads took, and the graph's xruns over the window (graph-check.py xruns, summed over the nodes: one graph-wide dropout counts once per node). playing presses PLAY and STOP: never run it while someone plays; idle only reads.

What healthy looks like (milo, Pi 5, the Lo-fi Say It project, 2026-10-08):

idle playing
frames/s 0 16 (the 16ths' playhead and the 10 Hz meters)
render / GUI thread 0 % / 3 % 13 % / 15 %
realtime threads 14 % 20 %
RT page faults / 20 s 0–2 (PipeWire's own data loops) ~85, all in libzynthbox's SyncTimerThread (below)
xruns 0 0

Found and fixed on 2026-10-10

  • Hidden pages followed the playhead. The five instrument pages stay built in their StackLayout, and every grid's cells bound to the step playing, so the pages not on screen re-evaluated their cells on every 16th. A grid (PianoRoll, ChordRoll, StepGrid), the samplers' play position and the SONG page's section progress now read the step only while visible. Measured, 20 s playing on the LEAD page (milo, an unsaved project): GUI thread 14 % → 9 %, render 8 % and realtime 19 % unchanged, 0 xruns.

Found and fixed on 2026-10-08

  • The screen drew every vsync with nothing moving (65 frames/s idle, 39 % of a core on the render thread). Three hidden button shadows in the header each held an OpacityAnimator inside a Behavior that never finished: an Animator runs on the render thread, and on an item that is not shown it never completes, so Qt Quick keeps rendering frames for it. The Zynthbox style (qml-style-zynthbox, and the copies in qml-module-zynthbox) now uses NumberAnimation in every such Behavior. Idle went to 0 frames/s and 0 %. zynthbox-qml uses the same style: it gains the same.
  • Playing drew every vsync too (65 frames/s, render 58 %, GUI 26 %): a 60 ms fade on the playhead wash of every step key at every 16th, on every grid including the hidden pages', an 80 ms smoothing animation on the master meter restarted at every 100 ms reading, and the samplers' playheads republished at every audio block. The playhead wash is instant, the meter has no Behavior, the playheads publish at 15 Hz (PlayPositionMs): 16 frames/s, render 13 %, GUI 15 %, sound unchanged (0 xruns either way).
  • The background polls cost the audio nothing measurable: the USB poll forks lsblk every 2 s at all times (Wi-Fi, Bluetooth, address and vitals poll only while the drawer is open), yet ravving's 24 realtime threads took 0 page faults over 30 s idle: Qt starts processes without copying the parent's memory into the audio threads' way. Keep it that way: a new poll is measured with this tool before it ships.
  • The xrun warning fired on every start (the issues center): the graph rebuilds as clients and links come and go, and the engines load their sounds for seconds after registering. BeatRepeat now leaves out xruns within 3 s of a client or link change and during the first 20 s; a stall without a graph change still counts (checked by stopping ravving for 200 ms seven times: 7 dropouts reported).

Rules that follow

  • An idle screen draws nothing. Before shipping UI work, tools/audio-impact.sh 20 idle must read 0 frames/s; if not, device.sh animations names the item.
  • No Animator (Opacity/Scale/Rotation/XAnimator…) inside a Behavior: use NumberAnimation. No Behavior on something the transport changes at every step or every meter reading: those values change instantly.
  • Anything fed by the audio side (positions, levels) is published at the rate the eye needs (15 Hz for a moving line, 10 Hz for meters), never per audio block.
  • An infinite animation (loops: Animation.Infinite) runs only while its state lasts (a take waiting, a latched pad) and only while its item is shown.
  • A poll that forks or blocks runs only while what it feeds is on screen, unless it watches for something that has to be noticed at once (a USB stick); measure it with this tool.

Open

  • libzynthbox's SyncTimerThread (FIFO 99, the sequencer clock) takes ~4 minor page faults a second while playing: it touches memory that has not been mapped yet (a growing buffer or a fresh allocation) on a realtime thread. Not ravving's code; to check whether zynthbox-qml shows the same and to report upstream (~/Coding/libzynthbox-bug-reports.md).
  • The GUI thread's 15 % while playing is mostly the hidden pages following the playhead (every grid's 16 keys re-evaluate at every step); giving hidden pages no playhead would roughly halve it.

11. List models (2026-10-08)

Views fed a plain list (a QVariantList from the backend, a JS array) rebuild every delegate whenever the list is set again; on the Pi a row with a Zynthbox Button costs ~1.4 ms to make (five SVG frames). The long or often-updated lists now go through KeyedListModel (src/, tests in tests/: cmake -DRAVVING_TESTS=ON build && ctest --test-dir build): a new list is applied as the fewest row changes, matched by a key; the longest also set reuseItems.

Measured with AFTER=script tools/qml-profile.sh (an interaction: the USB page's takes folder, two re-scans, the presets folders, the kit picker and a favourite toggled twice):

before after
Creating 212 ms, 5130 objects 135 ms, 3550
Javascript 213 ms 159 ms
Binding 147 ms 96 ms
USB rows made 92 42 (only the folders opened; a re-scan makes none)
Buttons made 170 120

Trap met: a model whose roles were replaced by each list's fields reset itself whenever the USB page went from folders to files and back (a reset rebuilds everything): the roles only grow now, and a test keeps it so. Use KeyedListModel for any list that is long or updated often; small fixed lists (the banks, the kinds) stay plain.
