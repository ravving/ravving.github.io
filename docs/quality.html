    Quality

    Static analysis, startup timing, QML profiling, the screenshot tour, what the rest costs the sound.

    The checks to run on ravving every so often (and before a release) and what each tool is for. All the tools live in tools/; the laptop ones need no libzynthbox (ravving builds without it), the device ones run against root@milo.local (DEVICE= for another).

    When Run Look at
    after C++ changes tools/static-analysis.sh new lines in analysis/summary.txt against the accepted findings (§1)
    after changes to a shell script (tools/*.sh, data/start.sh) tools/static-analysis.sh shell (ShellCheck, here or on the device) analysis/shellcheck.log: the scripts are kept at zero findings; a finding that is the script's intent (a remote command built on the laptop, a deliberate word split) gets a # shellcheck disable= line with the reason above it
    after adding a pointer handler (Tap / Drag / Pinch / Point / Wheel) to a page or the header tools/static-analysis.sh handlers zero: each binds enabled: … !Session.inputBlocked, else a drag on a dialog reaches it (§1, "Handlers under dialogs")
    after QML changes the screenshot tour (§4) QML warnings in its output; pixel diffs against a reference tour
    after a skin set is added or changed (data/skins/) tools/check-skins.py, then tools/skin-tour.sh OUT SET (§4) the set passes every contrast check; its eight machine pages in OUT/SET-sheet.png and its SETTINGS shots
    after the export covers change (src/backend/albumart.cpp, data/artworks) tools/make-artworks.sh when an artwork or sticker was added, then ctest -R albumart and tools/render-covers.sh OUT (testing.md, "The covers, on the laptop") OUT/sheet.jpg: every title readable, no sticker on a title or an icon, the stickers a few and along the edges
    after CMake changes tools/static-analysis.sh cmake (also ctest -R cmake-health) zero findings (§1, "The CMake's health"): the baseline is empty
    after a shortcut changes tools/static-analysis.sh shortcuts (also ctest -R shortcuts) no file worse than tools/shortcuts-baseline.json (§1, "The shortcuts"); --map to see a page's keys
    after QML changes tools/static-analysis.sh health (also ctest -R qml-health) no file worse than tools/qml-health-baseline.json (§1, "The QML's health"); lower the baseline when a file improves
    after anything that touches startup tools/boot-timing.sh restart 5 the medians against the previous run's
    before a release tools/boot-timing.sh reboot 3, tools/qml-profile.sh boot to first frame; what QML creates before it
    before a release the whole list in §13 every gate passes, in order
    after the webpage's look or text changes (site/), and before a release node tools/check-site-a11y.mjs (§12) 0 failures: contrast in both themes, a focus ring on every stop, names, no sideways scroll, no endless motion, the same structure in en, es and ja
    after any UI, animation, poll or watcher change, and in every phase pass tools/audio-impact.sh (§9) idle 0 frames/s; playing ≈ the playhead and meter rates; 0 RT-thread faults from ravving's own code; 0 xruns

    1. Static analysis: clang-tidy and clazy

    tools/static-analysis.sh            # both; or `tidy` / `clazy` alone

    It configures a separate build folder with a compile database: BUILD, by default /tmp/ravving-analysis, so the normal build/ is never touched. It generates moc and the QML type registration, then runs two tools over src/ only, in parallel:

    • clang-tidy, with the repo's .clang-tidy;
    • clazy, levels 0–2, without the Qt-idiom noise listed in the script.

    Reports go to REPORTS (default ./analysis): clang-tidy.log, clazy.log, and summary.txt with one count per check. Arch packages: clang (clang-tidy, run-clang-tidy) and clazy.

    A newer clang-tidy brings new checks. Decide for each whether it finds something or restates the house style, and turn the latter off in .clang-tidy, with a line saying why.

    ShellCheck

    tools/static-analysis.sh shell runs ShellCheck 0.10 at -S style over every shell script; the baseline is 0. ShellCheck is on the device (apt install shellcheck); on a laptop without it the script sends the files there.

    Handlers under dialogs

    The modal dimmer stops items, not pointer handlers. Qt Quick still hands a press to every handler under it after the dialog's button or field took it, and a page's DragHandler then takes the drag over past its threshold. Disabling the page while a dialog is up is no way out: a disabled ComboBox closes its own list at once.

    So:

    • the modal layers (dialogs, the MENU drawer, a drop-down's list) register in the kit's Interaction.overlays, by identity, so a repeated open can't leave the page blocked;
    • every handler on a page or the header binds enabled: !Session.inputBlocked (which reads Interaction.inputBlocked; a kit control binds that one);
    • tools/check-handlers.py (static-analysis.sh handlers, also in all) fails on a new one that doesn't.

    The QML's health

    tools/check-qml-health.py reads the style (style/), the UI kit (controls/) and the app (qml/) and counts, per file:

    • layering: a layer reaching up. The style may not use the kit or the app, and the kit may not use the app's types, Session, Rave or the context objects. An app component that is only a look on a Qt Quick Control belongs in the style. The app may not redo a kit control (tools/qml-health.json's kit-owned patterns).
    • dead: ids never used in their file, files nothing instantiates, and properties, functions and signals used nowhere in the QML, the C++, the shaders or the tools.
    • stale: commented-out code, TODO / FIXME / XXX / HACK, console.log;
    • tangled: long files, deep nesting, long functions and handlers, parent.parent, files reaching into many app objects (the limits are in tools/qml-health.json);
    • poor: untyped functions, implicit handler parameters, property var, loose ==, delegates without pragma ComponentBehavior: Bound;
    • duplicate: the same 8 lines (whitespace and comments aside) in two places.
    • skin: a colour passed by hand that the Skin already gives, a skin loop, the style reading the skin's ink.
    • docs: a kit or Theme type without its QDoc page, or a member without its /*! */.

    The QML baseline

    tools/qml-health-baseline.json holds today's counts. A file that gets worse fails the check; one that gets better is reported, and --update-baseline lowers its count. --verbose lists every finding, --check NAME runs one family.

    The CMake's health

    tools/check-cmake-health.py reads every CMakeLists.txt and counts, per file:

    • correctness: Qt's CMake rules. Qt 6 commands only, and a version in find_package(Qt6). qt_standard_project_setup() comes before the targets, the C++ standard before Qt. QML goes only in qt_add_qml_module, and its dependencies are named by target. Every target_ command says PRIVATE, PUBLIC or INTERFACE, every glob has CONFIGURE_DEPENDS, and no setting is directory-wide.
    • dead: unused variables, options and functions; listed files that are gone; source files no CMake file lists or globs.
    • stale: commented-out commands, TODOs, comments naming a gone file, a header that lists the parts but misses one, a policy the setup already sets.
    • tangled: long files, deep nesting.
    • duplicate: a command or list entry twice; a definition or include folder a linked library already gives. Also the same run of commands three times: a function would do, like ravving_test() in tests/CMakeLists.txt.
    • style: lower case, indents in fours, no tabs, lines up to 120 characters. A long call puts one argument per line, file lists are sorted with each header beside its source, and every file starts with a header comment.

    The CMake baseline

    Its baseline (tools/cmake-health-baseline.json) is empty: any finding fails. Both health tools share tools/health_report.py (the table, the baseline, --verbose, --update-baseline).

    The shortcuts

    tools/check-shortcuts.py reads the keys the C++ input layer takes before any page (src/ravving.cpp: ALT + MODE, ALT + ▲, ALT + 1, X, Y, ALT + the step keys and the knobs) and every Hardware.on… handler. It counts, per file:

    • shadowed: a handler, or its ALT branch, for a key the C++ layer takes first.
    • repeated: the same handler in two places; one shared type or function should hold it.
    • overlap: one key bound by two sibling objects of a file with different code.
    • tangled: long handlers, nested ternaries, event without event =>, deep reaches, an object's handlers scattered, a group of handlers with no comment saying what the keys do.

    --map prints every file's keys after the global layer. tools/shortcuts-baseline.json holds today's counts, as the QML baseline does.

    The accepted findings

    What is left is known and accepted; anything not in this list is new and worth reading.

    Check Count Why it stays
    bugprone-implicit-widening-of-multiplication-result 12 soundfont record offsets (index * Size) and the track lanes: int-sized files and lists
    bugprone-signed-bitwise 11 MIDI status / channel and LED colour byte masks on int; values are 0..255
    bugprone-incorrect-roundings 3 int(x + 0.5) on frame counts, which are never negative
    bugprone-multi-level-implicit-pointer-conversion 2 jack_free(ports) and QMetaObject's void * arguments: the C APIs' own types

    clazy qproperty-without-notify 1 HardwareEvent::accepted: a per-event object, never bound

    2. Startup time

    main() writes the phases of a start to the journal (src/startuptimer.h):

    ravving: startup main 0 ms           process up (after startx, X and the binary loading)
ravving: startup application 18 ms   QGuiApplication
ravving: startup libzynthbox 649 ms  libzynthbox's singletons and engines
ravving: startup studio 2922 ms      machines, effects, the session (Studio)
ravving: startup backends …          the rest of the backends (outputs, Bluetooth, USB, sharing…)
ravving: startup qml 3681 ms         Main.qml created
ravving: startup first-frame …       the first frame on screen
ravving: startup wired …             audio and MIDI connected

    tools/boot-timing.sh restart 5      # service restarts: CSV + medians, ms from the service starting
tools/boot-timing.sh reboot 3       # reboots (ravving the default UI): also kernel boot → first frame
tools/boot-timing.sh last           # the last start, without restarting anything

    Compare medians, never single runs: the first frame moves by up to 3 s between runs because kwin starts beside ravving (start.sh) and the window is not shown before kwin manages it.

    The start depends on the page the session restores, since only the page on screen is built first. DRUMS is the heaviest (all three drum machines' step grids), and BASS a typical one.

    • Compare runs on the same restored page: "page" in the session.json, 0 drums … 4 sampler.
    • Before blaming a change for a slower start, compare against an old build (a git worktree, deployed) on the same day, project and page. The device's state moves the times too.

    Restart sparingly. Every restart stops and starts the HiFiBerry's PCM, and after a few dozen in a session the Pi's RP1 audio DMA driver can oops (the device reboots itself). Prefer 3–5 runs per measurement, and take boot-timing.sh last after a start that happens anyway.

    Deploy with checksums

    rsync -a keeps the laptop's modification times. A file edited before the device last built another tree then arrives older than that build's objects, and ninja skips it. tools/device.sh deploy syncs with rsync -rlp --checksum. After switching trees by hand, run find src qml -exec touch {} + on the device before building.

    What keeps the start short

    1. Only the page on screen is built before the first frame (Main.qml's PageLoader). Once the first frame is up, the other four pages and the mixer are built, one per 40 ms tick. The page is restored (in main.cpp) before the QML loads, so the first page built is the right one.
    2. KnobBadge builds its drawing on first show (shown, not visible): most badges stay hidden.
    3. The LV2 ports are cached on disk (JalvPlugin::readPorts, ~/.cache/ravving/lv2-ports.json) instead of lv2info running for each plugin built at start. Each entry carries its bundle's and binary's modification times; an installed or upgraded plugin does not match and is asked again. Delete the file to force a full re-read.
    4. Imported soundfonts cost next to nothing: only each font's preset list ("pdta") is read, found by walking the RIFF chunk headers (SoundFontFile::presetData, which steps over an unpadded odd-sized chunk too). The journal says what it cost: ravving: kits N ms, imported soundfonts: F fonts, S sources, M ms (also after a USB import, refreshImported); that line is the check after adding a font whose writer is new.

    3. QML profiling

    tools/qml-profile.sh NAME           # ./NAME.qtd and ./NAME-summary.txt
tools/qml-profile-summary.py NAME.qtd --type Creating --top 40
tools/qml-profile-summary.py NAME.qtd --from 2 --to 4

    How it works:

    1. A systemd drop-in sets RAVVING_QML_DEBUG=10002,block. main.cpp opens the QML debug server, and waits for qmlprofiler before loading any QML.
    2. The script attaches on the device, waits for startup wired, and flushes the trace.
    3. It removes the drop-in and restarts ravving.

    The summary lists self time per event type, per file and per event. Look at Creating first, how many of what were built, and at the call counts: 1436 calls of one component is the finding, not its 0.1 ms each.

    Never probe the debug port by connecting to it: the server takes the first connection as its client.

    4. Visual checks: the screenshot tour

    tools/tour.sh OUT_DIR [en|es|ja]           # offscreen, 1280 × 800, a fresh state each run
tools/tour-compare.py REF_DIR NEW_DIR --diffs DIFF_DIR
tools/tour-diff.py REF_DIR NEW_DIR --out CROPS_DIR    # where each shot changed, old above new

    The tour (RAVVING_SCREENSHOT_DIR, the ScreenshotTour class) saves a PNG of each view. It shows:

    • every page, drum machine and sampler editor;
    • the header's knob focus and the sections opened;
    • every dialog, opened, shot and closed in turn, on each page and on the mixer, SONG, MUSIC PLAYER and RECORDER pages, the drawer's and the dialogs inside dialogs too.

    A dialog's shot is named d-<view>-<type>-<id> after its QML type and id, so a new dialog is in the tour with nothing to add. Beside the shots, the run writes:

    • index.txt: the shots in order;
    • log.txt: the run's output;
    • style-dump.json: the values the look reads (tools/style-dump.qml): ravving's design tokens (the palette, sizes, durations, icon sizes, fixed settings), the application font and palette, and the registered font families.

    Running and comparing

    • tools/tour.sh starts from a fresh profile, session, cache, library and project each time (RAVVING_HOME), with the language given written into that profile.
    • STYLE_PREFIX=DIR puts DIR/qml and DIR/plugins first on the import and plugin paths.
    • RAVVING_STYLE=Basic instead draws plain controls.
    • tools/tour-compare.py counts the differing pixels per shot (compare -metric AE) and lists the shots only one run has.
    • With --diffs, it also writes a diff image per differing shot. It compares the two style dumps value by value, and exits with the number of shots that differ.
    • tools/tour-diff.py shows where each shot changed, old above new (--out), and marks the known noise listed in tools/tour-noise.json.
    • Two runs of the same build match on every shot except those with live values. These are the MENU drawer (d-*-Drawer-menu: CPU load, temperature) and the issues list (d-*-IssuesPopup-*: when each was raised). On the device, the Wi-Fi, Bluetooth and USB lists vary too. A difference there alone is not a change.
    • A reference is a tour of the previous commit, taken on the same machine. The laptop's Qt is newer than the device's, so compare laptop with laptop; the device's tour is the one that counts.

    What the tour can't show

    The tour runs without Zynthbox, so no engine is loaded and the machines' pages don't show the real sequencer. It finds QML trouble and visual regressions. The pictures for the site and the guide are taken from the running app on the device instead (tools/device.sh shot, site/README.md).

    Skin sets in the tour

    • SKIN=<set> starts tools/tour.sh in another instruments' skin set (jelly, ravving, a skin file's key): a skin set is checked on every page at once, SKIN=jelly tools/tour.sh OUT.
    • The tour runs in a fixed folder, so two can't run at once: when several runs may overlap, start each as flock /tmp/ravving-tour.lock tools/tour.sh ….
    • tools/skin-tour.sh OUT_DIR SET… does that for skin sets: it checks each set's colours (tools/check-skins.py), tours it under the lock into OUT_DIR/SET/ and puts its eight machine pages side by side in OUT_DIR/SET-sheet.png. The laptop has no drum soundfonts, so the drums' rows don't show there: the checker covers what is drawn on their well.
    • tools/skin-fix.py [--hues] FILE.json… nudges a failing set's colours (their lightness only; with --hues, a glow may also turn) until the checker passes it, and prints what moved.
    • tools/check-skins.py --similar lists the closest pairs of sets (mean Delta E of the machines' cases, keys, wells and lights): a set under 15 from another looks like it on the device. The checker runs as ctest skins-readable.

    5. Making ravving the device's UI

    tools/device.sh default ravving       # or on the device: /usr/share/ravving/default-app.sh ravving
tools/device.sh default status
tools/device.sh default zynthbox      # back to stock; add --purge to uninstall ravving too

    default-app.sh masks zynthbox-qml in root's user units (a --user disable cannot undo its global enable in /etc/systemd/user, and updates re-enable it globally; the mask wins over both) and enables ravving. Going back unmasks and starts zynthbox-qml, disables and resets ravving, and drops the development environment (RAVVING_GDB, RAVVING_QML_DIR).

    6. The Store AppImage: the release check

    tools/appimage-test.sh builds the AppImage on the device and installs it the way the Store does. Then it walks every choice of the setup page and ravving's ZYNTHBOX button by touch, asserting the device's state after each step.

    Run it after a version bump, or any change to setup/, tools/default-app.sh, data/ravving.service or packaging/. It takes about eight minutes, with results in analysis/appimage-test-<date>/. Details are in packaging.md.

    7. Soundfonts and engines: when one is added

    sh tools/soundfont-check.sh, run on the device from the laptop, takes every soundfont data/kits.json names: the drum kits, the machines' default engines, and every FluidSynth sound source. It checks each one:

    1. the file exists;
    2. its zones can sound. A font whose instrument zones declare a velocity range of 0–0 is mute at any velocity. SynStrings, LaString, MelloString and Organ.sf3 on the image are like that, and are left out;
    3. the preset the entry asks for (bank:program) exists in the font;
    4. a chord rendered offline through fluidsynth on that preset actually comes out: a kick, snare and hat for a kit, low notes for a bass, three seconds for pads that swell slowly.

    It prints PASS or FAIL per font, and exits with the number of failures. Run it after editing the sources in kits.json, after an image update (the fonts live in /zynthian/zynthian-data/soundfonts), and before a release.

    Behind it

    • tools/soundfont.py (presets · ranges · render · categorise) looks inside one font, and proposes kits.json entries for new ones (categorise --json).
    • tools/mididump.py shows what an engine's JACK MIDI port really carries, for a source that stays silent in ravving but sounds offline (testing.md).

    A new engine type (a SoundEngine subclass) gets the same treatment. Its sources go into kits.json, the check runs, and pw-top shows its nodes' rate and quantum against the graph's (48000 / 256 on the device).

    pipewire-pulse and the music player

    ravving's music player needs pipewire-pulse, since Qt's audio output on Linux is PulseAudio, so the unit wants it. Its stream runs at its own adapted quantum, and leaves the graph at 256 / 48000. The graph's rate is pinned (clock.allowed-rates = [ 48000 ]), so a 44.1 kHz file can't switch it.

    After a PipeWire update, check with pw-top -b -n 2: idle, with an MP3 playing, and with the MP3 plus the transport. The driver must stay at 256 / 48000, with its xrun count unchanged.

    8. The audio graph: routing, clocks and xruns

    When an engine, insert or route is added or changed, and in every phase pass:

    tools/device.sh graph all -s 60      # rates, idle-but-linked nodes, threads, xruns over 60 s, the links

    Expected on a Zynthbox:

    • the driver is the sound card's playback node, at 48000 / 256;
    • every ravving-* audio node is at 48000, with a period of 256 (jalv), or 512 (FluidSynth's stream, by design);
    • no node with links is not running;
    • 0 xruns in 60 s, idle and with the reference project playing. Run it twice, once with device.sh cuia SWITCH_PLAY_RELEASED first.

    Any steady xrun rate means a stall somewhere. Check first systemctl --user show-environment for RAVVING_GDB=1 (gdb costs 20–40 a minute). Then graph-check.py threads, for a render thread without realtime priority, or one above PipeWire's data loops. What each column means, and the tools behind it, are in routing.md.

    9. What the rest costs the sound

    The sound comes first on this device: a feature, a poll, a watcher or an animation may not cost the audio anything it can hear.

    ravving's audio threads run at realtime priority, so other work can't preempt them directly. What it can do is:

    • load the CPUs and the memory bus they share;
    • stall a cycle with a page fault on a realtime thread;
    • hold a lock the audio side needs.

    Measure it, before and after:

    tools/audio-impact.sh               # 30 s idle, then 30 s with the transport playing
tools/audio-impact.sh 20 idle       # only the idle window (no keys pressed: safe while someone plays)
tools/device.sh animations          # what keeps the window drawing, item by item

    audio-impact.sh prints, per state:

    • the frames per second the window put on screen (Ravving.framesSwapped, counted on the render thread);
    • CPU in % of one core, for the render thread, the GUI thread, ravving's realtime threads (policy FIFO / RR: the JACK clients, SyncTimer, MidiRouter…) and the rest;
    • the page faults the realtime threads took;
    • the graph's xruns over the window (graph-check.py xruns, summed over the nodes, so one graph-wide dropout counts once per node).

    playing presses PLAY and STOP, so never run it while someone plays. idle only reads.

    What healthy looks like (a Pi 5, a full project):

    idle playing
    frames/s 0 16 (the 16ths' playhead and the 10 Hz meters)
    render / GUI thread 0 % / 3 % about 13 % / 10–15 %
    realtime threads about 14 % about 20 %
    RT page faults / 20 s 0–2 (PipeWire's own data loops) some in libzynthbox's SyncTimerThread, none in ravving's code
    xruns 0 0

    The rules

    • An idle screen draws nothing. Before shipping UI work, tools/audio-impact.sh 20 idle must read 0 frames/s; if not, device.sh animations names the item.
    • No Animator (Opacity/Scale/Rotation/XAnimator…) inside a Behavior: use NumberAnimation. No Behavior on something the transport changes at every step or every meter reading: those values change instantly.
    • Anything fed by the audio side (positions, levels) is published at the rate the eye needs (15 Hz for a moving line, 10 Hz for meters), never per audio block.
    • An infinite animation (loops: Animation.Infinite) runs only while its state lasts (a take waiting, a latched pad) and only while its item is shown.
    • A grid, a play position or a progress reads the step playing only while visible: the hidden pages stay built in their StackLayout and must not follow the playhead.
    • A poll that forks or blocks runs only while what it feeds is on screen, unless it watches for something that has to be noticed at once (a USB stick); measure it with this tool.

    10. List models

    Views fed a plain list (a QVariantList from the backend, a JS array) rebuild every delegate whenever the list is set again. On the Pi, a row with a Zynthbox Button costs about 1.4 ms to make (five SVG frames).

    • The long or often-updated lists go through KeyedListModel (src/, tests in tests/: cmake -DRAVVING_TESTS=ON build && ctest --test-dir build). It applies a new list as the fewest row changes, matched by a key. The longest also set reuseItems.
    • Its roles only grow, since a reset would rebuild everything, and a test keeps it so.
    • Small fixed lists, like the banks and the kinds, stay plain.

    AFTER=script tools/qml-profile.sh profiles an interaction instead of a start.

    11. Phase passes

    Every phase of a feature ends with this pass. Run the suites with ravving under gdb on the device: systemctl --user set-environment RAVVING_GDB=1, then a restart. start.sh prints a backtrace to the journal on a crash. Turn gdb off again for the timing rows:

    Check How
    clang-tidy / clazy tools/static-analysis.sh: back to the accepted findings (§1)
    start-up (gdb off) tools/boot-timing.sh restart 3: the medians against the last pass
    QML profile tools/qml-profile.sh NAME: what the phase adds to Creating
    screenshot tour §4: every shot, no QML errors
    feature suites (gdb on) the page's suite and any the change touches (testing.md)
    what it costs the sound tools/audio-impact.sh (§9)
    valgrind memcheck on the offscreen tour (laptop) with --leak-check=no; read only the frames that name ravving (Qt's aeshash128 and forkfd reports are known false positives); it takes about 25 min

    12. The webpage: accessibility and the three languages

    node tools/check-site-a11y.mjs [--pages index.html,features.html] [--langs en,es] [--verbose]
ctest --test-dir build -C release-check -R site-a11y     # the same, as the release review's ctest

    It serves site/ over http and opens each page in headless Chromium (over the DevTools protocol, no extra packages). By default it checks the landing, the features page, the docs home, Your first beat and Play it live, each in English, Spanish and Japanese, which takes about five minutes. Exit status is the number of failures.

    Check How Fails when
    contrast every text in both themes, with reduced motion so every row is shown; its ground stacked from its ancestors' colours under 4.5:1, or 3:1 for large text (24 px, or 18.66 px bold)
    focus Tab through the page in both themes a stop has no ring (outline or shadow), or is hidden
    names every link, button and picture a link or button has no name (text, aria-label, title, an image's alt), an <img> has no alt
    layout 320, 360, 768 and 1280 px wide the page scrolls sideways
    motion reduced motion an animation still runs forever
    parity the es and ja pages against the English a heading, link, button or picture more or fewer

    What it doesn't measure:

    • Text over a picture or a gradient. --verbose counts these per page ("over images"): look at them in both themes.
    • A screen reader, a real phone and 200 % zoom. These are tried by hand before a release.

    The skins' contrast figures (check-skins.py) and the design sheet's are the colours' own ratios. They don't certify a page: this check measures the text where it is drawn.

    13. Before a release

    Every gate, in the order to run them. Each one is described where it lives; this list only collects them. A release ships when every row passes.

    # Gate Run Passes when
    1 The checks ctest --test-dir build every test passes (translations-current, design-tokens, artworks and ui-rules among them)
    2 The webpage ctest --test-dir build -C release-check -R site-a11y (§12) 0 failures; text over pictures looked at in both themes
    3 Static analysis tools/static-analysis.sh (§1) back to the accepted findings
