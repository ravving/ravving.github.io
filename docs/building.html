Building

The CMake layout, the build folders, faster builds, profiling the build, the site.

Project layout

One CMake project, its targets each with the CMakeLists.txt of their sources (the source files themselves are where they were: the split is of the CMake files only):

File Owns
CMakeLists.txt the project: version, C++ standard, AUTOMOC, qt_standard_project_setup, the dependencies (find_package Qt6 / KF6BluezQt / ZLIB, pkg_check_modules jack / sndfile / taglib), RAVVING_DATA_INSTALL_DIR and RAVVING_THEME, the build options (RAVVING_QML_AOT, RAVVING_PCH, RAVVING_TIME_TRACE, RAVVING_UNITY, RAVVING_IWYU, RAVVING_TESTS) with ravving_build_settings(<target>), their per-target side; the add_subdirectory calls; the generated files (VERSION, config/plasmarc) and the install rules of the project as a whole (data/, the theme, systemd and WirePlumber drop-ins, the desktop entry and icons)
src/backend/CMakeLists.txt ravving_backend, the static backend library (src/backend/* and src/zynthboxbridge.*): its sources, its PUBLIC include directories (src/, so the app includes backend/xxx.h; src/backend/, so its files include each other bare), its PUBLIC link set (the Qt modules, JACK, sndfile, TagLib, zlib, BluezQt), the RAVVING_* compile definitions, the unity build
src/CMakeLists.txt ravving, the app: src/*.cpp, the Ravving QML module over qml/ at the repository root (each file's path from there is its resource alias, so the resources stay qrc:/qt/qml/Ravving/qml/… and the module's qmldir stays at build/Ravving), RAVVING_QML_AOT, the branding resources and the shaders, the link to ravving_backend, the binary's install rule; the binary itself stays at build/ravving
setup/CMakeLists.txt ravving-setup, the AppImage's setup program (build/setup/ravving-setup)
tests/CMakeLists.txt the laptop-side tests, built with -DRAVVING_TESTS=ON

Target names, options, output paths and the install layout are those tools/device.sh, tools/build-appimage.sh, tools/static-analysis.sh and tools/build-profile.sh rely on; a new backend class goes into src/backend/CMakeLists.txt, a new QML file into src/CMakeLists.txt's RAVVING_QML_FILES.

The build folders

Folder Where What for Settings
build/ laptop and device the development loop: tools/device.sh deploy, ctest RAVVING_QML_AOT=OFF, RAVVING_PCH=ON
build-release/ device the Store AppImage (tools/build-appimage.sh, configured there on each run) Release at -O2 (no debug information; binaries stripped at install), RAVVING_QML_AOT=ON, RAVVING_PCH=ON, prefix /usr

Neither is ever removed by the tools: device.sh deploy syncs the source with --exclude '/build*' (so its --delete leaves both alone on the device), REMOVE RAVVING and the release check uninstall only what cmake --install put on the system, and the AppImage build clears only its staging trees (build-release/stage, build-release/appimage). Keeping them is what keeps builds incremental.

Faster builds

A clean build of 0.2.0, laptop, 4 cores, RelWithDebInfo (the device's settings), 2026-10-10:

as it was RAVVING_QML_AOT=OFF + RAVVING_PCH=ON
C++ compile (CPU) 829 s 499 s (precompiled Qt headers)
QML compile (CPU) 740 s 156 s (bytecode only)
qmlcachegen (CPU) 134 s 22 s
wall clock 426 s 190 s

The device (a Pi 5, 4 cores) takes about as long as the laptop for the same work.

  • RAVVING_QML_AOT (default ON). qmlcachegen compiles each QML file's bindings into C++, which then has to be compiled: on the Pi that was 40 % of a build. OFF keeps the QML precompiled but as bytecode only (--only-bytecode): the bindings run in Qt's interpreter and JIT, which is fine to develop with; a release keeps ON (build-release/).
  • RAVVING_PCH (default ON): the Qt headers nearly every file includes (QObject, QString, QVariant, the containers, QDebug, QJsonDocument…) parsed once instead of in each of ~90 files.
  • ccache is used when it is installed (CMAKE_CXX_COMPILER_LAUNCHER): a file compiled before with the same flags comes from its cache (after a reconfigure, switching branches).
  • The device builds at the lowest priority (nice -n 19 ionice -c 3 in device.sh deploy): not faster, but a build beside the music does not take the audio's time.

A corrupted ninja log rebuilds everything

ninja: warning: premature end of file; recovering means build/.ninja_deps was cut short (a build killed mid-run, two builds at once in one folder): ninja then trusts nothing it built and plans every step on every build. ninja -C build -t recompact, then one full build, puts it right (2026-10-10: every laptop build had been doing all 336 steps). Never run two builds in one build folder; let a build finish rather than kill it.

Why one header edit recompiled every QML file

The QML module is built from the ravving target, and Qt's type registration reads the metadata of every QObject class in that target. Any change to a backend header (machine.h, studio.h…) regenerated it, and with it every QML file's compiled C++: minutes for a one-line change. Fixed by building src/backend (and zynthboxbridge) as its own static library, ravving_backend, outside the QML module: QML reaches it through context properties (studio, ravving…), which need no registration, and the one type it registered, Sections (for its LOOP / SONG enum), is now two numbers in Rave.qml (Rave.sectionsLoop, Rave.sectionsSong). Touching machine.h then: 157 s and every QML file before, 19 s and no QML after.

Profiling the build

tools/build-profile.sh [OUT_DIR] [-- cmake options] builds ravving from clean with clang and -ftime-trace (RAVVING_TIME_TRACE) in analysis/build-profile/build (never build/), then:

  • analysis.txt, ClangBuildAnalyzer's report: the slowest files to parse and to compile, the most expensive headers (where they come from, how often), the costliest template sets and functions;
  • trace.json, ninjatracing over .ninja_log: the build's timeline, one lane per job; open it in https://ui.perfetto.dev (or chrome://tracing) to see what holds the four cores up (moc's mocs_compilation.cpp, a slow file at the end, qmlcachegen's steps).

The tools: clang (Arch's), ClangBuildAnalyzer and ninjatracing in ~/.local/bin (built from their git checkouts in ~/.local/src), include-what-you-use from the AUR (yay -S include-what-you-use).

include-what-you-use: cmake -B analysis/iwyu -DRAVVING_IWYU=ON -DRAVVING_PCH=OFF and build ravving_backend there: each file's compile prints what to add, what to remove and which includes a forward declaration would replace (analysis/iwyu.log). Precompiled headers off, or it reports their includes as unused everywhere. Read it with care: it knows no Qt mapping (it would swap <QVariantMap> for Qt's internal <qvariant.h>: ignore those), and it does not see moc's generated code, so it calls a header unneeded where a Q_PROPERTY exposes a pointer to that class (machine.h's SoundControls and TrackEffects, devicecontrols.h's Wifi): moc needs the complete type there. The first pass (2026-10-10) found nothing else to change.

Unity builds (RAVVING_UNITY, the backend only: the app target carries qmlcachegen's and rcc's generated sources, and AUTOMOC's mocs_compilation.cpp stays out of the batches on its own) are there to measure, not on by default: many backend files define file-local constants with the same names (MaxBars, AuditionMs…), which collide once a batch merges them.

What the first profile found (laptop, clean, 182 s): parsing 154 s, optimising and code generation 180 s across 85 files; with precompiled headers only QQuickItem remains an expensive header (4 files, about 1 s each); no single hotspot: the heaviest files are the machines, the exporter and moc's mocs_compilation.cpp (about 15 s each), and the costliest template sets are Qt's containers (QMap::insert, QList::append) and QObject::connect.

The site

site/ is the page ravving serves at http://<device>:8098/help/ (the shortcuts, the features and the documentation; site/README.md says how it is made and how to retake a screenshot). It is installed as it is (install(DIRECTORY site …), this README left out), so it must be plain static files with relative references, and its documentation pages are generated into the repository:

python3 tools/build-site-docs.py          # README.md, docs/*.md, data/secret/README.md → site/docs/*.html
python3 tools/build-site-docs.py --list   # the pages
python3 tools/build-site-docs.py --plain  # the script's own converter, as on a machine without python-markdown

The page is public at https://ravving.github.io/: sh tools/publish-site.sh copies site/ (this README left out) into a clone of the ravving/ravving.github.io repository, commits it under the source commit and pushes; that repository's workflow deploys its own content as the Pages artifact on every push. Nothing there needs access to this repository (which may be private) and no secret is kept anywhere. Run it once site/ is committed.

The rule (README, "Documentation"): the docs and the page follow every change, in the same commit; python3 tools/build-site-docs.py --check (ctest site-docs-current) fails when the rendered pages no longer match the markdown.

Run it after editing a doc and commit site/docs/ with the markdown. It uses python-markdown when it is installed (Arch python-markdown, Debian python3-markdown) and its own small converter otherwise; PAGES in the script lists the documents, their groups and blurbs.
