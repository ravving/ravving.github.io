    Building

    What ravving is made of, the dependencies, the CMake layout, the build folders, faster builds, the site, the documentation rules.

    What ravving is made of

    What ravving is made of, all taken from the device (nothing is bundled, by the AppImage either): ravving runs on the Zynthbox QtQuick Controls style (qml-style-zynthbox, picked by name in main.cpp, so there is no build-time check: a missing style shows the Basic look and unthemed controls), and that style imports io.zynthbox.ui (ZUI, from qml-module-zynthbox: Button, CheckBox, Switch, Menu and TextField read their theme from it) and the KDE Frameworks it draws with (Kirigami, KSvg, Plasma). The audio engine comes from libzynthbox (io.zynthbox.components) and zyncoder, both loaded at run time. So the order is: libzynthbox + zyncoder, qml-module-zynthbox, qml-style-zynthbox, then ravving; on a stock Zynthbox they are the installed libzynthbox, qml-module-zynthbox and qml-style-zynthbox packages, and a rebuilt module or style must be installed before ravving is tried. The music player plays through Qt Multimedia (qt6-multimedia-dev to build; libqt6multimedia6 with its FFmpeg plugin at run time, both on the image; its sound goes out through PulseAudio, so ravving's service wants pipewire-pulse.service, which a Zynthbox has but leaves off; the player's stream runs at its own adapted quantum and leaves the graph at 256 frames, 48 kHz), and the exports use TagLib (libtag1-dev), zlib and libsndfile with its FLAC, Vorbis and LAME encoders.

    The sound itself comes from programs and data the Zynthbox image ships, started and wired by ravving at run time and bundled by nothing: jalv (the LV2 host) with the LV2 plugins the machines and effects name by URI in data/kits.json and src/backend/ (TAL NoiseMaker, DISTRHO Nekobi, Calf Monosynth, Calf Crusher and Phaser, Dragonfly Room Reverb, TAP Echo; tools/lv2probe.sh checks a URI on the device), FluidSynth 2 for the drum kits and the soundfont sound sources, the soundfonts under /zynthian/zynthian-data/soundfonts (the SFZ Drum Machines kits, SF2 Instruments with FluidR3Mono_GM.sf3 and ACBass.sf3), and PipeWire's JACK (pw-jack) with Zynthbox's MIDI routing (ZLRouter, a2j). A machine whose plugin or soundfont is missing starts silent and says so in the journal; engines.md has what each engine does and expects.

    Dependencies

    On the device (Debian 13 arm64, as a Zynthbox image is) the build needs, by Debian name:

    For Packages
    the toolchain cmake, ninja-build, g++, pkg-config
    Qt 6 (Core, Gui, Qml, Quick, QuickControls2, Concurrent, Network, DBus, Multimedia) qt6-base-dev, qt6-declarative-dev, qt6-multimedia-dev
    Bluetooth (KDE's BluezQt over BlueZ's D-Bus API) libkf6bluezqt-dev
    the audio processors and the graph probe (JACK's API; PipeWire's library at run time) libjack-jackd2-dev
    exports: the audio files, their tags, the .ravv bundles libsndfile1-dev, libtag-dev (TagLib 2; libtag1-dev on older images), zlib1g-dev
    the tools (tools/*.py) and syncing a checkout python3, rsync

    Everything else ravving needs it finds at run time on a stock Zynthbox: libzynthbox and zyncoder, qml-module-zynthbox and qml-style-zynthbox with the KDE Frameworks they draw with (Kirigami, KSvg, Plasma), libqt6multimedia6 with its FFmpeg plugin, PipeWire with pipewire-jack (pw-jack), pipewire-bin (pw-loopback, pw-link, pw-dump, pw-top) and pipewire-pulse (left off by the image; ravving's service wants it), udisks2 and util-linux (USB sticks: udisksctl, lsblk), jalv with the LV2 plugins and FluidSynth with the soundfonts named below. Bluetooth needs three packages the image lacks, bluez-obexd, libspa-0.2-bluetooth and libkf6bluezqt6, plus two drop-ins ravving installs: tools/bluetooth-setup.sh does all of it (packaging.md, "Bluetooth on a fresh device").

    tools/device.sh deploy                 # from the laptop: sync, build, install, restart, wait
# or by hand (rsync without -a: older laptop mtimes would make ninja skip changed files)
rsync -rlp --checksum --exclude build --exclude .git ./ root@milo.local:/root/ravving/
ssh root@milo.local
cd /root/ravving
cmake -S . -B build -G Ninja -DCMAKE_INSTALL_PREFIX=/usr
cmake --build build && cmake --install build
systemctl --user daemon-reload
systemctl --user start ravving        # try it once: stops zynthbox-qml (the services conflict)
systemctl --user start zynthbox-qml   # and back

    To make ravving the device's UI (it starts at boot, and zynthbox-qml is masked so nothing brings it back), and to return to stock Zynthbox with nothing of ravving left in systemd:

    /usr/share/ravving/default-app.sh ravving
/usr/share/ravving/default-app.sh zynthbox           # add --purge to uninstall ravving too
/usr/share/ravving/default-app.sh status

    From the laptop, tools/device.sh default ravving|zynthbox|status does the same. default-app.sh run ravving|zynthbox switches for the session only (the boot default stays), which is what ravving's own menu offers under POWER → ZYNTHBOX.

    The QML

    The QML is compiled into the binary (the Ravving QML module: qmlcachegen bytecode and C++ for typed bindings), so a QML change is a rebuild like any other, and QML errors show at build time. To try QML on the device without rebuilding, copy the qml/ folder over and start ravving with RAVVING_QML_DIR pointing at it.

    Run on a desktop

    cmake -S . -B build -G Ninja && cmake --build build
RAVVING_WINDOWED=1 RAVVING_NO_ZYNTHBOX=1 RAVVING_STYLE=Basic ./build/ravving
# or straight from the source tree's QML, no rebuild between QML edits:
RAVVING_WINDOWED=1 RAVVING_NO_ZYNTHBOX=1 RAVVING_STYLE=Basic RAVVING_QML_DIR=$PWD/qml ./build/ravving

    On a desktop without a terminal, Qt logs to journald; add QT_FORCE_STDERR_LOGGING=1 to see QML warnings.

    Keys (they send the same events as the device): 1–5 number keys · q w e r t y u i a s d f g h j k the 16 step keys · arrows · Enter select · Esc back · Space play · Backspace stop · o metronome · m menu · z/x, c/v, b/n knobs 1–3 down/up · ,/. big knob.

    Environment variables

    Variable Effect
    RAVVING_WINDOWED=1 windowed instead of fullscreen
    RAVVING_NO_ZYNTHBOX=1 skip libzynthbox (UI only)
    RAVVING_STYLE Quick Controls style (default Zynthbox)
    RAVVING_QML_DIR read the QML from this folder (a source tree's qml/) instead of the copy compiled in
    RAVVING_DATA_DIR read kits.json and the theme (plasma/desktoptheme/) from this folder (desktop: $PWD/data; the plasmarc then comes from build/config/)
    RAVVING_HOME one folder for everything ravving writes (config/, state/, cache/, library/), for a sandboxed run
    RAVVING_LIBRARY the library alone (projects, presets, samples, recordings) somewhere else
    RAVVING_PROJECT_DIR the session folder alone (default ~/.local/state/ravving)
    RAVVING_SCREENSHOT_DIR capture every page to PNGs there, then quit
    RAVVING_GDB=1 (service) run under gdb, backtrace to the journal
    QT_LOGGING_RULES="ravving.cuia.debug=true" log every hardware event (CUIA, knobs)

    For the service, set them with systemctl --user set-environment NAME=value and clear them with unset-environment.

    Project layout

    One CMake project, its targets each with the CMakeLists.txt of their sources (the source files themselves are where they were: the split is of the CMake files only):

    File Owns
    CMakeLists.txt the project: version, C++ standard, AUTOMOC, qt_standard_project_setup, the dependencies (find_package Qt6 / KF6BluezQt / ZLIB, pkg_check_modules jack / sndfile / taglib), RAVVING_DATA_INSTALL_DIR and RAVVING_THEME, the build options (RAVVING_QML_AOT, RAVVING_PCH, RAVVING_TIME_TRACE, RAVVING_UNITY, RAVVING_IWYU, RAVVING_TESTS) with ravving_build_settings(<target>), their per-target side; the add_subdirectory calls; the generated files (VERSION, config/plasmarc) and the install rules of the project as a whole (data/, the theme, systemd and WirePlumber drop-ins, the desktop entry and icons)
    src/backend/CMakeLists.txt ravving_backend, the static backend library (src/backend/* and src/zynthboxbridge.*): its sources, its PUBLIC include directories (src/, so the app includes backend/xxx.h; src/backend/, so its files include each other bare), its PUBLIC link set (the Qt modules, JACK, sndfile, TagLib, zlib, BluezQt), the RAVVING_* compile definitions, the unity build
    src/CMakeLists.txt ravving, the app: src/*.cpp, the Ravving QML module over qml/ at the repository root (each file's path from there is its resource alias, so the resources stay qrc:/qt/qml/Ravving/qml/… and the module's qmldir stays at build/Ravving), RAVVING_QML_AOT, the branding resources and the shaders, the link to ravving_backend, the binary's install rule; the binary itself stays at build/ravving
    setup/CMakeLists.txt ravving-setup, the AppImage's setup program (build/setup/ravving-setup)
    tests/CMakeLists.txt the laptop-side tests, built with -DRAVVING_TESTS=ON

    Target names, options, output paths and the install layout are those tools/device.sh, tools/build-appimage.sh, tools/static-analysis.sh and tools/build-profile.sh rely on; a new backend class goes into src/backend/CMakeLists.txt, a new QML file into src/CMakeLists.txt's RAVVING_QML_FILES.

    The build folders

    Folder Where What for Settings
    build/ laptop and device the development loop: tools/device.sh deploy, ctest RAVVING_QML_AOT=OFF, RAVVING_PCH=ON
    build-release/ device the Store AppImage (tools/build-appimage.sh, configured there on each run) Release at -O2 (no debug information; binaries stripped at install), RAVVING_QML_AOT=ON, RAVVING_PCH=ON, prefix /usr

    Neither is ever removed by the tools: device.sh deploy syncs the source with --exclude '/build*' (so its --delete leaves both alone on the device), REMOVE RAVVING and the release check uninstall only what cmake --install put on the system, and the AppImage build clears only its staging trees (build-release/stage, build-release/appimage). Keeping them is what keeps builds incremental.

    Faster builds

    The development build (build/) compiles about twice as fast as the release build: the QML as bytecode only and the Qt headers precompiled. The device (a Pi 5, 4 cores) takes about as long as a 4-core laptop for the same work.

    • RAVVING_QML_AOT (default ON). qmlcachegen compiles each QML file's bindings into C++, which then has to be compiled: on the Pi that is 40 % of a build. OFF keeps the QML precompiled but as bytecode only (--only-bytecode): the bindings run in Qt's interpreter and JIT, which is fine to develop with; a release keeps ON (build-release/).
    • RAVVING_PCH (default ON): the Qt headers nearly every file includes (QObject, QString, QVariant, the containers, QDebug, QJsonDocument…) parsed once instead of in each of ~90 files.
    • ccache is used when it is installed (CMAKE_CXX_COMPILER_LAUNCHER): a file compiled before with the same flags comes from its cache (after a reconfigure, switching branches).
    • The device builds at the lowest priority (nice -n 19 ionice -c 3 in device.sh deploy): not faster, but a build beside the music does not take the audio's time.
    • The backend is a library of its own. src/backend (and zynthboxbridge) build as the static library ravving_backend, outside the QML module: Qt's type registration reads the metadata of every QObject class in the QML module's target, so a backend header inside it would regenerate every QML file's compiled C++. QML reaches the backend through context properties (studio, ravving…), which need no registration; the LOOP / SONG values of Sections are two numbers in Rave.qml (Rave.sectionsLoop, Rave.sectionsSong). A backend header edit recompiles no QML.

    A corrupted ninja log rebuilds everything

    ninja: warning: premature end of file; recovering means build/.ninja_deps was cut short (a build killed mid-run, two builds at once in one folder): ninja then trusts nothing it built and plans every step on every build. ninja -C build -t recompact, then one full build, puts it right. Never run two builds in one build folder; let a build finish rather than kill it.

    Profiling the build

    tools/build-profile.sh [OUT_DIR] [-- cmake options] builds ravving from clean with clang and -ftime-trace (RAVVING_TIME_TRACE) in analysis/build-profile/build (never build/), then:

    • analysis.txt, ClangBuildAnalyzer's report: the slowest files to parse and to compile, the most expensive headers (where they come from, how often), the costliest template sets and functions;
    • trace.json, ninjatracing over .ninja_log: the build's timeline, one lane per job; open it in https://ui.perfetto.dev (or chrome://tracing) to see what holds the four cores up (moc's mocs_compilation.cpp, a slow file at the end, qmlcachegen's steps).

    The tools: clang (Arch's), ClangBuildAnalyzer and ninjatracing in ~/.local/bin (built from their git checkouts in ~/.local/src), include-what-you-use from the AUR (yay -S include-what-you-use).

    include-what-you-use: cmake -B analysis/iwyu -DRAVVING_IWYU=ON -DRAVVING_PCH=OFF and build ravving_backend there: each file's compile prints what to add, what to remove and which includes a forward declaration would replace (analysis/iwyu.log). Precompiled headers off, or it reports their includes as unused everywhere. Read it with care: it knows no Qt mapping (it would swap <QVariantMap> for Qt's internal <qvariant.h>: ignore those), and it does not see moc's generated code, so it calls a header unneeded where a Q_PROPERTY exposes a pointer to that class (machine.h's SoundControls and TrackEffects, devicecontrols.h's Wifi): moc needs the complete type there.

    Unity builds (RAVVING_UNITY, the backend only: the app target carries qmlcachegen's and rcc's generated sources, and AUTOMOC's mocs_compilation.cpp stays out of the batches on its own) are there to measure, not on by default: many backend files define file-local constants with the same names (MaxBars, AuditionMs…), which collide once a batch merges them.

    The site

    site/ is the page ravving serves at http://<device>:8098/help/ (the shortcuts, the features and the documentation; site/README.md says how it is made and how to retake a screenshot). It is installed as it is (install(DIRECTORY site …), this README left out), so it must be plain static files with relative references, and its documentation pages are generated into the repository:

    python3 tools/build-site-docs.py          # docs/*.md, data/secret/README.md → site/docs/*.html
python3 tools/build-site-docs.py --list   # the pages
python3 tools/build-site-docs.py --plain  # the script's own converter, as on a machine without python-markdown

    The same run writes site/docs/search.json, the index behind the SEARCH box in every docs page's sidebar (every section, its heading and text): the search runs in the browser alone, so it works on the public page and on the device's own copy without internet. --check (the site-docs-current test) compares the pages and the index with what the markdown gives.

    Only the developer docs (docs/) and the packs page are rendered; the webpage's manual is docs/manual-interim.md until the user guide (guide/) replaces it. The script never reads notes/, guide/_material/ or .claude/, and two tests keep it so:

    • docs-fences (tools/check-docs-fences.py): no page in PAGES lives in those folders, and no rendered page links or includes anything from them;
    • docs-history (tools/check-docs-history.py): no page in PAGES tells history or carries the wording of the requests behind a feature (dates, used to, found on milo, the design reference's name…: the phrases of tools/check-cpp-docs.py's BANNED list and a few more).

    The page is public at https://ravving.github.io/: sh tools/publish-site.sh copies site/ (this README left out) into a clone of the ravving/ravving.github.io repository, commits it under the source commit and pushes; that repository's workflow deploys its own content as the Pages artifact on every push. Nothing there needs access to this repository and no secret is kept anywhere. Run it once site/ is committed.

    The rule ("The documentation rules", below): the docs and the page follow every change, in the same commit; python3 tools/build-site-docs.py --check (ctest site-docs-current) fails when the rendered pages do not match the markdown.

    The C++ API reference is site/api/, generated by QDoc from the sources' /*! */ blocks with python3 tools/build-api-docs.py (Qt 6's qdoc; --check is ctest api-docs-current) and committed the same way; writing-code-docs.md has the rules and the details.

    Run it after editing a doc and commit site/docs/ with the markdown. It uses python-markdown when it is installed (Arch python-markdown, Debian python3-markdown) and its own small converter otherwise; PAGES in the script lists the documents, their groups and blurbs.

    The documentation rules

    • The docs and the page follow every change. A feature added, changed or removed is not done until the same commit updates what says it: the developer docs (docs/*.md) it belongs in, the manual (docs/manual-interim.md, until the user guide in guide/ replaces it), and the page in site/ (the SHORTCUTS row of a key, the FEATURES highlight or grouped item of a feature, translated through po-site/), then python3 tools/build-site-docs.py. Push, then sh tools/publish-site.sh puts it at https://ravving.github.io/; the device's copy follows the next deploy.
    • The docs say what the code does now. No dates, no history, no measurements of the day, no traps met, no wording from the requests behind a feature: those are kept for the maintainers outside the published docs (ctest -R docs-history enforces the phrases).
    • Every new or changed C++ API comes with its QDoc in the same commit (writing-code-docs.md; ctest -R cpp-docs, ctest -R api-docs-current).
    • Every release has its translations reviewed (translations.md).
