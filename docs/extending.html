    Extending

    Adding a machine, an engine, SOUND MODIFIERS, an effect, an issues-center check.

    The recipes for growing ravving. Read architecture.md first for the layers; this is the how-to. The code rules hold throughout:

    • reuse a part before writing a new one;
    • keep each class to one job;
    • give every public API its QDoc block in the .cpp (writing-code-docs.md);
    • give every non-obvious line an inline comment that says why.

    A new machine (a page's instrument)

    The drums and the bass share everything except what is specific to them. A new machine (CHORDS, LEAD, SAMPLER) follows the same path.

    1. Backend: a Machine subclass

    In src/backend/machine.h. It inherits the pattern, bars, presets, level, pan, pause, mute, effects, LIVE play and STEP entry. Implement:

    • onAttached(): write the machine's own state into its libzynthbox pattern;
    • refresh(): publish the bar on screen to QML (its own Q_PROPERTYs + stepsChanged);
    • revoice(): rewrite every step's velocity (mute/solo/kick modes changed);
    • clearOwnSteps(), applyChart(chart), chart(): its preset format (a chart is a map of strings, one character per step, so preset files stay readable);
    • placeHit(position, key, accented), liveNotes(key), liveVelocity(key, accented): what a live key writes and plays (a list of notes: one for a row or a mono note, a whole chord for ChordMachine).

    Saving and opening

    • state(): everything it keeps (call Machine::state() and add to it: its steps, kit, sound…); a project file is exactly this, so it must be complete;
    • restoreContent(state): take that back while running (opening a project) and write the pattern. An empty state means its defaults: the default preset, kit and sound.
    • In a state, a missing key means "default", and a present but empty one means "empty", so a cleared pattern stays cleared.
    • Call restoreContent from the constructor too, so start-up and opening share one path, as MonoMachine and ChordMachine do.

    Write steps through addSubnote/setSubnoteMetadata: velocity −1 is silent, and the duration is in pattern ticks via stepTicks(). Call markEdited() after a user change.

    2. Data

    • an entry in kits.json's machines: key, kind, track, zynthianChannel, engine, sound, presets, defaultPreset, baseNote… Tracks and channels must be unused.
    • a presets file, data/<machine>-presets.json ({presets: [{name, genre, chart}]}), installed by CMakeLists.txt.

    A new instance of an existing kind, like another mono synth, needs nothing else in C++.

    3. Studio

    In studio.cpp's loadKits(), a new kind is one more kind == branch creating it. addMachine() then wires it up generically (attachMachine()): saving, ❚❚, the track lane, sends, the engine, DRIVE, SOUND MODIFIERS and expressions. It appears as studio.machines.<key>.

    4. QML: a MachinePanel subclass

    Like MonoMachinePanel.qml and ChordMachinePanel.qml, with the toolbar and editor as children. Override what MachinePanel declares:

    • stepLeds, and liveKeyDown/Up: what pads do while LIVE;
    • stepKey, and moveSelection(dy): ▲ ▼ in the editor, false at the edge;
    • keyForNote / padForKey: what a keyboard note plays and which pad lights.

    Light live notes from heldKeys.

    5. QML: the page

    A MachinePage declaring its panel (see pages/ChordsPage.qml); it forwards the device and an external keyboard to it.

    6. Build files and finish

    Add the C++ files to src/backend/CMakeLists.txt and the QML files to src/CMakeLists.txt (RAVVING_QML_FILES). Add a screenshot step in src/main.cpp, and the machine to Rave.machines, with its finish colours as strings.

    A new engine

    Engines are SoundEngine subclasses (soundengine.h): start(), reconfigure(config), midiInputPort(), audioOutputPorts() (left, right), optional setControl(symbol, value), and the started signal. SoundEngine::createEngine() picks one by the type of the kits.json engine object:

    • "jalv" (JalvEngine): any LV2 instrument, e.g. {"type": "jalv", "uri": "http://distrho.sf.net/plugins/Nekobi", "controls": {"volume": 75}}. Ports and control indexes come from lv2info (cached per URI); a mono output is sent to both sides. Nothing else is needed for a new LV2 synth.
    • "fluidsynth" (FluidSynthEngine): soundfonts (the drum kits).

    A new kind (setBfree, sfizz, a sampler…) is one more subclass run through ConsoleProcess (libzynthbox's ProcessWrapper: restarted on a crash, startup commands, a console prompt) and one more type in createEngine(). Choose an engine by measuring it first (debugging.md: synthprobe/analyse): velocity response, glide, CPU (top), level.

    SOUND MODIFIERS: an engine's own controls

    A machine's SOUND MODIFIERS are data: its sound in kits.json, which Machine turns into a SoundControls (machine.sound). Cards of knobs, each driving an engine port by its LV2 symbol, a 0..1 knob mapped onto min..max (linearly, or "curve": "log" for ports the engine treats as logarithmic), with a 0..1 default:

    "sound": [
  { "title": "FILTER", "knobs": [
      { "name": "CUTOFF", "symbol": "cutoff", "min": 300, "max": 9000, "curve": "log", "default": 0.55 } ] },
  { "title": "TONE", "knobs": [
      { "name": "WAVE", "default": 0, "choices": [
          { "label": "SAW",  "controls": { "osc1waveform": 0,   "osc1pw": 0.5 } },
          { "label": "JUNO", "controls": { "osc1waveform": 0.5, "osc1pw": 0.75 } } ] } ] } ]
    • A knob with choices is a switch: its value snaps to choice i of n at i / (n − 1). It shows as a WaveCycler, which draws SAW, SQR, TRI and SIN. Each choice sets its controls (several ports; give every choice the same ports) or a value for the knob's symbol.
    • Ports with no knob go in engine.controls.
    • A live control a page plays, like the ribbon's vibrato, is an expression: "expressions": {"vibrato": {"symbol": "lfo2pitch", "max": 60}}, played with machine.setExpression("vibrato", amount).

    Get the ports right from the mods

    Every engine Zynthbox ships has an engine mod whose docs/RESEARCH.md decodes its ports from the engine's own source:

    • which ports are logarithmic;
    • how enums quantise (TAL: i / den, rounded, 1-based);
    • which envelope drives what (Calf: EG1 → cutoff, EG2 → amp);
    • what a port called volume really does.

    Read it before writing a machine's engine.controls and sound, and record what ravving relies on in engines.md. Read a plugin's port ranges with lv2info, and check what the numbers mean in its source: an LV2 range isn't always the unit its own GUI shows.

    Studio connects the controls to the engine, and sends them all whenever it starts or restarts. The values are saved with the machine.

    A new effect

    • On the track lane (EQ, COMPRESSOR, SIDECHAIN, PAN): an entry in EffectChain::effects() (name, knobs, defaults, shared or per machine) and its mapping in TrackEffects::apply() onto the JackPassthrough lane's properties.
    • An insert (DRIVE): a JalvPlugin per machine, created in Studio::attachMachine().
    • It goes to TrackEffects, which maps the knobs onto its controls and starts it on first use, and to JackWiring::addSynth(…, insert).
    • TrackEffects::driveSwitched → JackWiring::setInsertActive() puts it in the path only while it's on, so the dry sound never depends on the extra process.
    • Calibrate its gain staging with lv2probe.sh.
    • A send (REVERB, DELAY): one shared JalvPlugin in GlobalEffects, fed from every lane's wet outputs (JackWiring::addSends) and returned with addEffectReturn.
    • On the master (LIVE FX: CRUSH, PHASER, STUTTER/LOOP): LiveFx and JackWiring::setMasterInserts, which takes any AudioInsert.
    • Your own DSP (BeatRepeat): an AudioInsert subclass opening its own JACK client (libjack, linked through pkg-config; PipeWire's at run time). Keep the process callback lock-free: atomics from the GUI thread, buffers allocated in the constructor, no Qt calls. For musical timing, ZynthboxBridge::timerTickAtFrame(jack_frame_time()) gives the transport position sample-accurately.

    Hardware and focus

    • Handle keys with the Hardware attached property (like Keys); an unaccepted event bubbles to the parent. See architecture.md for the signal list.
    • A machine's vertical order (strip → SOUND MODIFIERS → editor → SOUND EFFECTS) lives in MachineModule: pages only call focusUp() / focusDown() at their editor's edge.
    • Knob-driven controls go in a KnobGroup (targets need value, from, to, knobStep, fineStep, knobBadge, knobPending: RaveKnob, RaveFader, WaveCycler have them).
    • Menus: RaveComboBox (drop-downs) and ChoicePopup (grids: kits, presets) already take the arrows, the big knob, SELECT and BACK, and hand the focus back on close.

    Before committing

    1. Build clean, with no warnings.
    2. Run the desktop screenshots, with no QML warnings.
    3. Deploy, and check on the device: a screenshot and a measurement.
    4. Update the docs this change touches, and the webpage's features or shortcuts.
    5. Rebuild the site's pages, then commit.

    A gotcha met on the way goes to notes/ for the maintainers, not into these docs.

    A change the user can undo goes through the project's history: see "The undo history" in architecture.md.

    Reporting a problem to the issues center

    Every component owns a check pass: at start, and whenever something fails or recovers, it tells the center (src/backend/diagnostics.h):

    #include "diagnostics.h"
Issues::report(QStringLiteral("wiring"), QStringLiteral("sound"), QStringLiteral("warning"),
               QStringLiteral("Some audio connections are missing"),          // the title, the user's words
               QStringLiteral("some ports never appeared…"),                  // the detail: what was seen
               QStringLiteral("Pick the sound again, or restart ravving."),   // what to do
               QStringLiteral("restart"));                                   // an action button, or ""
Issues::clear(QStringLiteral("wiring"));                                     // once it works again

    Rules:

    • A stable id per problem. Reporting it again updates it and counts it.
    • The level: error when something doesn't work, warning when it works worse or will stop, and notice for what's worth knowing, like a desktop without device keys.
    • Always a suggestion the user can follow.
    • Clear it from the same place that would see it recovered.

    A library's stderr line can become an issue through StderrWatch's pattern table (src/stderrwatch.cpp). tools/issues-test.sh exercises the center over the fifo.
