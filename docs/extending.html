    Under the hood / docs/extending.md

    Extending

    Adding a machine, an engine, SOUND MODIFIERS, an effect, an issues-center check.

    The recipes for growing ravving the way the drums and the bass were built. Read architecture.md first for the layers; this is the how-to. The code rules hold throughout: reuse a part before writing a new one, keep each class to one job, and give every public API a doc comment and every non-obvious line an inline one.

    A new machine (a page's instrument)

    The drums and the bass share everything except what is specific to them. A new machine (CHORDS, LEAD, SAMPLER) follows the same path.

    1. Backend: a Machine subclass (src/backend/machine.h). It inherits the pattern, bars, presets, level/pan/pause/mute, effects, LIVE play and STEP entry. Implement: - onAttached(): write the machine's own state into its libzynthbox pattern; - refresh(): publish the bar on screen to QML (its own Q_PROPERTYs + stepsChanged); - revoice(): rewrite every step's velocity (mute/solo/kick modes changed); - clearOwnSteps(), applyChart(chart), chart(): its preset format (a chart is a map of strings, one character per step, so preset files stay readable); - placeHit(position, key, accented), liveNotes(key), liveVelocity(key, accented): what a live key writes and plays (a list of notes: one for a row or a mono note, a whole chord for ChordMachine); - state(): everything it keeps (call Machine::state() and add to it: its steps, kit, sound…); a project file is exactly this, so it must be complete; - restoreContent(state): take that back while running (opening a project) and write the pattern; an empty state means its defaults (the default preset, kit, sound). Call it from the constructor too, so start-up and opening share one path (MonoMachine and ChordMachine do). A missing key means "default", a present but empty one means "empty" (a cleared pattern stays cleared). Write steps through addSubnote/setSubnoteMetadata (velocity −1 = silent, duration in pattern ticks via stepTicks()), and call markEdited() after a user change.
    2. Data: an entry in kits.json's machines (key, kind, track, zynthianChannel, engine, sound, presets, defaultPreset, baseNote…; tracks and channels must be unused) and a presets file (data/<machine>-presets.json, {presets: [{name, genre, chart}]}), installed by CMakeLists.txt. A new instance of an existing kind (another mono synth) needs nothing else on the C++ side.
    3. Studio (studio.cpp, loadKits()): a new kind is one more kind == branch creating it; addMachine() then wires saving, ❚❚, the track lane, sends, the engine, DRIVE, SOUND MODIFIERS and expressions generically (attachMachine()), and it appears as studio.machines.<key>.
    4. QML: a MachinePanel subclass (see MonoMachinePanel.qml, ChordMachinePanel.qml): the toolbar and editor as children, and the overrides MachinePanel declares: stepLeds, liveKeyDown/Up (what pads do while LIVE), stepKey, moveSelection(dy) (▲ ▼ in the editor; false at the edge), keyForNote / padForKey (what a keyboard note plays and which pad lights). Light live notes from heldKeys.
    5. QML: the page: a MachinePage declaring its panel (see pages/ChordsPage.qml); it forwards the device and an external keyboard to it.
    6. Add the C++ files to src/backend/CMakeLists.txt and the QML files to src/CMakeLists.txt (RAVVING_QML_FILES), a screenshot step in src/main.cpp, and the machine to Rave.machines (finish colours: strings).

    A new engine

    Engines are SoundEngine subclasses (soundengine.h): start(), reconfigure(config), midiInputPort(), audioOutputPorts() (left, right), optional setControl(symbol, value), and the started signal. SoundEngine::createEngine() picks one by the type of the kits.json engine object:

    • "jalv" (JalvEngine): any LV2 instrument, e.g. {"type": "jalv", "uri": "http://distrho.sf.net/plugins/Nekobi", "controls": {"volume": 75}}. Ports and control indexes come from lv2info (cached per URI); a mono output is sent to both sides. Nothing else is needed for a new LV2 synth.
    • "fluidsynth" (FluidSynthEngine): soundfonts (the drum kits).

    A new kind (setBfree, sfizz, a sampler…) is one more subclass run through ConsoleProcess (libzynthbox's ProcessWrapper: restarted on a crash, startup commands, a console prompt) and one more type in createEngine(). Choose an engine by measuring it first (debugging.md: synthprobe/analyse): velocity response, glide, CPU (top), level.

    SOUND MODIFIERS: an engine's own controls

    A machine's SOUND MODIFIERS are data: its sound in kits.json, which Machine turns into a SoundControls (machine.sound). Cards of knobs, each driving an engine port by its LV2 symbol, a 0..1 knob mapped onto min..max (linearly, or "curve": "log" for ports the engine treats as logarithmic), with a 0..1 default:

    "sound": [
  { "title": "FILTER", "knobs": [
      { "name": "CUTOFF", "symbol": "cutoff", "min": 300, "max": 9000, "curve": "log", "default": 0.55 } ] },
  { "title": "TONE", "knobs": [
      { "name": "WAVE", "default": 0, "choices": [
          { "label": "SAW",  "controls": { "osc1waveform": 0,   "osc1pw": 0.5 } },
          { "label": "JUNO", "controls": { "osc1waveform": 0.5, "osc1pw": 0.75 } } ] } ] } ]

    A knob with choices is a switch (its value snaps to choice i of n at i / (n − 1)) and shows as a WaveCycler (SAW, SQR, TRI, SIN are drawn); each choice sets its controls (several ports; give every choice the same ports) or a value for the knob's symbol. Ports with no knob go in engine.controls. A live control a page plays (the ribbon's vibrato) is an expression: "expressions": {"vibrato": {"symbol": "lfo2pitch", "max": 60}}, played with machine.setExpression("vibrato", amount).

    Get the ports right from the mods. Every engine Zynthbox ships has a mod in ~/Coding/<engine>_mod/ whose docs/RESEARCH.md decodes its ports from the engine's own source: which are logarithmic, how enums quantise (TAL: i / den, rounded, 1-based), which envelope drives what (Calf: EG1 → cutoff, EG2 → amp), what a port called volume really does. Read it before writing a machine's engine.controls and sound, and record what ravving relies on in engines.md. Studio connects the controls to the engine and sends them all whenever it (re)starts; values are saved with the machine. Read a plugin's port ranges with lv2info and check what its numbers mean in its source: an LV2 range is not always the unit its own GUI shows.

    A new effect

    • On the track lane (EQ, COMPRESSOR, SIDECHAIN, PAN): an entry in EffectChain::effects() (name, knobs, defaults, shared or per machine) and its mapping in TrackEffects::apply() onto the JackPassthrough lane's properties.
    • An insert (DRIVE): a JalvPlugin per machine created in Studio::attachMachine(), given to TrackEffects (which maps the knobs onto its controls and starts it on first use) and to JackWiring::addSynth(…, insert); TrackEffects::driveSwitched → JackWiring::setInsertActive() moves it into the path only while on, so the dry sound never depends on the extra process. Calibrate its gain staging with lv2probe.sh.
    • A send (REVERB, DELAY): one shared JalvPlugin in GlobalEffects, fed from every lane's wet outputs (JackWiring::addSends) and returned with addEffectReturn.
    • On the master (LIVE FX: CRUSH, PHASER, STUTTER/LOOP): LiveFx and JackWiring::setMasterInserts, which takes any AudioInsert.
    • Your own DSP (BeatRepeat): an AudioInsert subclass opening its own JACK client (libjack, linked through pkg-config; PipeWire's at run time). Keep the process callback lock-free: atomics from the GUI thread, buffers allocated in the constructor, no Qt calls. For musical timing, ZynthboxBridge::timerTickAtFrame(jack_frame_time()) gives the transport position sample-accurately.

    Hardware and focus

    • Handle keys with the Hardware attached property (like Keys); an unaccepted event bubbles to the parent. See architecture.md for the signal list.
    • A machine's vertical order (strip → SOUND MODIFIERS → editor → SOUND EFFECTS) lives in MachineModule: pages only call focusUp() / focusDown() at their editor's edge.
    • Knob-driven controls go in a KnobGroup (targets need value, from, to, knobStep, fineStep, knobBadge, knobPending: RaveKnob, RaveFader, WaveCycler have them).
    • Menus: RaveComboBox (drop-downs) and ChoicePopup (grids: kits, presets) already take the arrows, the big knob, SELECT and BACK, and hand the focus back on close.

    Before committing

    Build clean (no warnings), run the desktop screenshots (no QML warnings), deploy, check on the device (screenshot + measurement), update architecture.md and these guides, then commit as a single line authored by the user.

    Reporting a problem to the issues center

    Every component owns a check pass: at start, and whenever something fails or recovers, it tells the center (src/backend/diagnostics.h):

    #include "diagnostics.h"
Issues::report(QStringLiteral("wiring"), QStringLiteral("sound"), QStringLiteral("warning"),
               QStringLiteral("Some audio connections are missing"),          // the title, the user's words
               QStringLiteral("some ports never appeared…"),                  // the detail: what was seen
               QStringLiteral("Pick the sound again, or restart ravving."),   // what to do
               QStringLiteral("restart"));                                   // an action button, or ""
Issues::clear(QStringLiteral("wiring"));                                     // once it works again

    Rules: a stable id per problem (reporting it again updates and counts it); error when something does not work, warning when it works worse or will stop, notice for what is worth knowing (a desktop without device keys); always a suggestion the user can follow; clear it from the same place that would see it recovered. A library's stderr line can become an issue through StderrWatch's pattern table (src/stderrwatch.cpp). tools/issues-test.sh exercises the center over the fifo.
