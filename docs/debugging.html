    Debugging

    Device recipes and the traps met so far.

    How ravving was tested while it was built, and the tools in tools/ that do it. Everything here runs from the laptop against the device (root@milo.local; set DEVICE= for another). The device's root shell is zsh.

    The tools

    Tool Runs on What it does
    tools/device.sh laptop deploy, press keys (CUIA), tap, screenshot, play MIDI, read the log
    tools/midifile.py either write a MIDI file holding a note or a chord, to play in as a keyboard
    tools/meter.py device level, brightness and crest factor of any JACK ports
    tools/synthprobe.py device play a scripted note list straight into an engine and record it
    tools/analyse.py device measure a synthprobe recording: segments and a pitch track
    tools/lv2probe.sh device try an LV2 effect on a live signal before wiring it in
    tools/record.py device record JACK ports to a numpy file
    tools/repeatcheck.py either how exactly a recording repeats at a given length (STUTTER / LOOP)
    tools/default-app.sh device make ravving the device's UI, or go back to zynthbox-qml (device.sh default …)
    tools/boot-timing.sh laptop time ravving's start by phase over restarts or reboots
    tools/qml-profile.sh laptop record and summarise a QML profiler trace of a start
    tools/qml-profile-summary.py laptop read a .qtd trace: self time per type, file and event
    tools/static-analysis.sh laptop clang-tidy and clazy over src/
    tools/bt-diagnose.sh device why a Bluetooth device does (not) connect or play, read-only (device.sh bt [ADDR]); device.sh bt capture records an HCI trace
    tools/audio-impact.sh laptop what the rest costs the sound: frames/s, CPU per thread group, realtime page faults, xruns, idle and playing

    The quality and performance checks (what to run when, the baselines, the traps met) are in quality.md.

    sh tools/device.sh tools copies the device-side ones to its /tmp. They need python3-jack and numpy there (installed on milo) and must run under pw-jack: a plain JACK client would start its own jackd.

    When ravving stops unexpectedly

    The service comes back on its own (Restart=always: startx leaves with 0 even when ravving dies under it, so on-failure never fired; at most 5 starts in 2 minutes). The next start tells the issues center how the run before ended (src/backend/lastrun.h): ravving keeps a marker, ~/.local/state/ravving/running, while it runs and removes it on a clean exit (SIGTERM, a normal return); data/start.sh writes last-exit (" ", 128 + n for signal n). A crash (signal 11, 6), a kill (9), a failure (exit 1: often the display went away) or the session ending first (no exit written: X stopped, as on 2026-10-11) each read as such, with the journalctl line to look at. Tested on milo: pkill -SEGV -x ravving → back 3 s later, the issue "ravving stopped unexpectedly" (error); systemctl --user restart ravving → nothing.

    Recipes

    Deploy and wait. sh tools/device.sh deploy syncs the tree (not build/), builds, installs, restarts the service and returns once the journal says audio and MIDI wired, plus a moment for the window. Keys sent while ravving boots are lost.

    Go somewhere and look.

    sh tools/device.sh cuia SWITCH_NUMBER_3_RELEASED        # page 3 (BASS)
sh tools/device.sh cuia SWITCH_ARROW_UP_RELEASED SWITCH_ARROW_UP_RELEASED
sh tools/device.sh tap 255 766                           # the bass's DRIVE chip
sh tools/device.sh shot /tmp/bass.png                    # 1280 × 800; crop with PIL to read details

    The CUIA names are zynthbox's: SWITCH_STEP5_PRESSED / _RELEASED (a step key held, then let go), SWITCH_MODE_RELEASED (LIVE), SWITCH_SELECT_RELEASED, SWITCH_BACK_RELEASED, KNOB0_UP … KNOB3_DOWN (knobs 1–3 and the big one). A step key with LIVE off edits the pattern on release: switch LIVE on (MODE) before using step keys as a test signal, and off again after.

    Call a backend method. sh tools/device.sh call pads loadSample 0 /zynthian/…/x.wav, call pads audition 0, call pads setFlag 0 looping true, call input record: the fifo's call|OBJECT|METHOD|ARGS… line (src/cuiafifo.h, fields split on | so paths keep their slashes) invokes any Q_INVOKABLE or slot on a machine (by its kits.json key), studio, input or take, converting the arguments; the journal logs each call with its arguments and whether it was found.

    Play notes as a keyboard. python3 tools/midifile.py /tmp/c2.mid 36 then sh tools/device.sh play /tmp/c2.mid (it goes in through Midi Through, 14:0, which ravving reads like any controller: the bass plays it when it is LIVE, or with nothing LIVE while its page is on screen). A chord: midifile.py /tmp/c.mid 40 52 67.

    Measure a sound. While a note plays (aplaymidi -p 14:0 /tmp/c2.mid & on the device):

    pw-jack python3 /tmp/meter.py TrackPassthrough:Channel4-lane1-dryOutLeft
# rms 0.0256 hf 0.001 crest 3.44

    Compare runs, never single numbers: an effect off, on, off again (the last run must match the first, or something else changed). hf/rms is brightness, crest falls with saturation or compression. Ports worth knowing:

    Port What it carries
    ravving-<machine>:<out> the engine itself (ravving-bass:lv2_audio_out_1)
    TrackPassthrough:Channel{t+1}-lane1-dryOutLeft a machine's track after its EQ/compressor/pan (bass: Channel4)
    TrackPassthrough:Channel{t+1}-lane1-wetOutFx1Left / Fx2 its reverb / delay send
    ravving-reverb:lv2_audio_out_1, ravving-delay:outputleft the send effects
    GlobalPlayback:dryOutLeft the master, before the LIVE FX inserts

    Measured references: the bass track ~0.026 RMS for a held C2, the drums 0.15–0.17 playing, reverb return 0.04 with a send on. A soloed machine (S) mutes the others' sends too: check the INSTRUMENTS chips before suspecting an effect.

    Check the wiring. ssh root@milo.local 'pw-jack jack_lsp -c' lists every connection; follow a machine from its engine: ravving-bass:lv2_audio_out_1 → SynthPassthrough:Synth4 → TrackPassthrough:Channel4-lane1 → AudioLevels:Channel4 → GlobalPlayback, with DRIVE on ravving-bass-drive between the engine and the synth slot. JackWiring logs audio and MIDI wired when every connection it wants exists, or some ports never appeared after 20 s.

    Try an engine. Before choosing one, run it alone and probe it:

    pw-jack jalv -n probe http://distrho.sf.net/plugins/Nekobi &     # on the device
pw-jack python3 /tmp/synthprobe.py probe:lv2_events_in probe:lv2_audio_out_1 \
    --notes "0.2:36:40:0.2 0.8:36:127:0.2 2.6:36:100:0.4 2.9:48:100:0.3"
python3 /tmp/analyse.py --segment "plain:0.2:0.4" --segment "accent:0.8:1.0" --track "slide:2.85:3.15"

    That is how Nekobi's accent threshold (velocity > 90) and its ~60 ms glide on overlapping notes were found.

    Try an effect. lv2probe.sh URI SOURCE MIDIFILE sym=val … runs a throw-away copy of an LV2 fed from a port and measures it, one setting per call; DRIVE's calibration (Calf Saturator: input gain, saturation, makeup) came from runs like lv2probe.sh http://calf.sourceforge.net/plugins/Saturator ravving-bass:lv2_audio_out_1 /tmp/n36.mid level_in=16 drive=5. lv2info URI lists a plugin's ports and ranges; lv2ls | grep -i word finds plugins.

    Test a time effect. Record the master after the repeat while holding a pad, then check the repeat: pw-jack python3 /tmp/record.py ravving-repeat:out_l --seconds 4.5 &, hold STUTTER (xdotool mousemove 400 113 mousedown 1; sleep 1.5; xdotool mouseup 1; the transport must play), then python3 /tmp/repeatcheck.py --file /tmp/record.npy --bpm 120 --length-steps 1: ~0 live, 1.000 while held. Dragging a held pad is xdotool mousemove steps of 5 px while the button is down.

    Read the saved state. /root/.local/share/ravving/project/session.json is the whole session (the same format as a project): machines (each one's steps or line, bars, kit, sound, effects, level, paused, preset…), bpm, swing, master, liveFx, globalEffects, ui. It is written 1.5 s after a change and on exit. Projects are in /zynthian/zynthian-my-data/ravving/projects/ (.current names the open one). To check a save/open round trip: copy session.json, SAVE, NEW, open the project again, and compare the two files' machines (a python one-liner; every machine should be identical). A backup of the pre-session layout is in /root/ravving-project-backup-20261005.

    From QML, give studio.uiValue() its fallback with ?? (a JS object does not convert to the C++ default), and know that a JS object passed to C++ arrives as a QJSValue (setUiValue unwraps it, or it would save as null).

    Logging. Categories are off by default:

    ssh root@milo.local 'systemctl --user set-environment QT_LOGGING_RULES="ravving.cuia.debug=true;ravving.midi.debug=true" && systemctl --user restart ravving'
sh tools/device.sh log 30

    ravving.cuia prints every key with where it landed (accepted/unhandled) and the focus chain; ravving.midi every external MIDI message. systemctl --user unset-environment QT_LOGGING_RULES turns them off again.

    Screenshots without the device. RAVVING_SCREENSHOT_DIR=dir RAVVING_STYLE=Basic RAVVING_NO_ZYNTHBOX=1 RAVVING_DATA_DIR=$PWD/data QT_QPA_PLATFORM=offscreen ./build/ravving captures every page and a few scripted states (src/main.cpp: add a step there, and find items by objectName with findItem()). It also shows QML warnings: a clean run prints nothing.

    Check the audio input. Read both channels while someone plays or touches the plug's tip (a finger on a working input hums around −30 dBFS; an open one sits near −75):

    pw-jack python3 /tmp/record.py "Built-in Audio Stereo:capture_FL" --seconds 10 --save /tmp/l.npy
amixer -c 3 sset "ADC Left Capture Source" "VINL1[SE]"     # try the ADC's other inputs

    Two cards are called "Built-in Audio Stereo" (the HiFiBerry and a Dummy, always −180 dBFS), and which one gets the number suffix (capture_FL-92) changes between boots: check with pw-dump (the port alias names the card) or ravving's journal line input ports. ravving finds them itself (InputPorts).

    Why a Bluetooth device does not connect or play. Read-only, nothing is connected or restarted, so it is safe while someone listens:

    sh tools/device.sh bt 6C:5A:B5:49:35:D8          # one device; no address: every known one
sh tools/device.sh bt 6C:5A:B5:49:35:D8 -1d      # only the last day of the journals
sh tools/device.sh bt capture 60 /tmp/lg.snoop   # btmon for 60 s: connect the device meanwhile
btmon -r /tmp/lg.snoop | less                    # or open it in Wireshark

    The report has the adapter and main.conf, the A2DP endpoints PipeWire registered (one per codec, shared by every device), WirePlumber's Bluetooth drop-ins, the PipeWire Bluetooth objects (card, sink, codec) and ravving's loopback, then per device its record (keys hidden), its cached A2DP endpoints decoded (which codecs it takes), the bluetoothd / WirePlumber / ravving journal lines and a tally: link up, Unable to select SEP, create-socket, page-timeout, profile-unavailable, A2DP transports opened. What each failure means, and the LG-vs-Sony case it was written for, is in bluetooth.md ("One audio device at a time"). In a capture, a page that is never answered shows as Create Connection followed by Connect Complete … Page Timeout; a link refused for lack of an endpoint shows the AVDTP Discover / Get Capabilities and then a disconnect with no Set Configuration.

    Traps met so far

    • zsh does not split $var into words: pass a stored argument list as ${=var}.
    • pkill -f/pgrep -f with a pattern that also matches the ssh command line kills or finds the shell itself.
    • jalv over ssh without pw-jack starts a real jackd and breaks the session's audio.
    • The machine finishes in Rave.machines are colour strings: .r/.g/.b are undefined (the colour silently comes out black or transparent). Type them first: readonly property color glow: finish.glow.
    • An Item delegate in a Layout needs implicitHeight (from its content), or the layout gives it nothing and its neighbours take the room.
    • A property int x: other meant as "the previous value" is a binding: it may update before the change handler reads it. Set it in Component.onCompleted instead.
    • Hardware events start at the focused item and bubble: a page that moves a selection on ▲ must first check whether the event came from its strip (stripFocused).
    • A QQC ComboBox takes the focus for good when tapped: use RaveComboBox.
    • Nekobi's output is quiet (−32 dB RMS): a saturator needs input gain to bite.
    • After a restart the window maps a few seconds after wired; a screenshot taken earlier is black.
    • amixer reads a negative value as an option (-4.5dB): put -- before sset.
    • A popup's QQC.Overlay.modal must be set on the popup itself: on the ApplicationWindow it does nothing with the Zynthbox style. A style-made popup (a ComboBox's list) cannot be given one: draw a ModalDim in the overlay under it.
    • Machines' sends leave the track lane before AudioLevels' gain: a VOL that should silence the echoes has to scale the sends too.
