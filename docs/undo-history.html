    The undo history

    What is undone, what becomes one step, the History API, making a feature undoable.

    How ravving undoes and redoes edits: the History class, what is recorded, and how a new feature becomes undoable. The classes are in the API reference.

    Ravving has one undo history for the project, History (src/backend/history.*), published to QML as studio.history. Everything that can be undone goes through it; nothing keeps an undo stack of its own.

    What is undone

    The patterns: every machine's notes, steps, chords, slots, accents, slides, lengths, automation, live timing and its preset's name (Machine::historyState()). Not the sound (source, factory sound, MODS), the mix (level, pan, mute), the effects or the project's settings (tempo, swing, key). Anything can join by becoming a participant (below).

    And the arrangement (Sections::historyState(), "SECTIONS"): which sections there are, their order, names, colours and lengths, and the song.

    • A removed section is put aside with its content (Sections::m_removed). Undoing the removal brings it back whole, in its place and in the song. Redoing it hands over to the neighbour, as REMOVE did.
    • Not in it: the section on screen, and the machines' content (they have their own). A pick is no step, so an undo never switches what plays. The one exception is a section added and then undone: the first section takes over.
    • Opening a project forgets the removed sections.

    Two ways back

    What it undoes Where
    The timeline the project's last step, whichever machines it touched the header's ↶ ↷; a toast names it ("UNDO · CHORDS + BASS")
    One machine that machine's last change only, wherever it is in the timeline the pattern toolbar's ↶ ↷ (machine.undo() / redo(), machine.canUndo / canRedo), BACK on its grid for ↶ (the cursor to machine.editStep in STEP entry)

    A machine can go back on its own because the participants' states are independent of each other: putting back the bass's last pattern cannot break the chords'.

    What becomes one step

    • One turn of the event loop. Everything recorded before control goes back to the event loop is one step. An action that changes several machines at once is undone in one go without any call: CLEAR (every machine), a key change that snaps the bass and the lead into the new key.
    • Quick changes of one participant. A change within History::MergeMs (500 ms) of the same participant's last one joins its step: a knob turning, a handle dragged, a SELECT move repeated.
    • A group. Everything between begin(label) and end() (they nest), for an action spread over several turns. Machines also have their own groups for a recorded take (Machine::beginEditGroup() / endEditGroup()): the take is recorded once, at its end.

    A step stores, for each participant it touched, the state before and after; nothing else. The history keeps History::Depth (100) steps.

    When the history forgets

    • forget(participant): its state is replaced wholesale, so its steps go (a section picked: undoing into a section that is not on screen would be a surprise; an engine attached again).
    • clear(): a project opened or NEW (Studio::applyProjectState()).

    The API

    C++ (History):
    add(p) / remove(p) register a participant (its state now is where it starts) / take it out
    record(p) after each change: a step, or part of the open one, when its state differs
    forget(p), clear() see above
    undo(), redo(), canUndo, canRedo, undoText, redoText the timeline
    undoIn(key), redoIn(key), canUndoIn(key), canRedoIn(key) one participant
    begin(label), end() a group
    signals changed(), undone(what), redone(what)

    QML: studio.history.undo(), .redo(), .canUndo, .canRedo, .undoText, .redoText, .begin(), .end(), .clear(); a machine's own: machine.undo(), .redo(), .canUndo, .canRedo.

    Making something undoable

    1. Implement HistoryParticipant (four functions):
      • historyKey(): a name unique among the participants ("bass", "song");
      • historyLabel(): how the user reads a step of it ("BASS", "SONG");
      • historyState(): its state as plain data, equal when nothing that matters changed (leave out what only says what is on screen: a bar shown, a tab);
      • applyHistoryState(state): become that state (it may emit its change signals as usual: the history does not record what it puts back).
    2. Register it: studio.history → history->add(this) once it exists (Studio does it for the machines, Machine::setHistory()).
    3. Call history->record(this) after each change the user makes (a machine does it on its edited() signal). Changes that are not the user's (a state restored, a project loaded) call forget(this) instead.
    4. Its own ↶ ↷, if it has any, call history->undoIn(key) / redoIn(key); their enabled state is canUndoIn(key) / canRedoIn(key), refreshed on changed().

    Nothing else: the timeline, the grouping, the toasts and the header's buttons come with it.

    Notes

    • historyState() is computed after every change, so keep it cheap (a map of the content); the machines' is their contentState() less the sound and the view.
    • One machine's undo clears the timeline's redo, since what it would redo doesn't match what's there.
    • A timeline undo of a step a machine was part of can be redone by that machine's ↷ too: it falls back to the timeline's redo.
