    Packaging

    The Store AppImage, the setup page, what the device needs, Bluetooth on a fresh device.

    ravving reaches a device as an AppImage in the Store's Apps category, installed as the Store installs any app:

    1. The Store downloads the file into ~/.local/share/zynthbox/apps/<author>/<name>/.
    2. It registers it with libappimage: a desktop entry in ~/.local/share/applications.
    3. It extracts it next to itself with --appimage-extract, as an <md5>.AppDir.
    4. From then on, zynthbox-qml launches that AppDir's AppRun when the entry is tapped.

    The bundle is for the Zynthbox device only. It's built on the device, for its architecture, against the Qt, zyncoder and Zynthbox QML modules the device already has. It holds ravving, the setup program, the data, and one library: libravving.so, ravving's own sound library.

    libravving.so is built from libravving/ beside ravving and installed as /usr/lib/libravving.so. zynthbox-qml's libzynthbox.so is not touched.

    building.md, "What ravving is made of", has the whole chain.

    What the AppImage starts isn't ravving but ravving-setup (setup/): a page over zynthbox-qml that installs ravving from the bundle and picks which UI the device runs.

    What the device needs

    Everything else ravving needs comes from the device, so it's listed in one place, data/requirements.json (installed with the data, and in the bundle), and checked in three places.

    The setup page, before installing

    default-app.sh deps DIR [--install] [--json] runs check-requirements.py from the bundle. It checks every requirement, and every library the bundle's ravving links to (ldd's "not found"). requirements.json's libraries names the Debian package of each library ravving links to.

    • The page lists what's missing, the feature each costs, and what brings it: a Debian package, or "in this bundle" for a file the AppImage carries (ravving's WirePlumber settings).
    • INSTALL WHAT IS MISSING puts the bundle's files in place and installs the packages (see "Installing what is missing" below), then checks again.
    • A startup requirement or library missing means ravving can't start there. TRY IT and MAKE IT THE DEFAULT stay dimmed until INSTALL WHAT IS MISSING has brought it: the title says FIRST, WHAT'S MISSING, and INSTALL is the page's orange button meanwhile.
    • A package the device's software sources don't have is named in the list and in the outcome. When ravving needs it to start, the update stays blocked: there is no fallback.
    • A choice tapped while the check still runs waits for it, and goes on only if ravving can start.

    The hand-off

    • TRY IT and MAKE IT THE DEFAULT hand over to ARU's party (the three shapes dancing) until Zynthbox stops, and the page with it; ravving's own splash comes next. A failure ends the party and the page says why.

    The install, and ravving itself

    • The install itself (default-app.sh install) puts the new binary beside the old one and checks it with ldd first. One that lacks a library isn't installed: the installed ravving stays as it was.
    • ravving, once started (Requirements, four seconds after the first frame). It checks the feature requirements by files and programs only: no process, microseconds.
    • Each missing one is a warning in the issues centre, like "MUSIC PLAYER will not work", with what it costs and the package for the device's admins.

    What ravving needs that a Zynthbox image may not have:

    Needed for What How it gets there
    everything Qt Quick Shapes, Virtual Keyboard (Qt 6 QML) qml6-module-qtquick-shapes, -virtualkeyboard
    starting at all the libraries ravving links to: Qt 6, KF6 BluezQt and I18n, TagLib 2, libsndfile (with LAME, mpg123, Vorbis), JACK, zlib, libgit2 libkf6bluezqt6, libtag2, libqt6multimedia6, … (requirements.json "libraries", one package per library; INSTALL WHAT IS MISSING fetches them)
    MUSIC PLAYER Qt Multimedia's FFmpeg backend libqt6multimedia6
    BLUETOOTH speakers / SEND PipeWire's Bluetooth plugin, BlueZ's obexd libspa-0.2-bluetooth, bluez-obexd (and tools/bluetooth-setup.sh's service steps)
    BLUETOOTH, INPUT ravving's WirePlumber settings (A2DP endpoints, one name per sound card) in the bundle (etc/wireplumber/…): install and INSTALL WHAT IS MISSING put them in /etc/wireplumber/wireplumber.conf.d/, applied from the next start
    synths, effects, drums jalv, lv2info, FluidSynth, the LV2 plugins and soundfonts the Zynthbox image's own packages
    sound at all libravving.so, ravving's sound library in the bundle (usr/lib): install puts it in /usr/lib

    Adding a feature that needs something new: add it to data/requirements.json (its files, programs, package, the feature and its effect, restart when it takes effect only from the next start), and to this table. A new library ravving links to goes into libraries with its package (dpkg -S on the device): ctest requirements-install fails on a build's library that has none.

    Installing what is missing

    INSTALL WHAT IS MISSING runs default-app.sh deps <bundle> --install --json:

    1. The files the bundle carries at the same path (etc/wireplumber/… for /etc/wireplumber/…) are copied into place. This needs no network.
    2. apt-get update, then apt-cache policy for the packages: those the device's package sources don't have are left out and named.
    3. apt-get install for the rest.
    4. The check again: the list, and the choices, follow what's there now.

    apt runs so that it can't hang or break:

    • in the system's environment: no AppImage folders on PATH or LD_LIBRARY_PATH, no Python virtualenv from zynthbox-qml, the standard XDG_DATA_DIRS;
    • with its input closed and DEBIAN_FRONTEND=noninteractive, keeping changed configuration files (--force-confdef --force-confold), so no question can wait for an answer;
    • waiting at most two minutes for another package manager's lock, with 30 s network timeouts;
    • after dpkg --configure -a when an earlier install was cut short.

    The page shows apt's latest line while it runs, and its ✕ waits until it's done. Then it says how it went:

    Outcome The message
    done what was installed; "Everything ravving needs is here", or what's left needs more than a package
    offline the device couldn't reach its package sources; nothing was installed
    locked another program is installing software; try again in a few minutes
    unavailable which packages the device's software sources don't have (the others are installed); when ravving needs one to start, that it can't be installed or updated until they do
    interrupted, timeout, failed what happened, with apt's last error
    restart a WirePlumber setting or the Bluetooth plugin was installed: restart the device

    Every script run, with its output, goes to ~/.local/state/ravving-setup/setup.log (and to zynthbox-qml's journal). ctest requirements-install walks every outcome against stand-ins for apt (tests/requirements-install-test.py).

    How it's installed

    The bundle is what cmake --install puts on the device. default-app.sh install DIR copies it from the bundle to the system paths:

    • the binary, checked with ldd before it replaces the old one (one that lacks a library is refused, and deps DIR --install gets its package);
    • /usr/share/ravving as a whole, so nothing of an older version stays behind;
    • the unit, the translations and the WirePlumber settings;
    • the bluetoothd path fix, where a drop-in starts a bluetoothd that isn't there.

    An update from any older version is the same install: what the older one put on the device is replaced, and its settings and session are kept.

    The setup page

    Four choices, each a default-app.sh command on the bundle's own copy of the script (so the script always matches the files it installs):

    Choice What it runs Effect
    TRY IT (LAUNCH RAVVING once installed, UPDATE AND TRY IT over an older one) install, then run ravving ravving now; Zynthbox at the next boot, or from ravving's POWER → ZYNTHBOX
    MAKE IT THE DEFAULT install, then ravving ravving at every boot (zynthbox-qml masked)
    ZYNTHBOX AT BOOT AGAIN zynthbox zynthbox-qml at boot; ravving stays installed
    REMOVE RAVVING (tap twice) zynthbox --purge the same, and ravving's program and data leave the system; projects, takes and recordings stay

    The page's title and its RIGHT NOW line come from default-app.sh status, re-read after every action: the installed version, what starts at boot, and what runs now.

    Its look and layout

    Laid out as the webpage's landing (design-system B22):

    • The column at the left, centred on the field's grain: the eyebrow (SETUP · BUNDLE), a title, the versions in orange and the lede. The title says where the device stands: TRY IT ON YOUR MIKO, UPDATE RAVVING, RAVVING IS READY, RAVVING STARTS AT BOOT or FIRST, WHAT'S MISSING.
    • The choices: TRY IT (the page's one orange button) and MAKE IT THE DEFAULT, then what each does and RIGHT NOW as the landing's list of ways. What the device lacks is a card under them.
    • The ways back at the foot under a hairline: ZYNTHBOX AT BOOT AGAIN and REMOVE RAVVING.
    • The sidebar at the right: one of the covers' artworks, a new one at each start, with the logo at its foot and the ✕ in its corner. The outcome line runs along the foot of the column.
    • When the column doesn't fit (a long list, longer words in Spanish or Japanese), it scrolls.

    It's in ravving's language (SETTINGS · LANGUAGE, else the system's), from ravving's own catalog. It links Qt only (ravving's style, kit and tokens are Qt only), so it starts on any Zynthbox.

    The choices

    The orange line reads by what the device has:

    Installed The line reads
    nothing "Version Y, ready to try."
    another version "From X to Y."
    this version "Version Y is installed." (the install step is skipped, and TRY IT reads LAUNCH RAVVING)

    A choice that would change nothing is dimmed: MAKE IT THE DEFAULT while ravving already boots, ZYNTHBOX AT BOOT AGAIN while Zynthbox does, and REMOVE while nothing is installed. The AppImage itself stays in the Store's list until it's removed there.

    Switching stops the UI that's running, and everything it started: the setup page under zynthbox-qml, or the script itself under ravving's ZYNTHBOX button. So the script re-runs the switching commands in a transient unit of its own (systemd-run --user --wait), and only then touches the services.

    • run APP switches for the session only. The boot default stays; a masked zynthbox-qml is unmasked for the start and masked again.
    • ravving and zynthbox change what boots.

    Building the AppImage

    The builder is NX AppHub CLI (nx-apphub-cli build), the tool the Zynthbox kit's other apps use, driven by packaging/appimage/ravving.yml.in, modelled on the kit's vvave bundle (UriHerrera/storage, AppImages/vvave/app_arm64.yml):

    • deps is empty, so nothing is downloaded; the zbkit repo entry is the kit's and goes unused;
    • our binaries get into the AppDir through the scripts/ folder next to the YAML, which nx-apphub copies into usr/bin before it looks for binarypath;
    • the data, desktop entry, icon and unit come from the install staging tree, through prebuild-commands;
    • binarypath and exec are ravving-setup: nx-apphub patches that binary's RPATH (with patchelf; the paths it adds do not exist in this bundle, which is harmless) and writes the AppRun for it;
    • runtime: go (go-appimagetool, a type-2 AppImage that --appimage-extract understands). The tool is an AppImage itself and the device has no FUSE 2, so it runs with APPIMAGE_EXTRACT_AND_RUN=1, and needs ARCH set because AppRun is a script.

    From the laptop:

    tools/device.sh appimage [OUT_DIR]     # default OUT_DIR: the Store packages folder beside the repo

    syncs the source, and installs nx-apphub on the device if it's missing (tools/install-nx-apphub.sh: patchelf and the Python dependencies from Debian, the CLI from its git checkout into a venv). Then it runs tools/build-appimage.sh there, and copies ravving-<version>-aarch64.AppImage back. On the device itself:

    cd /root/ravving && tools/build-appimage.sh dist

    The version

    The version is project(ravving VERSION …) in CMakeLists.txt. It names the file, fills usr/share/ravving/VERSION and shows on the setup page.

    The Store page's assets

    Next to the AppImage, the Store listing wants an icon and a gallery:

    • device.sh appimage also renders ravving-icon-512.png from data/icons/ravving.svg (the icon the bundle carries: ravving's mark, the two Vs and the pink diamond, on a dark rounded tile) into the same output folder;
    • device.sh gallery [OUT_DIR] screenshots each of the five pages of the ravving that is running on the device (ravving-1-drums.png … ravving-5-sampler.png, 1280 × 800, by the number keys) into the Store packages folder's gallery/; pick three for the page. Load a project worth showing first: the shots are of whatever is on screen.

    Before a release: the translations

    Every release has its translations reviewed:

    • someone who reads the language reads what changed in po/ and po-site/ since the last release;
    • the screenshot tour is taken in Spanish and Japanese;
    • ctest -R translations-current passes: no fuzzy or untranslated text, every placeholder kept, the translated pages rendered.

    Translations has the steps.

    The release check: tools/appimage-test.sh

    Run it after any release-worthy change (a version bump, a change to the setup page, the scripts or the unit), from the laptop:

    tools/appimage-test.sh            # build on the device, install like the Store, walk everything
tools/appimage-test.sh --no-build # the AppImage already in the device's dist/
tools/appimage-test.sh --keep     # leave the entry in the device's Apps list afterwards

    Run it on a freshly booted device. It switches between the two UIs six times in a few minutes. Several walks in a row can leave zynthbox-qml hung loading its sketchpad ("Starting engine …"): a Zynthbox and PipeWire wedge after many fast restarts, which only a reboot clears.

    It:

    1. builds the AppImage (device.sh appimage);
    2. installs it as the Store would (tools/store-register.py install): it registers with libappimage, extracts the AppDir, and points the desktop entry at its AppRun;
    3. checks the AppDir's contents;

    4. walks the page and ravving by touch, asserting default-app.sh status after each step:

    5. TRY IT from a purged system: ravving runs, and installed is the bundle's version. /usr/bin/ravving is the bundle's binary, byte for byte, and finds every library (ldd). The boot default is untouched;

    6. ravving's POWER → ZYNTHBOX: zynthbox-qml runs;
    7. MAKE IT THE DEFAULT: ravving runs and boots, zynthbox-qml is masked;
    8. ZYNTHBOX again: zynthbox-qml runs and stays masked for boot;
    9. ZYNTHBOX AT BOOT AGAIN: zynthbox-qml boots, ravving still installed;
    10. REMOVE RAVVING twice, then ✕: nothing of ravving left, the page gone.

    How the walk runs

    • The launch: tools/store-launch.sh starts the page in zynthbox-qml's own service cgroup, on the device's display. That's exactly a Store launch, so a switch that kills zynthbox-qml kills the page too, as in real use.
    • The record: screenshots and the status after every step go to analysis/appimage-test-<date>/. Eyeball the page shots for dimmed choices and messages.
    • Your data: the user's ravving settings (~/.config/ravving) and live session (~/.local/state/ravving) are copied aside before the walk's purge, and put back at the end, even after a failed step.
    • The device's state is put back at the end: a dev install by cmake --install, or ravving as the boot default by default-app.sh ravving. The Store entry is removed, unless --keep.
    • A failed assertion stops the run and prints the device's status. The device is then left mid-walk; tools/device.sh default zynthbox or ravving brings it back by hand.

    Testing an AppImage without the Store

    By hand on the device, the pieces the release check uses:

    tools/store-register.py install dist/ravving-0.5.0-aarch64.AppImage camiloh "Ravving 0.5.0"
                                   # → prints the AppDir; the entry shows in Apps at once
tools/store-launch.sh "$APPDIR"    # the page, as zynthbox-qml's Apps list would start it
tools/store-register.py remove "~/.local/share/zynthbox/apps/camiloh/Ravving 0.5.0/ravving-0.5.0-aarch64.AppImage"

    store-register.py does what registerAppImage / unregisterAppImage in zynthbox-qml's zynthian_gui_main.py do, minus the UI. Or, in zynthbox-qml: SCREEN_MAIN_MENU (tools/device.sh cuia), tap Apps, tap Ravving.

    The page is touch only, and tools/device.sh tap X Y drives it (REMOVE's first tap arms, the second removes). The choices keep one width and the outcome line keeps its room, so these points hold in every state but a long list of what is missing, which pushes the ways back down:

    Choice X Y
    TRY IT 291 300
    MAKE IT THE DEFAULT 605 300
    ZYNTHBOX AT BOOT AGAIN 283 643
    REMOVE 613 643
    ✕ (close) 1248 31

    The setup page off the device

    tools/setup-shots.sh [OUT_DIR] screenshots the page at 1280 × 800 in each state, in English, Spanish and Japanese: nothing missing, a fresh device, features missing, ravving unable to start, a long list, installing, and each install outcome. Look at every shot after changing the page: nothing may overlap, and the ✕ must be reachable.

    It runs build/setup/ravving-setup offscreen against tools/setup-fake.sh, a stand-in for default-app.sh whose answers its variables set (FAKE_LACKS, FAKE_INSTALL, FAKE_SLOW…). The program's own switches:

    Variable What it does
    RAVVING_WINDOWED=1 a window instead of full screen
    RAVVING_BUNDLE_DIR the bundle to show instead of the program's own
    RAVVING_SETUP_SCRIPT a stand-in for the bundle's default-app.sh; the page acts as on a Zynthbox
    RAVVING_SETUP_CALL a Bundle method to call once the page is up (installRequirements, tryIt…)
    RAVVING_SETUP_SHOT, RAVVING_SETUP_SHOT_DELAY save the page as a PNG after the delay (ms), and quit

    The setup page on a device without ravving's packages

    The release check runs on a device that has every package. To see the page as a fresh Zynthbox shows it, hide those packages from it. tools/without.sh (on the device, as root) starts a command in a private mount namespace where the paths given don't exist. Nothing changes on the device; only that command sees them gone.

    cd /tmp/rvx && APPIMAGE_EXTRACT_AND_RUN=1 /root/ravving/dist/ravving-<version>-aarch64.AppImage --appimage-extract
L=/usr/lib/aarch64-linux-gnu
H=$L/qt6/qml/QtQuick/Shapes,$L/qt6/qml/QtQuick/VirtualKeyboard,$L/libKF6BluezQt.so.6,$L/libtag.so.2
H=$H,$L/qt6/plugins/multimedia/libffmpegmediaplugin.so,$L/spa-0.2/bluez5,/usr/libexec/bluetooth/obexd
H=$H,/etc/wireplumber/wireplumber.conf.d/50-ravving-bluetooth.conf,/etc/wireplumber/wireplumber.conf.d/50-ravving-hardware.conf
setsid /root/ravving/tools/without.sh "$H" -- env DISPLAY=:0 XAUTHORITY=/root/.Xauthority /tmp/rvx/squashfs-root/AppRun &

    Start it over zynthbox-qml (stopping ravving takes the display down), and take shots with scrot (device.sh shot asks ravving). The page must:

    • start, and list every lack with its package;
    • keep TRY IT and MAKE IT THE DEFAULT dimmed;
    • run INSTALL WHAT IS MISSING through to its outcome.

    apt runs against the real system there, where the packages are already installed. It reports them installed, and the hidden paths stay listed.

    Bluetooth on a fresh device

    A stock Zynthbox (Debian 13, BlueZ 5.82, PipeWire 1.4, WirePlumber 0.5) cannot start bluetooth.service and registers no A2DP endpoints:

    Problem Cause Fix (shipped by ravving)
    bluetooth.service fails at boot (status 203/EXEC), the adapter stays DOWN, the control center says "its service is not running" zynthian-sys's drop-in /etc/systemd/system/bluetooth.service.d/01-disable-sap-plugin.conf starts /usr/lib/bluetooth/bluetoothd, which Debian 13 moved to /usr/libexec/bluetooth/ data/systemd/50-ravving-bluetoothd-path.conf, installed to the same drop-in folder: the same flags (--compat --experimental --noplugin=sap) with the path that exists
    a speaker or headphones pair but will not connect: org.bluez.Error.Failed br-connection-profile-unavailable; the adapter's UUIDs (bluetoothctl show) list no Audio Source / Audio Sink WirePlumber's Bluetooth monitor (monitors/bluez.lua) waits for a logind "active" seat before creating the BlueZ handle that registers the A2DP endpoints; the root startx session never reports one, so the monitor never starts and BlueZ has nothing to connect the device to data/wireplumber/50-ravving-bluetooth.conf, installed to /etc/wireplumber/wireplumber.conf.d/: wireplumber.profiles.main.monitor.bluez.seat-monitoring = disabled
    no audio over Bluetooth at all libspa-0.2-bluetooth (PipeWire's A2DP / HFP plugin with the SBC, aptX, FastStream, LDAC codecs) is not installed apt install libspa-0.2-bluetooth, then a WirePlumber restart (it loads the plugin at start)
    no file transfer bluez-obexd (the OBEX daemon, obex.service in the user session, D-Bus activated as org.bluez.obex) is not installed apt install bluez-obexd
    the Qt side ravving links KDE's BluezQt (libkf6bluezqt6; libkf6bluezqt-dev to build), which a stock image may lack ravving can't start without it: the setup page's INSTALL WHAT IS MISSING installs it before UPDATE is offered

    tools/bluetooth-setup.sh does all of it on a device and checks every step (--check only checks); cmake --install puts the two drop-ins in place as well. After the setup bluetoothctl show lists Audio Source, Audio Sink, Handsfree and Handsfree Audio Gateway.

    cmake --install and the AppImage's install put ravving's drop-ins in place, and the setup page's INSTALL WHAT IS MISSING installs the packages (bluez-obexd, libspa-0.2-bluetooth, libkf6bluezqt6); the first two take effect from the device's next start. tools/bluetooth-setup.sh does it all without the AppImage, restarting the services instead. --check verifies it afterwards.

    After the setup, bluetoothctl show lists Audio Source, Audio Sink, Handsfree and Handsfree Audio Gateway. ravving's WirePlumber drop-in also sets:

    • bluetooth.autoswitch-to-headset-profile = false, so recording from headphones never switches them to HFP;
    • bluez5.enable-sbc-xq.

    One more setting is the device's own, set by hand on a new image, since BlueZ reads no drop-in folder: FastConnectable = true under [General] in /etc/bluetooth/main.conf. With it, a speaker or headphones paging the device connect within a fraction of a second.
