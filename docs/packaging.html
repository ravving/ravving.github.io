Packaging

The Store AppImage, the setup page, what the device needs.

ravving reaches a device as an AppImage in the Store's Apps category, the way zynthbox-qml installs any app: the Store downloads the file into ~/.local/share/zynthbox/apps/<author>/<name>/, registers it with libappimage (a desktop entry in ~/.local/share/applications), extracts it next to itself with --appimage-extract (an <md5>.AppDir), and from then on launches that AppDir's AppRun from inside zynthbox-qml when the entry is tapped.

The bundle is for the Zynthbox device only. It is built on the device, for its architecture, against the Qt, libzynthbox, zyncoder and Zynthbox QML modules the device already has, so it bundles no libraries at all: just ravving, the setup program and the data. In particular the device must have the qml-style-zynthbox package (the Zynthbox QtQuick Controls style ravving selects at startup) and the qml-module-zynthbox package it imports (io.zynthbox.ui), as every stock Zynthbox does; see the README's build section for the whole chain. What the AppImage starts is not ravving but ravving-setup (setup/), a page over zynthbox-qml that installs ravving from the bundle and picks which UI the device runs.

What the device needs

The bundle carries no libraries, so what ravving needs from the device is listed in one place, data/requirements.json (installed with the data, and in the bundle), and checked twice:

  • The setup page, before installing (default-app.sh deps DIR [--install] [--json], which runs check-requirements.py from the bundle): every requirement, and every library the bundle's ravving links to (ldd's "not found"). The page lists what is missing, the feature each costs and the Debian package that brings it, with INSTALL MISSING PACKAGES (apt-get, online). A startup requirement or library missing means ravving cannot start there: TRY IT and MAKE IT THE DEFAULT stay dimmed and the list says why.
  • ravving, once started (Requirements, four seconds after the first frame): the feature requirements by file and program checks only (no process, microseconds), each missing one a warning in the issues centre: "MUSIC PLAYER will not work", what it costs, the package for the device's admins.

What 0.2.0 needs that a Zynthbox image may not have (all on milo; several installed by hand during development):

Needed for What How it gets there
everything the Qt 6 Zynthbox style (qt6/qml/Zynthbox) and QML module (io.zynthbox.ui) not packaged yet: built from qml-style-zynthbox and qml-module-zynthbox's dev/qt6-port (the Debian packages are Qt 5)
everything Qt Quick Shapes, Virtual Keyboard, Kirigami, KSvg (Qt 6 QML) qml6-module-qtquick-shapes, -virtualkeyboard, qml6-module-org-kde-kirigami, -ksvg
starting at all libraries ravving links to: Qt 6 Multimedia, KF6 BluezQt, TagLib 2, LAME, Vorbis, libsndfile libqt6multimedia6, libkf6bluezqt6, libtag2, … (requirements.json "libraries")
MUSIC PLAYER Qt Multimedia's FFmpeg backend libqt6multimedia6
BLUETOOTH speakers / SEND PipeWire's Bluetooth plugin, BlueZ's obexd libspa-0.2-bluetooth, bluez-obexd (and tools/bluetooth-setup.sh's service steps)
BLUETOOTH, INPUT ravving's WirePlumber settings (A2DP endpoints, one name per sound card) in the bundle (etc/wireplumber/…): install puts them in /etc/wireplumber/wireplumber.conf.d/, applied from the next start
synths, effects, drums jalv, lv2info, FluidSynth, the LV2 plugins and soundfonts the Zynthbox image's own packages
SAMPLE KING one-shots libzynthbox's fix for notes cutting each other (exclusivity group −1) not upstream yet (~/Coding/libzynthbox-bug-reports.md): a stock libzynthbox cuts a one-shot when the next starts; not detectable from ravving

Adding a feature that needs something new: add it to data/requirements.json (its files, programs, package, the feature and its effect), and to this table.

usr/bin/ravving, usr/share/ravving and the unit are exactly what cmake --install puts on the device: default-app.sh install DIR copies them from the bundle to the system paths.

The setup page

Four choices, each a default-app.sh command on the bundle's own copy of the script (so the script always matches the files it installs):

Choice What it runs Effect
TRY IT (LAUNCH RAVVING once installed) install, then run ravving ravving now; Zynthbox at the next boot, or from ravving's POWER → ZYNTHBOX
MAKE IT THE DEFAULT install, then ravving ravving at every boot (zynthbox-qml masked)
ZYNTHBOX AT BOOT AGAIN zynthbox zynthbox-qml at boot; ravving stays installed
REMOVE RAVVING (press twice) zynthbox --purge the same, and ravving's program and data leave the system; projects, takes and recordings stay

The cards above them (installed version, what starts at boot, what runs now) are default-app.sh status, re-read after every action. The two installing tiles read by what the device has: "Install this bundle and …" with nothing installed, "Update the installed X to this bundle's Y and …" with another version, and "ravving Y is already installed: …" with this one, in which case the install step is skipped (TRY IT then reads LAUNCH RAVVING). A tile that would change nothing is dimmed: MAKE IT THE DEFAULT while ravving already boots, ZYNTHBOX AT BOOT AGAIN while Zynthbox does, REMOVE while nothing is installed. The AppImage itself stays in the Store's list until it is removed there.

Switching stops the UI that is running, and with it everything it started: the setup page under zynthbox-qml, or the script itself under ravving's ZYNTHBOX button. The script therefore re-runs the switching commands in a transient unit of its own (systemd-run --user --wait) and only then touches the services. run APP switches for the session only (the boot default stays; a masked zynthbox-qml is unmasked for the start and masked again), while ravving and zynthbox change what boots.

Building the AppImage

The builder is NX AppHub CLI (nx-apphub-cli build), the tool the Zynthbox kit's other apps use, driven by packaging/appimage/ravving.yml.in, modelled on the kit's vvave bundle (UriHerrera/storage, AppImages/vvave/app_arm64.yml):

  • deps is empty, so nothing is downloaded; the zbkit repo entry is the kit's and goes unused;
  • our binaries get into the AppDir through the scripts/ folder next to the YAML, which nx-apphub copies into usr/bin before it looks for binarypath; the data, desktop entry, icon and unit come from the install staging tree through prebuild-commands;
  • binarypath and exec are ravving-setup: nx-apphub patches that binary's RPATH (with patchelf; the paths it adds do not exist in this bundle, which is harmless) and writes the AppRun for it;
  • runtime: go (go-appimagetool, a type-2 AppImage that --appimage-extract understands). The tool is an AppImage itself and the device has no FUSE 2, so it runs with APPIMAGE_EXTRACT_AND_RUN=1, and needs ARCH set because AppRun is a script.

From the laptop:

tools/device.sh appimage [OUT_DIR]     # default OUT_DIR ~/Coding/store-packages

syncs the source, installs nx-apphub on the device if it is missing (tools/install-nx-apphub.sh: patchelf and the Python dependencies from Debian, the CLI from its git checkout into a venv), runs tools/build-appimage.sh there and copies ravving-<version>-aarch64.AppImage back. On the device itself:

cd /root/ravving && tools/build-appimage.sh dist

The version is project(ravving VERSION …) in CMakeLists.txt; it names the file, fills usr/share/ravving/VERSION and shows on the setup page.

The Store page's assets

Next to the AppImage, the Store listing wants an icon and a gallery:

  • device.sh appimage also renders ravving-icon-512.png from data/icons/ravving.svg (the icon the bundle carries: the 808 plate, the big knob lit in the drums' orange over a step row) into the same output folder;
  • device.sh gallery [OUT_DIR] screenshots each of the five pages of the ravving that is running on the device (ravving-1-drums.png … ravving-5-sampler.png, 1280 × 800, by the number keys) into ~/Coding/store-packages/gallery/; pick three for the page. Load a project worth showing first: the shots are of whatever is on screen.

The release check: tools/appimage-test.sh

Run it after any release-worthy change (a version bump, a change to the setup page, the scripts or the unit), from the laptop:

tools/appimage-test.sh            # build on the device, install like the Store, walk everything
tools/appimage-test.sh --no-build # the AppImage already in the device's dist/
tools/appimage-test.sh --keep     # leave the entry in the device's Apps list afterwards

Run it on a freshly booted device. It switches between the two UIs six times in a few minutes, and after a few walks in a row (2026-10-10, the third) zynthbox-qml hung loading its sketchpad ("Starting engine JV/Helm") and only a reboot cleared it: a Zynthbox / PipeWire wedge after many fast restarts, not ravving's. After a fresh boot the same walk passed.

It builds the AppImage (device.sh appimage), installs it as the Store would (tools/store-register.py install, which registers with libappimage, extracts the AppDir and points the desktop entry at its AppRun), checks the AppDir's contents, then walks the page and ravving by touch, asserting default-app.sh status after each step:

  1. TRY IT from a purged system: ravving runs, installed is the bundle's version, /usr/bin/ravving is byte for byte the bundle's binary, the boot default is untouched;
  2. ravving's POWER → ZYNTHBOX: zynthbox-qml runs;
  3. MAKE IT THE DEFAULT: ravving runs and boots, zynthbox-qml is masked;
  4. ZYNTHBOX again: zynthbox-qml runs and stays masked for boot;
  5. ZYNTHBOX AT BOOT AGAIN: zynthbox-qml boots, ravving still installed;
  6. REMOVE RAVVING twice, CLOSE: nothing of ravving left, the page gone.

The page is started with tools/store-launch.sh, which puts it in zynthbox-qml's own service cgroup on the device's display: the exact situation of a Store launch, so a switch that kills zynthbox-qml kills the page too, as in real use. Screenshots and the status after every step go to analysis/appimage-test-<date>/ (eyeball the page shots: dimmed tiles, messages). The user's ravving settings (~/.config/ravving) and live session (~/.local/state/ravving) are copied aside before the walk's purge and put back at the end, a failed step included (a walk without this wiped them, 2026-10-10). Whatever the device had before is put back at the end: a dev install by cmake --install, ravving as the boot default by default-app.sh ravving; the Store entry is removed unless --keep. A failed assertion stops the run and prints the device's status; the device is then left mid-walk, and tools/device.sh default zynthbox or ravving brings it back by hand.

Testing an AppImage without the Store

By hand on the device, the pieces the release check uses:

tools/store-register.py install dist/ravving-0.3.0-aarch64.AppImage camiloh "Ravving 0.3.0"
                                   # → prints the AppDir; the entry shows in Apps at once
tools/store-launch.sh "$APPDIR"    # the page, as zynthbox-qml's Apps list would start it
tools/store-register.py remove "~/.local/share/zynthbox/apps/camiloh/Ravving 0.3.0/ravving-0.3.0-aarch64.AppImage"

(store-register.py does what registerAppImage / unregisterAppImage in zynthbox-qml's zynthian_gui_main.py do, minus the UI.) Or in zynthbox-qml: SCREEN_MAIN_MENU (tools/device.sh cuia), tap Apps, tap Ravving. The page is touch only; tools/device.sh tap X Y drives it: the tiles are the four quarters of the lower half (TRY IT 337 390, MAKE IT THE DEFAULT 943 390, ZYNTHBOX AT BOOT AGAIN 337 600, REMOVE 943 600), CLOSE 1160 736. A desktop look without a device:

QT_QPA_PLATFORM=offscreen RAVVING_WINDOWED=1 RAVVING_BUNDLE_DIR=<a staged bundle> \
  RAVVING_SETUP_SHOT=setup.png ./build/setup/ravving-setup

Bluetooth on a fresh device

A stock Zynthbox cannot start bluetooth.service and registers no A2DP endpoints (docs/bluetooth.md). cmake --install puts ravving's two drop-ins in place; the packages (bluez-obexd, libspa-0.2-bluetooth, libkf6bluezqt6) and the service restarts are tools/bluetooth-setup.sh's job, which the setup program should run (or the AppImage's first start), and which --check verifies afterwards.
