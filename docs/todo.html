    Needs the device and the user

    • Sound stalled on Bluetooth headphones after a new drum sound (user, 2026-10-12 05:07, Sony WH-CH720N, SBC-XQ): the DRUMS 2 engine restarted twice in 13 s (a GM soundfont drum), then silence, no issue reported, no PipeWire / bluez line in either journal; picking the output again (speakers, then the headphones) brought it back. Found: with Bluetooth as the output the jacks' ALSA sink was suspended (the master was unlinked from it), so the bluez sink (priority.driver 1010) was the graph's driver, against AudioOutputs' own design (the HiFiBerry, 10000, is meant to keep the clock). A Bluetooth transport that stalls as the driver stalls the whole graph silently. Fix applied the same day: the jacks stay linked and are MUTED (wpctl set-mute) while another output plays, so they keep the clock (AudioOutputs::setJacksMuted). VERIFIED live the same hour by hand (wpctl set-mute 59 1 + pw-link of the master to the jacks while the headphones played): the jacks sink took the clock back (pw-top: alsa_output the driver, the input and bluez following), the input's xrun counter stopped, and the user heard the samplers' mic clean again (it had been "awful": the mic's ALSA input was the graph's driver, 248 xruns). If it stalls again: tools/device.sh graph links, pw-top -b -n 2 and the bluez node's state from pw-dump BEFORE re-routing, then consider an OUTPUT STALLED watchdog (the bluez node leaving running while the transport plays → a notice and a re-route).

    Cosmetic and small fixes seen, not done

    • Chord names in flat keys (chords page review, 2026-10-09): C minor reads D#, G#maj7, A# where a musician expects E♭, A♭maj7, B♭; spell by the key signature (the parent major's flats or sharps), in the chord names and the rolls' row names together.
    • UNDO / REDO show bar 1 (same review): undoing an edit on bar 2 jumps the view back to bar 1; it should stay on (or go to) the bar the edit was on.
