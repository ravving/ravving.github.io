    The audio graph

    What ravving wires in PipeWire's JACK graph and the tools to look at it.

    What ravving wires, how to look at it and how to measure it. The graph is PipeWire's, seen by libzynthbox and the engines through PipeWire's JACK library (pw-jack), as zynthbox-qml also uses it. tools/graph-check.py (run with tools/device.sh graph …) does the checks below in one go.

    The graph ravving makes

    JackWiring (src/backend/jackwiring.*) asks libzynthbox's JackConnectionHandler for every link and retries until the ports exist (engines and passthroughs make their ports a moment after they are requested). Per machine (z: its Zynthian channel, t: its sketchpad track):

    ZLRouter:Zynthian-Channel{z} ─MIDI─> ravving-<key>-midi:midi_00          (FluidSynth)
                                      ravving-<key>:<lv2 midi in>         (jalv)
ravving-<key>:output_FL/FR ──> [DRIVE insert] ──> SynthPassthrough:Synth{z+1}-input{L,R}
SynthPassthrough:Synth{z+1}-dryOut ──> TrackPassthrough:Channel{t+1}-lane1-input
TrackPassthrough lane dryOut ──> AudioLevels:Channel{t+1} ──> GlobalPlayback:input
TrackPassthrough lane wetOutFx1 ──> ravving-reverb ──> GlobalPlayback:input   (send 1)
TrackPassthrough lane wetOutFx2 ──> ravving-delay  ──> GlobalPlayback:input   (send 2)
SamplerSynth:channel_{t+1}-sample{n} ──> the track's lane (the samplers' slots)
SamplerSynth:global-sketch1 ──> GlobalPlayback:input (the metronome's ticks)
GlobalPlayback:dryOut ──> ravving-repeat ──> ravving-crush ──> ravving-phaser (the master
    inserts: LIVE FX) ──> system:playback_1/2   (or ravving-out, a loopback, when the sound
    goes to Bluetooth / HDMI: [architecture.md](bluetooth.md))
jacks 4/5 (the HiFiBerry's capture, HardwarePorts) ──> [input inserts] ──> a track's lane (monitor) and / or
    AudioLevels:SystemRecorder (record); AudioLevels:SystemCapture meters the input

    The link PipeWire makes on its own from every new engine to the speakers is removed, as zynthbox-qml's autoconnect does, so all sound goes through its track (level, mute, FX).

    Clock: every JACK client (libzynthbox's nodes, jalv) runs at the graph's rate and period, 48000 / 256 on a Zynthbox. FluidSynth's audio goes through its PipeWire driver (a stream, so its node can run on its own clock): ravving tells it the graph's rate and period (AudioGraph, read once through a throwaway JACK client) so it is not resampled.

    Hardware port names

    ravving never trusts a hardware port's JACK name: pipewire-jack names a device's ports after its node's description, or system: for the default device, and two cards sharing a description take turns at the plain name and a -<serial> one from one start of PipeWire to the next. On a Zynthbox the kernel's snd-dummy and the HiFiBerry are both "Built-in Audio Stereo", so a name alone can point the input at the silent Dummy.

    • The device: data/wireplumber/50-ravving-hardware.conf hides the Dummy from PipeWire, so the HiFiBerry is the only "Built-in Audio Stereo", and (by its priority, 10000 against 1000) the system: device, on every start. libzynthbox and zynthbox-qml wire that name too.
    • ravving: HardwarePorts finds a card's ports by the card. In pw-dump each port's port.alias is ":" (kits.json input.portsCard), and its JACK name is the JACK port whose UUID carries that port's object serial (pipewire-jack makes a port's UUID as (1 << 32) | (serial + 1)). The input (captureOf) and the speakers (playbackOf, JackWiring::setSpeakers) are found that way at start; the input again each time it is armed (the RECORDER or INPUT opening).
    • Seeing it: pw-jack jack_lsp -U (the UUIDs) against pw-dump (the serials and aliases); the journal says ravving: input ports … and ravving: speakers ….

    Tools (all on the image)

    Tool What it shows Use
    pw-top -b -n 2 every node: driver (no +) or follower, QUANT/RATE it runs at, WAIT/BUSY per cycle, W/Q B/Q (fractions of the period), ERR (xruns), format the first thing to look at; tools/graph-check.py parses it
    pw-dump the whole graph as JSON: nodes with props (node.rate, node.latency, api.alsa.*), ports, links, devices with profiles scripting; pw-dump ID for one object
    pw-dot + dot -Tpng the graph as a picture pw-dot -o /tmp/g.dot; dot -Tpng /tmp/g.dot > g.png (graphviz on the laptop)
    pw-link -l / -o / -i links by PipeWire names (the only names some nodes have: the loopback's inputs) pw-link A:out B:in, pw-link -d to remove
    pw-jack jack_lsp -c / -l JACK names with connections / latency ranges ravving's and libzynthbox's names
    pw-mon events as they happen (nodes, links, params) watching an engine start or a link appear
    pw-metadata -n settings 0 the defaults (clock.quantum 1024, clock.rate) and forced values NOT the running clock: that is the driver row in pw-top
    pw-cli info ID one node's params (Props: channelVolumes…) volumes, formats
    wpctl status / inspect / set-profile WirePlumber's view: devices, profiles, defaults the sound card's profile (below)
    pw-jack jack_iodelay round-trip latency through a cable from an output jack to an input jack the only true end-to-end audio latency measurement
    pw-jack jack_midi_latency_test MIDI round trip through a loopback (a cable between a MIDI out and in, or a2j's Midi Through) MIDI path latency and jitter
    pw-jack jack_bufsize / jack_cpu_load the period, the DSP load JACK sees
    tools/mididump.py the MIDI an engine really receives on a port silent-engine investigations
    tools/meter.py RMS on any ports is sound passing a link
    tools/graph-check.py rates/periods vs the graph, xrun deltas, linked-but-idle nodes, the ravving links the routine check

    The routine (tools/device.sh graph all -s 60)

    1. rates: every audio node's rate and period against the running driver's. A node at another rate is resampled; a node with a larger period is buffered by that much.
    2. idle: nodes with links that are not running: a link that passes no data looks like this (an engine linked while still registering: re-make the link).
    3. xruns -s N: each node's ERR counter now and N seconds later. Compare idle vs playing, and before vs after a change.
    4. links ravving: what is linked, grouped by output port, to check against the map above.

    Clocks, threads and the debugger

    • FluidSynth is started with -r <graph rate> -o audio.period-size=<period> -o audio.periods=2: its node runs at the graph's rate, not resampled, buffered by two periods (48000 / 512, 10.7 ms). The ring is what keeps a busy engine from starving the graph.
    • Thread priorities (graph-check.py threads): PipeWire's data loops run FIFO 88 (daemon) and 83 (clients: libzynthbox's, jalv's, FluidSynth's); FluidSynth's own render thread (fluid_pipewire) is not realtime (its audio.realtime-prio 60 covers the synth thread only), jalv's main thread is not (it has no audio work); libzynthbox's SyncTimerThread runs FIFO 99 while the transport has run.
    • RAVVING_GDB=1 runs ravving under gdb -batch, which stops the whole process at every fork and thread start or exit: the graph then counts 20 to 40 xruns a minute. It is for crash hunts only: systemctl --user unset-environment RAVVING_GDB and a restart for a device that is used; tools/device.sh deploy says so when it finds it set. The same applies to any debugger or profiler attached to zynthbox-qml.
    • With nothing attached the graph has room to spare: a full project playing runs with 0 xruns, the busiest node (TrackPassthrough) at about 6 % of the period.

    MIDI

    • Sequenced notes: libzynthbox's SyncTimer schedules them on the JACK frame clock and ZLRouter puts each machine's on ZLRouter:Zynthian-Channel{z}, linked to the engine's MIDI input (above). tools/mididump.py PORT SECONDS prints what a port carries.
    • External keyboards: MidiRouter's hardware pass-through (MidiInput, port 3) feeds the LIVE machine; raw notes reach no engine on their own (the current sketchpad track is parked at 9). Midi Through arrives twice, through a2j and through PipeWire's Midi-Bridge, so copies closer than 4 ms are dropped (architecture.md).
    • Bluetooth MIDI: bluez_midi.server is PipeWire's BLE MIDI node, idle unless a BLE MIDI device connects.
    • Latency: measure a MIDI round trip with pw-jack jack_midi_latency_test between a hardware MIDI out and in joined by a cable (or a2j's Midi Through for the software path alone); an audio round trip with pw-jack jack_iodelay and a cable from an output jack into input jack 4 or 5.

    Who drives the graph

    The sound card's playback node is the driver (priority.driver 10000 from /etc/wireplumber/wireplumber.conf.d/99-default-soundcard.conf). It stays the driver whatever output is picked: with the sound routed to Bluetooth / HDMI the master's links to the jacks stay in place and the jacks are muted, since an unlinked playback node suspends and another node (the card's capture, or the Bluetooth transport) would become the clock.
